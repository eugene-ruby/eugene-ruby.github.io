Interactor помогает организовать бизнес-операцию как последовательность шагов с общим контекстом. Это полезно, когда нужно остановить цепочку при ожидаемой ошибке и компенсировать уже выполненные действия. Но откат здесь не автоматическая отмена всего, что произошло: у каждого побочного эффекта свои ограничения.

----
Вы уже используете `.call`, и у вас десяток `Service`.  
Но в одном — ошибка на шаге 3, в другом хочется отменить шаг 2, а третий возвращает `nil`, и никто не понимает почему.

Пора знакомиться с **Interactor**.

---

## 🧠 Теория

**Interactor** — gem для оформления бизнес-операций. Он передаёт данные через **контекст**, позволяет собирать шаги в цепочки и поддерживает методы компенсации `rollback`. Проверки входных данных при необходимости нужно писать самостоятельно: встроенной валидации параметров это не заменяет.

Gem поддерживает `collectiveidea`. Его можно использовать и без Rails, хотя примеры ниже рассчитаны на Rails-приложение.

---

## ⚙️ Пример

```ruby
class CreateUser
  include Interactor

  def call
    context.user = User.create!(context.params)
  rescue ActiveRecord::RecordInvalid => e
    context.fail!(error: e.record.errors.full_messages.join(", "))
  end
end
```

Вызов:

```ruby
result = CreateUser.call(params: {email: "user@example.com"})

if result.success?
  puts "Created: #{result.user.id}"
else
  puts "Ошибка: #{result.error}"
end
```

Здесь ожидаемая ошибка валидации превращается в неуспешный контекст. Не стоит перехватывать все исключения ради `context.fail!`: так ошибка в коде или недоступность базы будет выглядеть как обычный отказ создать пользователя. Если требуется проверять параметры до `User.create!`, добавьте её отдельно.

---

## 🚦 `.call` и `.call!`

Оба метода выполняют interactor. Если внутри вызван `context.fail!`, `.call` возвращает неуспешный контекст, а `.call!` выбрасывает `Interactor::Failure`. Контекст при этом доступен через исключение:

```ruby
begin
  CreateUser.call!(params: {email: "user@example.com"})
rescue Interactor::Failure => e
  puts e.context.error
end
```

Неожиданные исключения, которые код не обработал, не превращаются автоматически в `Interactor::Failure`. Выбирайте `.call!`, когда вызывающему коду удобнее обрабатывать ожидаемый отказ через исключение; в остальных случаях достаточно проверить результат `.call`.

## 🔁 С цепочками

```ruby
class SignupFlow
  include Interactor::Organizer

  organize CreateUser, CreateWallet, NotifyCrm
end
```

Если один из шагов вызовет `context.fail!`, последующие шаги не запустятся. Organizer вызовет `rollback` у ранее успешно завершившихся шагов в обратном порядке — но только если эти методы определены. Сам по себе `organize` не удалит созданного пользователя, не вернёт платёж и не отменит уведомление CRM.

---

## ⛑ Когда использовать?

* Нужно **собрать последовательность действий** и остановить её при ожидаемом отказе.
* Для выполненных шагов можно явно описать **компенсирующие действия**.
* Важно передавать между шагами **контекст** с результатами и ошибками.

Если операция короткая и не требует общего контекста или компенсации, обычного объекта с `.call` может быть достаточно.

## 🧱 Пример с rollback

```ruby
class ChargeCard
  include Interactor

  def call
    context.payment = Payment.charge!(context.user, context.amount)
  end

  def rollback
    Payment.refund(context.payment) if context.payment
  end
end
```

Здесь предполагается, что `Payment.charge!` возвращает платёж, по которому `Payment.refund` может оформить возврат; сигнатуру нужно согласовать с вашим платёжным API. Если шаг после `ChargeCard` завершится через `fail!`, Organizer вызовет его `rollback`. Это компенсация, а не гарантия атомарности: возврат тоже может завершиться ошибкой или не произойти мгновенно.

У `CreateUser` из примера выше метода `rollback` нет. Поэтому при сбое следующего шага созданная запись останется. Если это недопустимо, предусмотрите для неё подходящую компенсацию или используйте транзакцию базы данных там, где все нужные изменения можно выполнить в её пределах. Уже отправленное письмо или запрос во внешний сервис транзакция базы данных не отменит.

## 🤯 Когда interactor — зло

| Случай | Почему стоит пересмотреть решение |
| --- | --- |
| У каждого interactor по одной строке, а общего контекста и компенсаций нет | Дополнительные классы усложняют чтение без явной пользы. |
| Вся логика держится на `rollback` | Компенсации могут завершиться ошибкой; важно продумать состояние после частичного выполнения. |
| `Interactor::Organizer` используется для всего подряд | За цепочкой простых шагов бывает сложнее увидеть побочные эффекты и зависимости. |

---

## 📎 Советы из практики

* Делайте содержимое контекста понятным: какие поля нужны на входе, какие добавляет каждый шаг и где появляется `context.error`.
* **Не делайте interactor универсальным** — если он `DoEverything`, у вас не interactor, а intergalactic controller.
* Проверяйте в тестах не только результат `.call`, но и остановку Organizer после `fail!`, а также вызов нужных компенсаций.

---

## 🎤 Что сказать на собесе

> — Чем Interactor отличается от Service?

— `Service` обычно называют любой объект, оформляющий операцию; единого поведения у таких объектов нет. Interactor задаёт конкретный интерфейс с контекстом, `fail!` и, при использовании Organizer, последовательностью шагов и их компенсацией. Это удобно для сценариев с промежуточными результатами, но не избавляет от проектирования обработки ошибок и побочных эффектов.

---

## 🧾 Вывод

Interactor даёт общий интерфейс для операций и цепочек, а `rollback` позволяет явно описать компенсацию выполненных шагов. Если одного `.call` уже недостаточно, это может упростить управление сценарием. Главное — не путать остановку цепочки с гарантированным откатом всех изменений.
