Блокировки в PostgreSQL помогают избежать гонок при конкурентном изменении данных. В Ruby on Rails метод `lock` позволяет запросить `SELECT ... FOR UPDATE` и защитить обновление записи внутри транзакции. Для задач, не привязанных к конкретной строке, есть advisory locks.

---
У тебя два Sidekiq-потока, которые одновременно обновляют одну запись? Или гонка между пользователями за ресурсы? Добро пожаловать в мир блокировок.

## 🔒 SELECT FOR UPDATE

```ruby
User.transaction do
  user = User.lock.find(42)
  user.update!(balance: user.balance - 100)
end
```

`lock` добавляет к запросу **SELECT ... FOR UPDATE**. PostgreSQL блокирует выбранную строку до конца транзакции: другое обновление или запрос с конфликтующей блокировкой этой строки будет ждать. Обычному `SELECT` блокировка не мешает — он читает доступную версию данных.

---

## 🧬 Как это работает

* Если другой поток попытается обновить ту же строку или выполнить для неё `SELECT ... FOR UPDATE`, он будет ждать освобождения блокировки.
* При обычном уровне изоляции `READ COMMITTED` ожидающий запрос после завершения первой транзакции сможет прочитать актуальную версию строки. Поэтому чтение баланса и его изменение нужно выполнять в одной транзакции.
* Блокировка строки удерживается до конца транзакции. Без явной транзакции она освободится по завершении самого запроса и не защитит последующее обновление.

---

## ⚠️ Без lock — возможны гонки

```ruby
# Поток 1
user = User.find(1)
user.balance -= 100
user.save

# Поток 2
user = User.find(1)
user.balance -= 100
user.save
```

Если оба потока прочитают одинаковый исходный баланс до сохранения, каждый запишет значение на 100 меньше исходного. Итог: баланс уменьшится только на 100, хотя два списания должны были уменьшить его на 200.

---

## 🛠 Дополнительные опции

```ruby
User.lock("FOR UPDATE SKIP LOCKED")
```

* `SKIP LOCKED` пропускает строки, уже заблокированные другими транзакциями. Это полезно, когда несколько обработчиков выбирают задачи из общей таблицы и могут взять любую доступную задачу. Выборку и назначение задачи нужно выполнять в одной транзакции; для произвольного чтения данных пропуск строк не подходит.
* `NOWAIT` можно указать как `User.lock("FOR UPDATE NOWAIT")`. Если строка уже заблокирована, запрос сразу завершится ошибкой вместо ожидания. Если конфликта нет, он получит обычную блокировку до конца транзакции.

## 🧱 Advisory locks

Для взаимного исключения **на уровне логики**, не привязанного к блокировке строки, можно использовать advisory lock:

```ruby
ActiveRecord::Base.connection_pool.with_connection do |connection|
  connection.execute("SELECT pg_advisory_lock(12345)")
  begin
    # ... do critical section ...
  ensure
    connection.execute("SELECT pg_advisory_unlock(12345)")
  end
end
```

`pg_advisory_lock` ждёт освобождения ключа. Это блокировка на уровне сессии: она не снимается при завершении транзакции, поэтому освобождать её нужно на том же соединении даже при ошибке. Она защищает только код, который использует тот же ключ по общей договорённости; сама по себе записи таблицы она не блокирует. Если блокировка должна жить ровно до конца транзакции, для этого есть `pg_advisory_xact_lock`.

## 🤓 Как отлаживать

```sql
SELECT a.pid, a.query, a.wait_event_type,
       pg_blocking_pids(a.pid) AS blocking_pids
FROM pg_stat_activity AS a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0;
```

Запрос показывает ожидающие сессии и PID сессий, которые их блокируют. Подробности об удерживаемых и ожидаемых блокировках можно посмотреть в `pg_locks`. Сам по себе список блокировок не объясняет, почему возникло ожидание: сопоставляй его с запросами и состоянием транзакций.

## 📌 Резюме

| Метод                    | Когда использовать                                |
| ------------------------ | ------------------------------------------------- |
| `lock`                   | Читать и изменять строку внутри одной транзакции  |
| `FOR UPDATE SKIP LOCKED` | Разбирать доступные задачи несколькими обработчиками |
| Advisory lock            | Синхронизировать код по общему логическому ключу  |
| `NOWAIT`                 | Не ждать занятую строку, а сразу получить ошибку  |
