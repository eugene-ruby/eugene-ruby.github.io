Иногда в Ruby нужно вызвать метод, имя которого неизвестно до момента выполнения программы — например, при обработке пользовательского ввода или реализации плагинной архитектуры. Разберём `send`, `__send__` и `public_send`: какие методы они могут вызвать и почему выбор `public_send` сам по себе не делает внешний ввод безопасным.

---

## 🧠 Теория: зачем это нужно?

Представьте, что вы пишете:
```ruby
user.name # => "Анна"
```
Если имя метода (`name`) приходит из базы данных, API или конфига, его можно передать объекту во время выполнения.

---

## 🔧 1. `send` — "швейцарский нож"

**Как работает:**  
Вызывает метод объекта по имени, в том числе приватный или защищённый.

```ruby
class User
  private
  def secret_code
    "123-456"
  end
end

user = User.new
user.send(:secret_code) # => "123-456" (несмотря на private!)
```

**Когда использовать:**
- В метапрограммировании и DSL, если действительно нужен доступ к непубличному методу.
- Иногда в тестах приватных методов, когда проверить поведение через публичный интерфейс не получается.

**Опасность:**  
`send` обходит ограничения видимости. Если имя метода приходит извне, можно случайно открыть вызов метода, который не предназначен для такого использования.

---

## 🛡 2. `__send__` — если `send` переопределён

**Как работает:**  
Как и `send`, вызывает в том числе непубличные методы. Имя `__send__` полезно, если объект определил собственный метод `send`:

```ruby
class Hacker
  def send(*)
    "Взломано!"
  end
end

obj = Hacker.new
obj.send(:object_id)      # => "Взломано!"
obj.__send__(:object_id)  # => целое число — ID объекта
```

**Когда использовать:**
- Когда вызываемый объект может определить собственный `send`, а нужен исходный механизм динамического вызова.

`__send__` **не защищён от переопределения**: класс может определить и этот метод. Поэтому не стоит считать его средством защиты от недоверенного объекта или недоверенного имени метода.

---

## 🔒 3. `public_send` — "вежливый гость"

**Как работает:**  
Вызывает метод по имени, только если он публичный.

```ruby
class BankAccount
  private
  def balance
    @balance
  end
end

account = BankAccount.new
account.public_send(:balance) # => NoMethodError
```

**Когда использовать:**
- Когда динамический вызов должен оставаться в пределах публичного интерфейса объекта.
- При обработке внешнего ввода — вместе с проверкой списка разрешённых действий.

**Ограничение:**  
`public_send` не вызовет приватный метод, но среди публичных тоже могут быть нежелательные для пользователя операции. Поэтому одно только ограничение видимости не заменяет проверку имени метода.

---

## 🎯 Жизненные примеры

### 1. Динамический рендеринг в Rails
```ruby
# Вместо:
case action
when "show" then render_show
when "edit" then render_edit
end

# Можно, если render_show и render_edit — публичные методы:
allowed_actions = %w[show edit]
public_send("render_#{action}") if allowed_actions.include?(action)
```

Если `action` приходит из запроса, список разрешённых значений не даст вызвать другой публичный метод с префиксом `render_`.

### 2. Плагинная система
```ruby
plugins = [:twitter, :facebook]
plugins.each { |name| public_send("connect_#{name}") }
```

Здесь список плагинов задан в коде. Если имена приходят извне, их тоже нужно сверять со списком разрешённых плагинов.

### 3. Тестирование приватных методов (антипаттерн, но иногда нужно)
```ruby
describe "#calculate_tax" do
  it "returns correct value" do
    expect(calculator.send(:calculate_tax, 100)).to eq(20)
  end
end
```

Такой тест зависит от приватной реализации. По возможности проверяйте результат через публичное поведение объекта.

---

## ⚠️ Опасные паттерны

1. **Пользовательский ввод → `send`**  
   ```ruby
   # Если у model есть метод destroy_all, пользователь сможет его вызвать:
   params[:action] = "destroy_all"
   model.send(params[:action])
   ```
   `public_send` не решит проблему, если нежелательный метод публичный. Проверяйте имя по списку разрешённых действий до вызова.

2. **Чрезмерное использование в простых случаях**  
   ```ruby
   # Лишний динамический вызов:
   user.send(:name)

   # Прямой вызов понятнее:
   user.name
   ```

3. **Проверка `respond_to?` вместо проверки допустимости**  
   ```ruby
   if user.respond_to?(method_name)
     user.public_send(method_name)
   end
   ```
   Такая проверка помогает выяснить, доступен ли метод, но не отвечает на вопрос, разрешено ли вызывать его в этом сценарии. Для внешнего ввода сначала ограничьте допустимые имена.

---

## 🎤 Что сказать на собеседовании

> — В чём разница между `send` и `public_send`?

— `send` может вызвать и непубличный метод, а `public_send` — только публичный. `__send__` ведёт себя как `send` и полезен, если у объекта переопределён `send`, но сам тоже может быть переопределён. Ни один из них не заменяет список разрешённых методов при работе с внешним вводом.

---

## 🧾 Вывод

| Метод         | Публичные методы | Непубличные методы | Можно переопределить |
|---------------|------------------|--------------------|----------------------|
| `send`        | Да               | Да                 | Да                   |
| `__send__`    | Да               | Да                 | Да                   |
| `public_send` | Да               | Нет                | Да                   |

Для динамического вызова в пределах публичного интерфейса выбирайте `public_send`. Если имя метода приходит извне, дополнительно сверяйте его со списком разрешённых значений. `send` и `__send__` используйте, когда доступ к непубличному методу действительно необходим.
