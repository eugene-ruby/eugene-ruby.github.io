Docker помогает упаковать и запустить Rails-приложение, но для работы с PostgreSQL, фоновыми задачами и несколькими узлами нужны дополнительные инструменты. Разберём, какие задачи решают Compose, Swarm и Kubernetes и где проходят границы их возможностей.

---
Вы только что завершили новый фич-флаг в Rails-приложении.  
`docker build -t myapp .` → `docker run -p 3000:3000 myapp` — первый контейнер запущен.  
Но что дальше? Как поднять приложение вместе с базой данных? Как распределить нагрузку между репликами и управлять секретами?  
Время познакомиться с **экосистемой Docker**.

---

## 🐳 Docker: контейнеры как LEGO

### Основы
Docker упаковывает приложение и его зависимости в **контейнерный образ**, из которого запускаются изолированные контейнеры. Это помогает сблизить окружения разработки и развёртывания, но само по себе не гарантирует одинаковое поведение: важны также конфигурация, данные и зафиксированные зависимости. Контейнеры обычно запускаются быстрее полноценных виртуальных машин, хотя модель изоляции у них другая.

**Упрощённый Dockerfile для Rails:**
```dockerfile
FROM ruby:3.2
RUN apt-get update && apt-get install -y libpq-dev postgresql-client
WORKDIR /app
COPY Gemfile* ./
RUN bundle install
COPY . .
CMD ["rails", "server", "-b", "0.0.0.0"]
```

Для приложения с гемом `pg` пакет `libpq-dev` нужен при сборке нативного расширения. Сам Dockerfile не задаёт подключение к базе данных — его нужно настроить отдельно.

## 🎻 Docker Compose: оркестр для разработчика

### Зачем?
Когда проект состоит из Rails-сервера, PostgreSQL, Redis, Sidekiq и Elasticsearch, запускать каждый контейнер вручную неудобно. **Compose** описывает сервисы и связи между ними в YAML.

**Пример `docker-compose.yml` для Rails и PostgreSQL:**
```yaml
services:
  db:
    image: postgres:15
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Set POSTGRES_PASSWORD}
    volumes:
      - db_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d postgres"]
      interval: 5s
      retries: 5
  web:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://postgres:${POSTGRES_PASSWORD}@db:5432/postgres
    depends_on:
      db:
        condition: service_healthy
volumes:
  db_data:
```

Перед запуском задайте `POSTGRES_PASSWORD`, затем выполните `docker compose up -d`. Пример предполагает, что Rails использует `DATABASE_URL`. Если пароль содержит специальные символы URL, его нужно закодировать для строки подключения. Не сохраняйте реальный пароль в репозитории.

### Антипаттерны
1. **Веб-сервер, воркер и cron в одном контейнере.** Обычно их удобнее запускать как отдельные сервисы: ими можно управлять и масштабировать независимо. Это не означает, что в контейнере технически допустим только один процесс.
2. **Секреты в репозитории.** `env_file` удобен для передачи переменных, но не защищает файл с паролями. Для секретов выбирайте способ хранения и передачи, подходящий окружению; в Swarm для этого есть Docker Secrets.
3. **Надежда на порядок запуска.** Обычный `depends_on` задаёт порядок запуска контейнеров, но не ждёт готовности БД. В примере ожидание связано с `healthcheck`; он проверяет, что PostgreSQL принимает подключения, а не что выполнены миграции.

## 🐝 Docker Swarm: кластеризация «на минималках»

### Когда выбирать?
Swarm стоит рассмотреть, если нужны сервисы и реплики на нескольких узлах, а возможностей его встроенной оркестрации достаточно. Он проще по набору концепций, чем Kubernetes, но отказоустойчивость зависит и от устройства кластера, и от самого приложения.

**Развёртывание:**
```bash
docker swarm init  # на первом узле
docker stack deploy -c docker-compose.prod.yml myapp
```

Для `stack deploy` нужен подходящий файл конфигурации: в отличие от локального `docker compose up`, он не собирает образ из `build`. Образ приложения должен быть доступен узлам кластера. Один управляющий узел в примере позволяет начать работу, но не обеспечивает отказоустойчивость управления кластером.

**Плюсы:**
- Overlay-сети и встроенное распределение запросов между репликами сервиса.
- Масштабирование сервисов и настройка обновления реплик.

**Ограничения:**
- Автоматическое масштабирование по метрикам не входит в базовые возможности Swarm.
- Обновление без простоя не получается автоматически: нужны достаточное число реплик, ресурсы и корректные проверки состояния приложения.
- Экосистема расширений и инструментов меньше, чем у Kubernetes.

## ☸️ Kubernetes: промышленный стандарт

### Почему все говорят про K8s?
Kubernetes полезен, когда приложению нужны возможности управления развёртываниями, ресурсами и масштабированием, ради которых команда готова поддерживать более сложную платформу. Число микросервисов само по себе не определяет момент перехода.

**Основные концепции:**
- **Pod**: минимальная развёртываемая единица с одним или несколькими контейнерами.
- **Deployment**: управление желаемым числом реплик Pod и их обновлением.
- **Service**: стабильный сетевой доступ к группе Pod.
- **Ingress**: правила маршрутизации HTTP-трафика; для их применения нужен Ingress-контроллер.

**Пример `deployment.yml` для Rails:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: myapp:latest
        ports:
        - containerPort: 3000
```

Это схема Deployment, а не готовое развёртывание: образ должен быть доступен узлам кластера, приложению нужны конфигурация БД и проверки готовности. Для обновлений предпочтительнее указывать конкретную версию образа вместо изменяемого тега `latest`.

## 🔥 Боли реального мира

### 1. Миграции БД в Kubernetes
**Плохо:**
```yaml
command: ["rails", "db:migrate && rails server"]
```
Такой `command` не запускает оболочку: `&&` попадёт в аргументы `rails`, и ожидаемая последовательность команд не выполнится. Даже если запустить их через оболочку, миграция при старте каждой реплики создаст риск одновременного выполнения.

**Решение:** выполняйте миграции отдельным Job, согласовав его запуск с развёртыванием приложения. Init-контейнер может дождаться доступности БД, но сама по себе эта проверка не подтверждает, что схема уже обновлена.

### 2. Секреты
- Swarm: `docker secret create` и подключение секрета к сервису.
- Kubernetes: ресурсы `Secret` или интеграция с внешним хранилищем секретов. Значения в `Secret` не становятся защищёнными только потому, что закодированы в base64: доступ к ним нужно ограничивать, а хранение — настраивать с учётом требований безопасности.

### 3. Логирование
Без централизованного сбора логов разбирать сбои в кластере трудно. Возможные варианты:
- ELK-стек.
- Loki + Grafana.
- Сервисы облачного провайдера.

## 🧭 Что выбрать для Ruby-проекта?

| Инструмент | Когда использовать | Пример использования |
|---|---|---|
| Docker | Упаковка и запуск отдельного приложения | `docker run -p 3000:3000 myapp` |
| Compose | Локальная разработка, демо-стенды | Запуск Rails, PostgreSQL и Redis |
| Swarm | Кластер, которому хватает встроенных возможностей Swarm | Несколько реплик приложения на разных узлах |
| Kubernetes | Нужны возможности платформы и команда готова к её сопровождению | Развёртывание нескольких сервисов с отдельными правилами масштабирования |

Для монолита на Rails Swarm может быть разумным выбором, если нужны несколько узлов, а требования укладываются в его возможности. Переход в Kubernetes стоит обосновывать конкретными задачами, а не числом сервисов или версиями Ruby.

## 🎤 Что спросят на собеседовании

> — Как бы вы развернули Rails-приложение с фоновыми воркерами в K8s?

— Использовал бы Deployment для веб-сервера и отдельный Deployment для Sidekiq: их можно масштабировать независимо. Миграции запускал бы отдельным Job в процессе развёртывания. Секреты передавал бы через Kubernetes Secrets или интеграцию с внешним хранилищем, настроив права доступа.

## 🧾 Вывод

Docker упаковывает и запускает приложение, а выбор остальных инструментов зависит от задач:
- **Compose** связывает сервисы, например при локальной разработке.
- **Swarm** управляет сервисами на нескольких узлах, если его возможностей достаточно.
- **Kubernetes** даёт больше механизмов для управления кластером, но требует больше усилий на настройку и сопровождение.

Главное — не переусложнить. Небольшому проекту может хватить Compose, но файл `docker-compose.prod.yml` сам по себе не обеспечивает отказоустойчивость: её требования нужно продумать отдельно.
