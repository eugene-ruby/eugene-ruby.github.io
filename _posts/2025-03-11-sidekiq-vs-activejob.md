Когда Rails-приложению нужно отправить письмо, обработать CSV или выполнить другую долгую операцию, пользователь не обязательно должен ждать её завершения. Фоновые задачи позволяют вынести такую работу из обработки HTTP-запроса. Разберём, чем отличаются инструменты для очередей и какие ошибки возникают при работе с ними.

---
Вы только что нажали «Оплатить», а приложение поставило задачу в очередь: `ChargeCreditCardJob.perform_later(order_id)`. Если Active Job настроен на Sidekiq, задачу примет Sidekiq через Redis, а выполнит отдельный воркер. **Постановка в очередь ещё не означает, что платёж прошёл**: результат нужно отслеживать отдельно и показывать пользователю корректный статус.

---

## 🧠 Теория: зачем нужны фоновые задачи?

Фоновые задачи помогают:

1. **Сократить ожидание ответа** — долгая операция выполняется вне HTTP-запроса.
2. **Обрабатывать временные сбои** — если настроены повторные попытки и ошибка допускает повтор.
3. **Распределять нагрузку** — задачи могут выполнять отдельные воркеры.

Выбор зависит от объёма и характера задач, требований к задержке, доступной инфраструктуры и сложности сопровождения. Очередь сама по себе не гарантирует ни успешного выполнения, ни отсутствия дублей.

---

## 🛠️ Обзор инструментов

### 1. Sidekiq (⭐️ Популярный вариант)
```ruby
# Gemfile
gem 'sidekiq'
```

**Плюсы:**
- Выполняет задачи в потоках одного процесса
- Поддерживает отложенный запуск через `perform_in` и `perform_at`
- Предоставляет Web UI для наблюдения за задачами

**Минусы:**
- Требует Redis
- Многопоточность требует аккуратной работы с общим состоянием и внешними соединениями

**Когда выбирать:** Когда Redis подходит инфраструктуре проекта, а задачи можно безопасно выполнять параллельно.

---

### 2. Active Job (⚡️ Стандартный интерфейс Rails)
```ruby
# Конфигурация для приложения с Sidekiq
config.active_job.queue_adapter = :sidekiq
```

**Плюсы:**
- Даёт единый интерфейс для постановки задач
- Позволяет использовать разные адаптеры очередей
- Удобен для кода, который не должен зависеть от API конкретного обработчика

**Ограничения:**
- Это не отдельный обработчик очереди: хранение и выполнение задач зависят от адаптера
- Возможности конкретного обработчика не всегда доступны через общий интерфейс

**Когда выбирать:** Когда достаточно общего API Rails или важна возможность сменить обработчик. Если нужны специфические функции Sidekiq, их придётся настраивать отдельно.

---

### 3. Resque (🎩 Процессы вместо потоков)
```ruby
# Gemfile
gem 'resque'
```

**Плюсы:**
- Использует Redis и отдельные процессы-воркеры
- Поддерживает плагины

**Минусы:**
- Требует Redis
- Модель с отдельными процессами может расходовать больше ресурсов при большом числе воркеров; фактические затраты зависят от задач и конфигурации

**Когда выбирать:** Когда процессная изоляция задач полезна проекту или Resque уже используется в приложении.

---

### 4. Delayed::Job (🗄️ Очередь в SQL-базе)
```ruby
# Gemfile
gem 'delayed_job_active_record'
```

**Плюсы:**
- Хранит задачи через Active Record в SQL-базе приложения, например PostgreSQL или MySQL
- Не требует Redis

**Минусы:**
- Очередь создаёт дополнительную нагрузку на базу данных
- За состоянием таблицы задач и воркеров нужно следить

**Когда выбирать:** Для проекта, которому подходит хранение очереди в SQL-базе и не хочется добавлять Redis. При росте нагрузки оценивайте влияние очереди на основную базу.

---

## 📏 Как сравнивать производительность

Одни цифры для Sidekiq, Resque и Delayed::Job не помогут выбрать инструмент: результат зависит от содержимого задач, числа воркеров, настроек базы и Redis, оборудования и того, измеряется ли время ожидания в очереди или только выполнение. Active Job при этом не самостоятельный участник сравнения — он работает поверх выбранного адаптера.

Сравнивайте инструменты на задачах своего приложения. Помимо пропускной способности, смотрите на время ожидания, потребление памяти, поведение при сбоях и нагрузку на базу данных.

## 💥 Антипаттерны

### 1. «Мега-задача»
```ruby
class ReportGenerationJob < ApplicationJob
  def perform(user_id)
    # 200 строк кода, 5 SQL-запросов, 3 API-вызова
  end
end
```

**Проблема:** Если задача завершится ошибкой, повтор может заново выполнить уже сделанную работу, включая внешние вызовы.

**Решение:** Разделяйте работу там, где этапы можно завершать и повторять независимо. Зависимый этап ставьте в очередь только после успешного сохранения результата предыдущего: экспорт не должен стартовать до появления данных, а письмо — до готовности файла. Для каждого этапа продумайте поведение при повторном запуске. Не дробите короткую связанную операцию только ради числа задач: это усложняет отслеживание ошибок.

---

### 2. Игнорирование идемпотентности
```ruby
class ChargeCreditCardJob < ApplicationJob
  def perform(order_id)
    order = Order.find(order_id)
    PaymentGateway.charge(order.total) # Что, если задача выполнится дважды?
  end
end
```

**Проблема:** После списания воркер может завершиться до записи нового статуса заказа. При повторе одна лишь проверка статуса не защитит от второго списания.

**Решение:** Если платёжный шлюз поддерживает ключи идемпотентности, передавайте один и тот же ключ для повторов операции по заказу. Например:
```ruby
def perform(order_id)
  order = Order.find(order_id)

  order.with_lock do
    return if order.paid?

    PaymentGateway.charge(
      order.total,
      idempotency_key: "order-#{order.id}-charge"
    )
    order.update!(paid: true)
  end
end
```

Блокировка сериализует обработку заказа в этой базе, но удерживается и во время внешнего вызова. Она не делает платёж частью транзакции БД: при сбое между списанием и `update!` статус останется прежним. Ключ должен сохранять своё значение для повторов той же операции, а поведение при тайм-ауте и неопределённом результате нужно согласовать с возможностями шлюза. Если он не поддерживает идемпотентность, необходима сверка результата перед новым списанием.

---

### 3. «Тихий провал»
```ruby
class ImageProcessingJob < ApplicationJob
  def perform(image_id)
    image = Image.find(image_id)
    image.process!
  end
end
```

Удалённое изображение и временный сбой обработки требуют разной реакции. Если отсутствие записи ожидаемо и работу уже не нужно выполнять, задачу можно завершить без повтора:
```ruby
class ImageProcessingJob < ApplicationJob
  discard_on ActiveRecord::RecordNotFound

  def perform(image_id)
    Image.find(image_id).process!
  end
end
```

Если ошибка `process!` бывает временной, для её класса можно настроить ограниченные повторы, например `retry_on Image::ProcessingError, wait: 5.minutes, attempts: 3`. Не перехватывайте все исключения без разбора: постоянная ошибка не исчезнет от повторов, а подавленное исключение скроет сбой от обработчика очереди. Следите за задачами, которые исчерпали попытки.

## 🎛️ Интеграция с PostgreSQL

Delayed::Job с адаптером Active Record может хранить задания в PostgreSQL. Адаптер Active Job `:async`, напротив, держит очередь в памяти процесса Rails: он не использует PostgreSQL как хранилище заданий, и ожидающие задачи могут быть потеряны при завершении процесса.

### Блокировки

Воркеры Delayed::Job используют поля таблицы заданий, чтобы координировать получение задач. Не добавляйте индекс только потому, что очередь стала большой: подходящий индекс зависит от версии схемы и реальных запросов. Если выборка задач замедлилась, сначала изучите её план выполнения и существующие индексы.

### Оптимизация
```ruby
# config/initializers/delayed_job.rb
Delayed::Worker.destroy_failed_jobs = false
Delayed::Worker.max_attempts = 3
Delayed::Worker.max_run_time = 15.minutes
```

Эти настройки задают хранение неуспешных задач, число попыток и время, после которого заблокированную задачу можно считать доступной для другого воркера. Подбирайте `max_run_time` с учётом длительности реальных задач: слишком малое значение повышает риск одновременной обработки одной задачи несколькими воркерами. Сохранённые неуспешные задания требуют наблюдения и очистки по правилам проекта.

## 🎤 Что сказать на собеседовании

> — Почему вы выбрали Sidekiq, а не Resque?

— Нашим задачам подходит многопоточное выполнение, Redis уже есть в инфраструктуре, а Web UI помогает следить за очередями. Если бы была важнее процессная изоляция, мы бы отдельно рассмотрели Resque. Выбор по скорости подтвердили бы измерениями на задачах проекта, а не общим сравнением.

---

## 🧾 Вывод

1. **Нужен обработчик с многопоточным выполнением и Redis?** → Рассмотрите Sidekiq.
2. **Нужен общий интерфейс Rails?** → Используйте Active Job с подходящим адаптером.
3. **Хотите хранить очередь в SQL-базе без Redis?** → Рассмотрите Delayed::Job и нагрузку на базу.
4. **Нужна процессная изоляция или Resque уже есть в проекте?** → Resque остаётся вариантом.

Какой бы инструмент вы ни выбрали, отдельно продумайте повторы, наблюдение за сбоями и операции, которые нельзя безопасно выполнить дважды.
