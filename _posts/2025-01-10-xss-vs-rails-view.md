XSS (Cross-Site Scripting) позволяет злоумышленнику внедрить код в страницу, которую откроет другой пользователь. Rails экранирует вывод в шаблонах, но эту защиту можно обойти — иногда случайно. Разберём, где она работает и почему для JavaScript, CSS и ссылок нужны дополнительные меры.

---

## 🔒 Как Rails защищает от XSS по умолчанию

### Автоматическое экранирование в ERB
Rails использует ERB (Embedded Ruby) для шаблонов. При выводе обычной строки через `<%=` Rails экранирует специальные символы HTML:

```erb
<%= @user_input %> <!-- Символ < будет выведен как &lt; -->
```

Поэтому строка с тегом `<script>` не станет тегом в HTML-странице. Это защита при выводе в HTML, а не универсальное экранирование для любого контекста: JavaScript, CSS и URL требуют отдельного внимания.

### `raw` и `html_safe`: когда осторожность отключается
Если явно пометить строку как безопасную, Rails не будет экранировать её при выводе:

```erb
<%= raw @user_input %> <!-- Опасно для непроверенного ввода -->
<%= @user_input.html_safe %> <!-- Тоже опасно -->
```

**Пример уязвимости:**
```ruby
# Контроллер
def show
  @comment = params[:comment]
end
```

```erb
<!-- Шаблон -->
<div class="comment">
  <%= raw @comment %> <!-- Непроверенный HTML попадёт на страницу -->
</div>
```

Если в `comment` передать `<script>alert(1)</script>`, `raw` позволит браузеру обработать его как HTML. Здесь достаточно убрать `raw`, если комментарий должен отображаться как обычный текст.

## 💥 Где чаще всего ошибаются

### 1. JSON в JavaScript
```erb
<script>
  var data = <%= raw @user_data.to_json %>;
</script>
```

`raw` отключает экранирование HTML. Если сериализатор оставит в JSON последовательность `</script>`, браузер закроет тег ещё до того, как разберёт JavaScript, и следующий HTML может стать исполняемым. Проявится ли уязвимость в таком примере, зависит в том числе от того, как формируется JSON; полагаться только на `raw` нельзя.

Для вставки JSON непосредственно в `<script>` используйте `json_escape`, а не один лишь `to_json.html_safe`. Пример — ниже. По возможности передавайте данные вне исполняемого скрипта и учитывайте контекст, в котором их затем читает JavaScript.

### 2. Динамические CSS/JavaScript
```erb
<style>
  .profile { background: url(<%= @user_background %>); }
</style>
```

HTML-экранирование не проверяет синтаксис CSS: подставленное значение может изменить правило или добавить новые правила. При этом payload с `</style><script>`, переданный через обычное `<%= %>`, не закроет тег `style`: Rails экранирует символ `<`. Такой сценарий становится опаснее, если обойти экранирование через `raw` или `html_safe`.

Не вставляйте произвольный пользовательский текст в CSS. Если пользователь выбирает оформление, ограничьте выбор допустимыми значениями; для URL отдельно проверяйте разрешённые адреса.

### 3. Ошибки в хелперах
```ruby
def custom_link(text, url)
  "<a href='#{url}'>#{text}</a>".html_safe
end
```

**Проблема:** `html_safe` помечает всю собранную строку как безопасную, хотя `text` и `url` не экранированы. Используйте `link_to(text, url)` для сборки HTML. Но `link_to` сам по себе не проверяет, допустим ли адрес: если `url` приходит от пользователя, отдельно ограничьте разрешённые схемы и типы ссылок.

## 🛡️ Как защититься: лучшие практики

### 1. Оставляйте экранирование включённым
```erb
<%= @user_input %> <!-- Для вывода текста в HTML -->
```

Не добавляйте `raw` или `html_safe` к пользовательскому вводу только ради того, чтобы отобразить разметку.

### 2. Используйте `sanitize` для разрешённого HTML
Если пользователям действительно можно вводить часть HTML, задайте список допустимых тегов и атрибутов:

```erb
<%= sanitize @user_html, tags: %w[a b i], attributes: %w[href] %>
```

Это другой сценарий, не замена обычному экранированию текста. Проверяйте, соответствует ли выбранный список тегов и атрибутов требованиям вашего приложения.

### 3. Content Security Policy (CSP)
CSP — дополнительный уровень защиты, а не исправление небезопасного шаблона. Политику можно настроить в `config/initializers/content_security_policy.rb`:

```ruby
Rails.application.config.content_security_policy do |policy|
  policy.default_src :self
  policy.script_src :self
end
```

Такая политика разрешает загружать скрипты со своего источника, но блокирует встроенные `<script>` из примеров выше, если для них отдельно не настроены nonce или хеши. Подбирайте политику под используемые приложением ресурсы, не ослабляя её только ради обхода этих ограничений.

### 4. Учитывайте контекст при вставке JSON в JavaScript
```erb
<script>
  var data = <%= json_escape(@user_data.to_json).html_safe %>;
</script>
```

`json_escape` делает JSON безопаснее для размещения внутри тега `<script>`, а `html_safe` позволяет вывести получившийся JSON как выражение JavaScript, а не как экранированный HTML-текст. Этот приём относится именно к выводу JSON в таком контексте; для произвольной строки JavaScript или CSS он не подходит. При действующей CSP для встроенного скрипта также потребуется разрешённый политикой nonce или хеш.

## 🧪 Тестируем защиту

### Тест на экранирование в RSpec
Если `show` отображает `@comment` в приведённом выше шаблоне, тест должен проверять именно этот ответ, а не отправлять запрос к `create`:

```ruby
describe "CommentsController", type: :controller do
  render_views

  it "экранирует HTML в комментарии" do
    get :show, params: { comment: '<script>alert(1)</script>' }

    expect(response.body).to include('&lt;script&gt;alert(1)&lt;/script&gt;')
    expect(response.body).not_to include('<script>alert(1)</script>')
  end
end
```

Проверка экранированного текста важна: одно лишь отсутствие `<script>` не доказывает, что комментарий вообще был выведен.

### Используйте Brakeman
Добавьте в Gemfile:
```ruby
gem 'brakeman', require: false
```
И запустите:
```bash
brakeman -q -w2
```

Статический анализ помогает находить подозрительный вывод данных, но не заменяет проверку конкретных шаблонов и сценариев.

## 🎤 Что сказать на собеседовании

> — Как Rails защищает от XSS?

— Rails экранирует обычные строки при выводе через `<%=` в ERB, но `raw` и `html_safe` позволяют обойти эту защиту. Для JSON внутри `<script>`, CSS и ссылок нужно учитывать их собственный контекст; CSP служит дополнительным барьером.

## 🧾 Вывод

Rails помогает защищаться от XSS, пока вывод данных соответствует контексту и экранирование не отключено без необходимости. **Автоматическое экранирование — не волшебная палочка**: не помечайте непроверенный ввод как безопасный HTML, отдельно разбирайте вставки в JavaScript и CSS, а CSP используйте как дополнительную меру.
