Деплой приложения — это как первый полёт на самолёте, который вы собрали в гараже: немного страшно, зато хочется понять, как всё устроено. Разберём переход от ручной выкатки к проверке и развёртыванию через GitHub Actions на примере небольшого Flask-приложения.

---

## 🧠 Что такое деплой и зачем он нужен?

Деплой (от англ. *deploy* — развёртывание) — это доставка версии приложения в окружение, где им смогут пользоваться другие люди. Это не только перенос кода: приложению также нужны зависимости, настройки и способ запуска.

**Что может пойти не так при ручной выкатке:**
- Скопировали файлы, но забыли `requirements.txt` — зависимости на сервере не совпали.
- Запустили приложение, но забыли применить нужные миграции БД — запросы начали завершаться ошибками.
- Не проверили изменение перед выкаткой — ошибка обнаружилась уже у пользователей.

---

## 🚀 Простейший Flask-пример

Наше тестовое приложение (`app.py`):

{% raw %}
```python
from flask import Flask, request, render_template_string

app = Flask(__name__)

HTML = '''
<form method="POST">
  <input name="text" placeholder="Введите текст">
  <button type="submit">Отправить</button>
</form>
{% if text %}
  <p>Вы отправили текст: {{ text }}</p>
{% endif %}
'''

@app.route('/', methods=['GET', 'POST'])
def index():
    text = request.form.get('text')
    return render_template_string(HTML, text=text)

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
```

`requirements.txt`:
```
Flask==3.0.0
gunicorn
```
{% endraw %}

`app.run()` удобен для локальной разработки, но запускает сервер разработки Flask. В контейнере ниже приложение будет работать через Gunicorn. Для воспроизводимой сборки зафиксируйте и его версию в `requirements.txt` перед использованием в своём проекте.

## 🐳 Упаковываем в Docker

**Dockerfile** — инструкция по сборке образа:

```dockerfile
FROM python:3.9-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt

COPY . .

CMD ["gunicorn", "--bind", "0.0.0.0:5000", "app:app"]
```

Чтобы `COPY . .` не захватывала локальное окружение и файлы с секретами, добавьте `.dockerignore`:

```text
.git
.env
.venv
__pycache__
```

**compose.yaml** для запуска:

```yaml
services:
  web:
    build: .
    ports:
      - "5000:5000"
    restart: unless-stopped
```

Собрать образ и запустить приложение можно одной командой:

```bash
docker compose up -d --build
```

В примере порт 5000 опубликован на хосте. Перед размещением доступного извне сервиса продумайте сетевой доступ, HTTPS и хранение секретов отдельно от образа.

## 🔥 Почему CI/CD полезен даже для pet-проекта

1. **Повторяемая проверка.** Workflow может проверять изменение перед выкаткой. Но проверки нужно явно настроить: сами по себе они не появляются.
2. **Меньше ручных шагов.** После настройки один и тот же сценарий запускается при каждом push в выбранную ветку.
3. **Практика работы с окружением.** На небольшом проекте проще разобраться, какие зависимости нужны сборке и что должно быть подготовлено на сервере.

Автоматизация тоже требует обслуживания. Для проекта, который вы разворачиваете редко, её сложность стоит сопоставить с пользой.

## ⚙️ Настраиваем CI/CD через GitHub Actions

Ниже workflow сначала собирает образ и выполняет простую проверку HTTP-ответа через тестовый клиент Flask. Только после успешной проверки он подключается к серверу и собирает приложение там. Это **не полный набор тестов**: сборка на сервере повторяется, а не использует образ, проверенный в GitHub Actions.

`.github/workflows/deploy.yml`:

{% raw %}
```yaml
name: Deploy to server

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3

      - name: Build image
        run: docker compose build

      - name: Smoke test
        run: docker compose run --rm web python -c "from app import app; assert app.test_client().get('/').status_code == 200"

      - name: Deploy via SSH
        uses: appleboy/ssh-action@v1.0.0
        with:
          host: ${{ secrets.SSH_HOST }}
          username: ${{ secrets.SSH_USERNAME }}
          key: ${{ secrets.SSH_KEY }}
          fingerprint: ${{ secrets.SSH_FINGERPRINT }}
          script: |
            set -e
            cd /path/to/project
            git fetch origin main
            git checkout --detach ${{ github.sha }}
            docker compose up -d --build
```
{% endraw %}

Добавьте `SSH_HOST`, `SSH_USERNAME`, `SSH_KEY` и `SSH_FINGERPRINT` в Settings → Secrets and variables → Actions → New repository secret. Отпечаток SSH-ключа сервера нужно сверить по доверенному каналу, а не просто скопировать из первого подключения.

На сервере заранее нужны Docker с Compose, Git и чистая рабочая копия репозитория в `/path/to/project` с настроенным доступом к `origin`. Команда `git checkout --detach` разворачивает именно коммит, запустивший workflow; локальные изменения в этой рабочей копии могут помешать переключению. Пользователю SSH также нужны права на запуск Docker. Для проекта с БД отдельно продумайте порядок миграций и откат: этот пример их не выполняет.

## 💀 Антипаттерны деплоя

1. **Откладывать описание сборки.** Когда зависимости и команды запуска нигде не зафиксированы, воспроизвести окружение на новом сервере трудно.
2. **Забывать о миграциях БД.** Если новая версия кода ожидает изменённую схему, запросы могут завершаться ошибками. Планируйте совместимость схемы, порядок изменений и восстановление при сбое.
3. **Полагаться на «работает на моей машине».** Docker помогает описать окружение, но не делает локальную машину и сервер полностью одинаковыми: настройки, данные и доступные ресурсы всё ещё могут различаться.
4. **Выкатывать без возможности проверить результат и откатиться.** Успешное завершение `docker compose up` само по себе не подтверждает, что приложение отвечает пользователям.

## 🎤 Что сказать на собеседовании

> — Как вы организуете деплой?

Можно описать то, что действительно сделано: «Для небольшого Flask-проекта собираю образ Docker и запускаю его через Compose. GitHub Actions проверяет ответ приложения, затем по SSH разворачивает конкретный коммит на сервере. Для сервиса с БД дополнительно потребуются порядок миграций, проверка после выкатки и план отката». Не стоит называть этот workflow blue-green деплоем: переключения между двумя окружениями здесь нет.

## 🧾 Вывод

Автоматизация убирает часть ручных действий и позволяет проверять изменение до выкатки. Пример выше — отправная точка, а не гарантия безотказного релиза: добавляйте проверки, мониторинг и сценарий отката по мере того, как растут требования к приложению.
