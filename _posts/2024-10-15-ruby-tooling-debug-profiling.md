Вы когда-нибудь видели, как разработчик пытается отладить код, добавляя `puts` на каждом шаге? Иногда этого достаточно, но в сложном сценарии легко потеряться в выводе. Разберём три инструмента для разных задач: **debug** поможет остановить выполнение и изучить состояние программы, **Benchmark** — измерить время, а **StackProf** — найти участки, на которые приходится больше всего работы.

---

## 🐞 Debug: когда puts уже не смешно

### Теория: зачем нужен дебаггер?

`puts` показывает только то, что вы заранее решили вывести. Дебаггер позволяет остановиться в нужном месте, посмотреть стек вызовов и значения переменных. Начиная с Ruby 3.1, гем `debug` входит в стандартную поставку Ruby.

**Проблема:**
```ruby
# app/services/payment_processor.rb
def process
  validate_amount! # ошибка возникает при обработке платежа, но где именно?
  charge_card
  create_invoice
end
```

**Решение:**
```ruby
require "debug"

def process
  debugger # точка остановки; можно также использовать binding.break
  validate_amount!
  charge_card
  create_invoice
end
```

При запуске приложения через `rdbg` выполнение остановится на этой строке. В интерактивной сессии можно изучить стек вызовов, значения переменных и продолжить выполнение. `binding.break` — альтернатива `debugger`, а не обязательная вторая точка остановки.

---

### Антипаттерны дебага

1. **«puts-driven development»**
   ```ruby
   puts "Дошёл сюда, user_id = #{user.id}" # А потом забыли удалить
   ```
   Временный вывод полезен, но его легко забыть в коде или случайно записать в лог чувствительные данные.
2. **Интерактивная остановка в продакшене**
   Не оставляйте `debugger` или `binding.pry` в рабочем коде: выполнение запроса может остановиться в ожидании отладчика. Перед развёртыванием удаляйте временные точки остановки.

## ⏱ Benchmark: измеряем правильно

### Теория: почему Time.now — плохая идея

`Time.now` показывает системное время, которое может измениться во время замера. Для измерения длительности удобнее использовать `Benchmark` из стандартной библиотеки Ruby: он показывает как затраченное процессорное, так и прошедшее время.

**Проблемный код:**
```ruby
start = Time.now
1000.times { User.where(active: true).to_a }
puts "Затрачено: #{Time.now - start} секунд"
```

**Замер с Benchmark:**
```ruby
require "benchmark"

result = Benchmark.measure do
  1000.times { User.where(active: true).to_a }
end

puts result
```

Вывод `Benchmark.measure` содержит user CPU time, system CPU time, их сумму и прошедшее время в скобках. Для запроса к базе особенно важно смотреть на прошедшее время: ожидание ответа базы не равно времени работы CPU процесса Ruby. `to_a` здесь нужен, чтобы запрос действительно выполнился; создание `ActiveRecord::Relation` само по себе может не обратиться к базе.

---

### Практика: Benchmark IPS

Для сравнения числа выполнений в секунду можно использовать отдельный гем `benchmark-ips`. Например, так выглядит сравнение двух способов загрузить relation:

```ruby
require "benchmark/ips"

Benchmark.ips do |x|
  x.report("with to_a") { User.where(active: true).to_a }
  x.report("with load") { User.where(active: true).load }
  x.compare!
end
```

Но результаты такого теста не доказывают, что один способ всегда быстрее: `to_a` возвращает массив, а `load` — загруженный relation. Кроме того, каждый прогон зависит от базы данных и её кеша. Сравнивайте варианты с одинаковым требуемым результатом и проверяйте поведение на данных, похожих на реальные. Для запросов к базе одного показателя iterations per second недостаточно, чтобы объяснить причину разницы.

## 🔥 StackProf: находим узкие места

### Теория: профайлинг — это не роскошь

Когда приложение тормозит, но непонятно где, пригодится профайлер. `stackprof` периодически снимает стек вызовов Ruby-кода. Профиль помогает увидеть, в каких методах сосредоточены образцы выполнения; это не список всех вызовов и не прямое измерение утечек памяти.

**Установка:**
```bash
gem install stackprof
```

**Запуск:**
```ruby
require "stackprof"

StackProf.run(mode: :cpu, out: "tmp/stackprof.dump") do
  # ваш медленный код
end
```

Каталог `tmp` должен существовать. Режим `:cpu` помогает искать затраты процессорного времени; ожидание ответа базы или сети нужно дополнительно исследовать другими средствами, например логами запросов. У StackProf есть и режим для анализа выделений объектов, но он сам по себе не подтверждает утечку памяти.

---

### Анализ результатов

1. **Текстовый отчёт:**
   ```bash
   stackprof tmp/stackprof.dump --text
   ```
   Отчёт показывает число образцов и методы, в стеке которых они встречались. Большая доля образцов у метода — повод изучить его и вызывающий код, а не доказательство, что каждый его вызов медленный.

2. **Flamegraph:**
   ```bash
   stackprof --flamegraph tmp/stackprof.dump > tmp/flamegraph.html
   ```
   Flamegraph помогает рассмотреть цепочки вызовов. Не считайте файл, полученный с `--flamegraph`, JSON-профилем для https://speedscope.app: для этого просмотрщика нужен совместимый формат экспорта.

---

### Боль: когда профайлинг врет

1. **Слишком короткие запуски**
   Sampling-профайлер может собрать слишком мало образцов для короткого фрагмента кода. Профилируйте представительный сценарий и проверяйте число образцов в отчёте.

2. **Эффект наблюдателя**
   Профилирование добавляет накладные расходы. Не принимайте время выполнения под профайлером за обычное время ответа приложения.

## 🧪 Комбо: Debug + Benchmark + StackProf

**Пример сценария:** API endpoint замедляется под нагрузкой.

1. **Debug**
   В среде разработки ставим точку остановки перед подозрительным участком и смотрим состояние объектов. Сам по себе дебаггер не покажет, на что тратится время под нагрузкой.

2. **Benchmark**
   Замеряем выполнение участка, а не только создание ленивого запроса:
   ```ruby
   Benchmark.measure { Order.preload(:items).where(user: user).to_a }
   ```
   `to_a` заставляет выполнить запрос и загрузить связанные `items`. Такой локальный замер не заменяет измерения времени полного запроса.

3. **StackProf**
   Профилируем представительное выполнение запроса, чтобы найти участки с заметной долей CPU-образцов. Если подозреваем N+1 запросы, проверяем SQL-логи или инструменты анализа запросов: одного CPU-профиля для этого недостаточно.

---

## 🎁 Выводы

1. **Debug** — для точечной отладки и изучения состояния программы.
2. **Benchmark** — для измерения времени и сравнения сопоставимых вариантов.
3. **StackProf** — для поиска участков Ruby-кода, требующих внимания при профилировании.

Удалить временные `puts` тоже не забудьте.
