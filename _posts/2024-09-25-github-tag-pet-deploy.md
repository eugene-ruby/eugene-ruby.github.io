Выкатка релиза начинается с ответа на простой вопрос: какой именно коммит отправится в прод? Git-тег помогает закрепить за ним версию. Разберём SemVer, создание тегов и запуск деплоя через GitHub Actions.

---
Вы только что замержили фичу в `main` и думаете:  
«Как бы это красиво упаковать в релиз?»  
Один из вариантов — поставить Git-тег на коммит, который готов к выпуску. Но сначала — немного теории.

---

## 🧠 Теория: Semantic Versioning (SemVer)

Версия в SemVer имеет формат `MAJOR.MINOR.PATCH`. Буква `v` в имени тега — распространённое соглашение, а не часть номера версии:

| Часть | Когда увеличивать? | Пример |
|-------|--------------------|--------|
| MAJOR | При несовместимых изменениях публичного API | v1.0.0 → v2.0.0 |
| MINOR | При добавлении функциональности с сохранением совместимости | v1.1.0 → v1.2.0 |
| PATCH | При исправлениях с сохранением совместимости | v1.2.0 → v1.2.1 |

`v1.2.3.4-hotfix-beta` не соответствует SemVer: у основной версии должно быть ровно три числовые части. Для предварительного выпуска допустим, например, тег `v1.2.3-beta.1`. Слово `hotfix` само по себе не требует отдельного формата версии: если исправление сохраняет совместимость, обычно увеличивают `PATCH`.

## 🔧 Практика: создаём тег

```bash
# Просматриваем теги версий
 git tag -l 'v*' | sort -V

# Создаём аннотированный тег на текущем коммите
 git tag -a v1.2.0 -m "Релиз: добавлен платежный шлюз"

# Отправляем тег в удалённый репозиторий
 git push origin v1.2.0
```

`sort -V` упорядочивает имена тегов, но не определяет автоматически, какую версию выпускать следующей. Перед созданием тега убедитесь, что текущий коммит — именно тот, который прошёл необходимые проверки.

**Важно:** тег — не ветка. Он указывает на коммит и обычно остаётся неизменным после публикации. Технически тег можно переназначить, но для уже опубликованного релиза это опасно: у разных участников и систем CI одно имя может указывать на разные коммиты.

## 🤖 Автоматизируем через GitHub Actions

Пример workflow `.github/workflows/deploy-on-tag.yml`:

```yaml
name: Deploy on Tag

on:
  push:
    tags:
      - 'v*' # Это широкий фильтр: он включает и пререлизные, и тестовые теги

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Extract version
        run: echo "VERSION=${GITHUB_REF#refs/tags/}" >> "$GITHUB_ENV"

      - name: Validate release version
        run: |
          if [[ ! "$VERSION" =~ ^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$ ]]; then
            echo "Для production нужен тег вида vMAJOR.MINOR.PATCH" >&2
            exit 1
          fi

      - name: Deploy to production
        run: |
          echo "Деплоим версию $VERSION"
          ./deploy.sh "$VERSION"
```

Здесь `./deploy.sh` — скрипт вашего проекта, а не встроенная команда GitHub Actions. Фильтр `v*` сам по себе пропустит и `v1.2.0-rc.1`, и `v0.0.0-test`. Проверка версии остановит этот job до деплоя, если тег не похож на стабильный релиз. Она не заменяет проверку того, что коммит готов к выпуску: шаги `test` и `build` при необходимости добавляют **перед** деплоем.

## 💣 Опасные моменты

1. **Перезапись опубликованных тегов**  
   `git tag -f v1.2.0` переназначит локальный тег. Если затем принудительно обновить его на сервере, CI и разработчики могут получить разные коммиты под одним именем. Если релиз уже опубликован, безопаснее выпустить новый тег с новой версией.

2. **Теги из feature-веток**  
   Для production-релиза ставьте тег на проверенный коммит, который команда выбрала для выпуска, — например, из `main` или `release`-ветки. Git не запрещает тегировать feature-ветку, но один и тот же workflow не должен отправлять такие теги в прод.

3. **Тег до проверки готовности релиза**  
   Даже аккуратная история `main` не гарантирует, что сборка и тесты проходят. Если тег запускает деплой, проверьте выбранный коммит до публикации тега или поставьте необходимые проверки перед шагом деплоя.

## 🎛️ Продвинутые сценарии

### Пререлизные версии

```bash
git tag -a v1.2.0-rc.1 -m "Release Candidate 1"
```

Это допустимая пререлизная версия SemVer. В workflow выше такой тег вызовет запуск job, но не пройдёт проверку для production-деплоя.

### Генерация CHANGELOG

Используйте [git-chglog](https://github.com/git-chglog/git-chglog) для формирования списка изменений между тегами.

## 🧪 Тестируем стратегию

Сначала можно проверить создание тега локально, без запуска production workflow:

```bash
git tag -a v0.0.0-test -m "Test tag"
git show v0.0.0-test
```

Тестовый тег не соответствует формату стабильного релиза из примера выше. Не отправляйте его в репозиторий, где публикация тегов может запускать боевой деплой. Для проверки всей цепочки CI используйте отдельный репозиторий или окружение без production-деплоя.

---

## 🎤 Что сказать на интервью?

> — Почему выбрали деплой через теги?

Тег позволяет назвать конкретный коммит релиза и использовать публикацию этого тега как событие для CI. К прежней версии можно вернуться, если сохранились нужные артефакты и процесс деплоя поддерживает откат; сам тег откат не выполняет.

---

## 🧾 Вывод

Git-теги помогают связать имя версии с конкретным коммитом, а CI — запустить для него проверки и деплой. Но тег сам по себе не гарантирует стабильность: перед публикацией нужен проверенный коммит, а перед боевым деплоем — защита от неподходящих тегов.
