В CRuby потоки обычно не выполняют Ruby-код одновременно из-за глобальной блокировки интерпретатора (GVL). Для ввода-вывода это не обязательно проблема, но для вычислений на Ruby потоки могут не дать ускорения. `Ractor` позволяет выполнять такой код параллельно — ценой ограничений на доступ к объектам.

Ниже — примеры для Ruby 3.4. Сам механизм появился раньше; его API в этой версии всё ещё считается экспериментальным.

## 🧬 Что такое Ractor?

**Ractor** (Ruby Actor) — изолированный контекст выполнения Ruby-кода. Несколько Ractor'ов могут выполняться параллельно, но не должны совместно изменять обычные Ruby-объекты.

- Изменяемые объекты не становятся общей памятью между Ractor'ами.
- Для обмена данными используют сообщения: объект можно скопировать, переместить или передать без копирования, если он пригоден для совместного использования (*shareable*).
- Параллельное выполнение возможно, но само по себе не гарантирует ускорения: создание Ractor'ов и передача данных тоже требуют времени.

---

## 🚀 Пример: параллельное вычисление

```ruby
r1 = Ractor.new { Ractor.yield 1 + 2 }
r2 = Ractor.new { Ractor.yield 3 + 4 }

puts r1.take # => 3
puts r2.take # => 7
```

Здесь созданы два Ractor'а, результаты которых забирает основной Ractor. Они *могут* выполняться параллельно, но на таких коротких вычислениях ждать выигрыша в скорости не стоит.

---

## ⚠️ Но есть нюанс: не каждый объект можно разделить

Передавать сообщения можно не только с объектами `shareable`. По умолчанию изменяемый объект, который допускает копирование, копируется при отправке:

```ruby
r = Ractor.new do
  Ractor.yield "Я получил: #{Ractor.receive}"
end

r.send("hello")
puts r.take # => Я получил: hello
```

Строка `"hello"` изменяемая, но этот код не вызывает ошибку. Получатель работает с её копией. Ошибка возможна, если объект нельзя ни разделить, ни скопировать; кроме того, копирование крупных структур может быть дорогим.

---

## 🧊 Что можно передавать?

* Без копирования передаются, например, `true`, `false`, `nil`, числа, символы и строки, пригодные для совместного использования.
* `Object.new.freeze` пригоден для совместного использования.
* Массив тоже может быть `shareable`, если заморожен **и все его элементы** пригодны для совместного использования. Просто `freeze` у внешнего массива не замораживает вложенные объекты.
* Изменяемые строки и массивы часто можно отправить как сообщение: тогда по умолчанию создаётся копия, а не общий объект.

```ruby
r = Ractor.new do
  Ractor.yield Ractor.receive.inspect
end

r.send([1, 2, 3].freeze)
puts r.take # => [1, 2, 3]
```

Для вложенных структур можно использовать `Ractor.make_shareable(obj)`: метод рекурсивно замораживает объект и доступные из него объекты. Это меняет исходные данные, поэтому применять его к структуре, которую ещё нужно изменять, нельзя.

---

## 🆕 Ruby 3.4: что важно знать

`Ractor.make_shareable` и `Ractor::RemoteError` — не нововведения Ruby 3.4. Первый помогает подготовить данные для совместного использования; второе исключение позволяет узнать об ошибке внутри Ractor'а при получении результата:

```ruby
obj = { a: 1 }
Ractor.make_shareable(obj)

r = Ractor.new { raise "ошибка вычисления" }

begin
  r.take
rescue Ractor::RemoteError => e
  warn e.cause.message # => ошибка вычисления
end
```

После `make_shareable` исходный хеш заморожен. Если вызывающий код должен продолжить его менять, подготовьте отдельный объект или передавайте данные копированием. Нельзя также рассчитывать, что `make_shareable` подойдёт для любого объекта.

## 🧪 Коммуникация между Ractor'ами

```ruby
r = Ractor.new do
  msg = Ractor.receive
  Ractor.yield "Привет, #{msg}"
end

r.send("Ruby")
puts r.take # => Привет, Ruby
```

`send` отправляет сообщение получателю, а `yield` передаёт результат тому, кто вызовет `take`. Для ответа через очередь сообщений можно передать ссылку на отправителя:

```ruby
r = Ractor.new do
  from = Ractor.receive
  from.send("👋 Привет из Ractor")
end

r.send(Ractor.current)
puts Ractor.receive
```

Здесь основной Ractor ждёт сообщение через `receive`; в первом примере он забирал результат через `take`. При организации обмена важно понимать, на каком из этих вызовов каждая сторона будет ждать другую.

---

## 🧠 Где это применимо?

* Вычисления на Ruby, которые можно разделить на независимые части и для которых затраты на обмен данными приемлемы.
* Обработка данных, если задачи слабо зависят друг от друга, например отдельные операции сериализации или десериализации.

Для задач, упирающихся во ввод-вывод, могут подойти обычные потоки. Ractor не заменяет изоляцию процесса: `eval` внутри него **не** становится безопасной песочницей для недоверенного кода.

## 🔥 Частые ошибки

Нельзя просто захватить локальную переменную из внешнего блока и использовать её внутри нового Ractor'а. Передайте данные аргументом при создании:

```ruby
items = [1, 2, 3]

r = Ractor.new(items) do |data|
  data.sum
end

puts r.take # => 6
```

Если нужна общая для нескольких Ractor'ов структура без копий, проверьте, пригоден ли объект для совместного использования: `Ractor.shareable?(obj)`. Для изменяемых данных учитывайте стоимость копирования; при необходимости можно передать владение объектом с `send(obj, move: true)`, но после перемещения отправитель не должен пользоваться этим объектом. Сериализация, например через JSON, — ещё один вариант обмена данными, но она добавляет расходы и требует учитывать преобразование типов.
