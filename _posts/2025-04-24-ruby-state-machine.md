Enum в Rails удобен, пока статус — просто одно из нескольких значений. Вы начали с `enum status: [:draft, :published, :archived]`, а теперь в коде встречается `if post.draft? && user.admin? && !weekend? && moon_in_taurus?`. Похоже, правила смены статуса уже живут в разрозненных условиях.

Разберёмся, когда помогает **State Machine** (автомат состояний) и как описать переходы в Rails. Сам по себе enum при этом не «ломается»: проблема в том, что он не задаёт правила переходов.

---

## 🧙‍♂️ Теория: что такое State Machine?

**Автомат состояний** — модель, в которой:

- объект находится в одном из заданных состояний;
- разрешённые переходы между состояниями описаны явно;
- переход может зависеть от условия (guard) и сопровождаться колбэками.

Например, если в жизненном цикле статьи публикация разрешена только из черновика, попытку опубликовать архивную статью автомат отклонит. Какие именно переходы допустимы, решает бизнес-логика, а не библиотека.

---

## 💣 Когда enum становится врагом

```ruby
class Article < ApplicationRecord
  enum status: [:draft, :published, :archived]

  def publish!
    return if archived? || (draft? && !user.has_permission?)
    update!(status: :published)
    NotifySubscribers.call(self)
    AuditLog.record!(self)
  end
end
```

Здесь запрет для черновика без разрешения виден, но вызов `publish!` для уже опубликованной статьи тоже пройдёт к уведомлению подписчиков. Кроме того, запись статуса и внешние действия не образуют одну атомарную операцию: если уведомление или аудит завершатся ошибкой, статус уже может быть сохранён.

Когда таких методов становится много, трудно увидеть все допустимые переходы и проверить, что правила применяются одинаково. Для нескольких простых статусов без ограничений переходов enum по-прежнему подходит.

## 🚀 Переходим на стейт-машину

### Вариант 1: Пишем свою (для мазохистов)

```ruby
class Article
  STATES = %i[draft published archived].freeze

  def initialize(state)
    raise ArgumentError, "Неизвестное состояние" unless STATES.include?(state)

    @state = state
  end

  def publish!
    raise "Публикация разрешена только из черновика" unless @state == :draft

    @state = :published
  end
end
```

Для маленького объекта этого может хватить. Но хранение состояния, остальные переходы и согласованность при одновременных изменениях придётся реализовать отдельно. Этот пример не заменяет модель Active Record из следующего варианта.

---

### Вариант 2: Используем `aasm` (рекомендуется)

```ruby
class Article < ApplicationRecord
  include AASM

  aasm column: :status do
    state :draft, initial: true
    state :published
    state :archived

    event :publish do
      transitions from: :draft, to: :published, guard: :valid_author?
    end

    event :archive do
      transitions from: [:draft, :published], to: :archived
    end
  end

  def valid_author?
    user && user.has_permission? && !user.banned?
  end
end
```

Здесь `publish!` сохраняет переход из черновика в опубликованное состояние, а `archive!` — из черновика или опубликованного состояния в архив. Необъявленный переход вызовет `AASM::InvalidTransition`; для публикации также должен выполниться guard. Guard проверяет условие перехода, но не заменяет валидации модели.

Пример предполагает, что `status` хранит строковые значения состояний. Если в существующей статье `enum` создан из массива, его значения обычно хранятся как числа. Нельзя просто удалить объявление enum и подключить показанную конфигурацию AASM к тому же столбцу: сначала продумайте перенос существующих значений, значение по умолчанию и код, зависящий от enum-предикатов и scopes.

AASM поддерживает колбэки, но их наличие не делает внешние действия — например, отправку уведомлений — гарантированными или атомарными вместе с записью в базу.

## 🔥 Горячие грабли

### ⚠️ 1. Пропущенные переходы

```ruby
event :archive do
  transitions from: :published, to: :archived # из :draft перехода нет
end
```

Это ошибка, **если** черновики тоже должны архивироваться. Не нужно разрешать переходы из каждого состояния на всякий случай: сопоставьте схему с требованиями и проверьте как разрешённые, так и запрещённые переходы. Для AASM используйте его API, а не `Article.state_machine.states` из примеров для других библиотек.

---

### 2. Слишком много колбэков

Если уведомление, аудит, обновление поиска и сброс кеша спрятаны в колбэках перехода, у `publish!` появляются неочевидные побочные эффекты. Тестировать и разбирать ошибки становится сложнее.

Оркестрацию таких действий можно вынести в отдельный сервис, оставив правила переходов в модели:

```ruby
PublishArticle.call(article)
```

Но перенос в сервис сам по себе не решает проблему сбоев между сохранением статуса и внешним вызовом. Если уведомление должно отправляться только после успешного сохранения, предусмотрите запуск после коммита; если нельзя потерять задачу при сбое, нужна отдельная схема надёжной доставки, например transactional outbox.

---

### 3. Игнорирование конкурентности

```ruby
article.publish! # Запрос 1
article.archive! # Запрос 2, работающий параллельно
```

Если запросы загрузили статью до изменений друг друга, проверки переходов могут выполняться на устаревшем состоянии. AASM не устраняет эту гонку автоматически. В зависимости от сценария используйте оптимистичную блокировку Active Record со столбцом `lock_version` или блокировку строки на время чтения и изменения. При конфликте нужно заново загрузить запись и проверить переход, а не повторять запись вслепую. Особенно важно не запускать внешние побочные эффекты до того, как сохранение перехода подтвердилось.

## 📊 Сравнение гемов

| Гем | На что обратить внимание |
|-----|--------------------------|
| `aasm` | Декларативные переходы и колбэки; следите за побочными эффектами |
| `statesman` | Подход с отдельными записями переходов; потребуется продумать их хранение |
| `workflow` | Более компактное описание переходов; сравните нужные вам возможности с требованиями проекта |

Для примера выше выбран `aasm`, но универсального выбора нет: он зависит от того, нужна ли история переходов и как устроены сохранение и побочные эффекты.

## 🧪 Тестирование

Проверяйте не только успешный переход, но и отказ из неподходящего состояния или при невыполненном guard:

```ruby
RSpec.describe Article, type: :model do
  describe "state transitions" do
    let(:article) { create(:article, status: :draft) }

    it "публикует черновик при выполненном условии" do
      allow(article).to receive(:valid_author?).and_return(true)

      expect { article.publish! }.to change(article, :status)
        .from("draft").to("published")
    end

    it "не публикует черновик, если условие не выполнено" do
      allow(article).to receive(:valid_author?).and_return(false)

      expect { article.publish! }.to raise_error(AASM::InvalidTransition)
      expect(article.reload.status).to eq("draft")
    end

    it "не публикует архивную статью" do
      article.update!(status: :archived)
      allow(article).to receive(:valid_author?).and_return(true)

      expect { article.publish! }.to raise_error(AASM::InvalidTransition)
    end
  end
end
```

Отдельно проверьте сам `valid_author?` и остальные переходы. Архивирование гостем в показанной конфигурации не запрещено: у события `archive` нет такого guard.

## 🎤 Что сказать на собеседовании

> — Почему не enum?

— Enum подходит для набора значений. Когда появились правила, определяющие, из какого состояния и при каких условиях можно перейти в другое, мы описали их в автомате состояний. Так допустимые переходы видны в одном месте и их проще проверять тестами. Хранение, конкурентные изменения и внешние действия при этом требуют отдельного внимания.

---

## 🧾 Вывод

**State Machine полезна, когда статус стал жизненным циклом объекта**, а переходы обросли условиями. Она помогает явно описать правила, но не заменяет транзакции, блокировки и продуманную работу с побочными эффектами.

Если же статусы нужны лишь для хранения и выборки записей, усложнять модель автоматом состояний незачем.
