ActiveRecord в Rails помогает собирать запросы к PostgreSQL, но в цепочках с `select`, `group`, `having` и `merge` легко ошибиться. Разберём, где возникает ошибка, а где запрос работает — просто не так, как ожидалось.

---

Кажется, всё просто: добавил `joins`, сгруппировал через `group(...)`, отфильтровал через `having(...)`. А потом получаешь ошибку при чтении поля или результат не соответствует замыслу. Почему?

## 😵 select + group

```ruby
user = User.select("users.id").group("users.id").first
user.name
# => ActiveModel::MissingAttributeError
```

В запросе выбрали только `id`, поэтому `name` не загружен. ActiveRecord не возвращает для такого поля `nil`: попытка прочитать его вызывает ошибку. Если нужен `name`, добавь его в `select` и учти правила группировки PostgreSQL: выбираемые поля должны быть сгруппированы, агрегированы либо функционально зависеть от сгруппированных полей. Например, при группировке по первичному ключу `users.id` PostgreSQL позволяет выбрать остальные поля `users`.

---

## 🔍 having без group: не всегда ошибка

```ruby
User.joins(:posts).having("COUNT(posts.id) > 10")
```

Сам вызов `having` не выполняет запрос. В PostgreSQL `HAVING` без `GROUP BY` допустим, если запрос использует агрегатную функцию: все подходящие строки рассматриваются как одна группа. Пример выше проверяет число записей после соединения в целом, **а не число постов у каждого пользователя**.

Чтобы найти пользователей с более чем десятью постами, сгруппируй строки по пользователю:

```ruby
User.joins(:posts)
    .group("users.id")
    .having("COUNT(posts.id) > 10")
```

Если фильтр относится к отдельным строкам и не использует агрегаты, нужен `where`, а не `having`.

## ⚠️ merge и потеря условий

```ruby
# В модели User
scope :active, -> { where(active: true) }

Post.joins(:user).merge(User.active)
```

Здесь `joins(:user)` добавляет таблицу пользователей в запрос, а `merge(User.active)` применяет к ней условие scope. Если заменить `joins` на обычный `includes(:user)`, Rails может загрузить пользователей отдельным запросом. Тогда условие на `users.active` в основном запросе окажется без нужного соединения и запрос завершится ошибкой. Когда нужны и фильтрация, и предварительная загрузка ассоциации, можно явно указать оба намерения:

```ruby
Post.joins(:user).includes(:user).merge(User.active)
```

`merge` не гарантирует сохранение всех прежних условий: при объединении scope одной модели условия по одному и тому же атрибуту могут переопределяться. Проверяй итоговый запрос, если объединяешь пересекающиеся фильтры.

---

## 👀 А если `joins` + `merge`?

```ruby
User.joins(:posts).merge(Post.published)
```

Если у `Post` определён scope `published`, это подходящий способ применить его к соединённой таблице. Но `merge` не требует `joins` сам по себе: он объединяет отношения и без соединения, например `Post.where(author_id: 1).merge(Post.published)`. Соединение нужно в данном примере, чтобы условие на таблицу `posts` могло работать в запросе к `users`.

## 🧨 Итого — частые ловушки

| Конструкция | Подводный камень |
| --- | --- |
| `select("...")` | чтение невыбранного поля обычно вызывает `ActiveModel::MissingAttributeError` |
| `group(...).having(...)` | без группировки агрегатное условие относится ко всему набору строк, а не к каждому объекту |
| `merge(...)` | пересекающиеся условия могут переопределяться; условия другой модели требуют её таблицу в запросе |
| `joins(:assoc).merge(...)` | scope должен содержать условия, применимые к соединённой таблице |
| `includes(:assoc).merge(...)` | `includes` не всегда добавляет соединение в основной запрос |

---

📌 Если цепочка стала сложной, посмотри SQL через `.to_sql`. Он поможет заметить отсутствующее соединение или не ту группировку до выполнения запроса.
