Service Object в Ruby on Rails помогает вынести сценарий из контроллера или модели, когда операция состоит из нескольких связанных шагов. Разберём регистрацию пользователя: создание записей в базе, вызовы внешних сервисов и тест такого сценария.

---

Итак, у нас есть `CreateUser.call(params)`…  
А потом появляются `create_wallet`, `send_email`, `notify_crm`, `log_event`, `raise_if_duplicate`.  
Если одному классу приходится отвечать за весь сценарий, пора разобраться с его границами. Проблема не в методе `.call`: он вполне подходит и для Service Object.

---

## 🧠 Теория: что такое Service Object?

Service Object — это объект, отвечающий за **бизнес-процесс**. Обычно у него есть метод `.call` или `#call`, который координирует несколько связанных операций.

Он может вызывать другие объекты и работать с внешними API. Названия «команда» и «сервис» в Ruby-проектах используют по-разному: важнее договориться, за какой сценарий отвечает объект и где проходят границы его ответственности.

---

## 🔧 Пример

```ruby
class Users::SignupService
  def initialize(params)
    @params = params
  end

  def call
    user = User.transaction do
      user = User.create!(@params)
      Wallet.create!(user: user)
      user
    end

    SendWelcomeEmail.call(user)
    CrmNotifier.new(user).notify_signup
    user
  end
end
```

Вызывается так:

```ruby
Users::SignupService.new(params).call
```

Транзакция объединяет создание пользователя и кошелька: если одна из этих операций завершится ошибкой, изменения в базе откатятся. Отправка письма и уведомление CRM происходят **после** транзакции. Если один из этих вызовов завершится ошибкой, записи уже останутся в базе. Транзакция БД не может откатить внешний запрос. Если доставка обязательна, понадобятся отдельный механизм повторов и защита от повторной обработки — например, очередь с надёжной постановкой задачи или outbox.

---

## 💡 Когда применять?

Service Object полезен, если:

* Операция **многосоставная**: включает несколько шагов, зависимостей или моделей.
* Нужна **явная последовательность действий**.
* Контроллеру достаточно запустить сценарий, а не управлять каждым его шагом.

Но отдельный класс не нужен для каждого вызова модели. Если операция проста, сервис может только добавить лишний переход по коду.

---

## 🧪 Пример теста

```ruby
describe Users::SignupService do
  it "создаёт пользователя и кошелёк" do
    params = attributes_for(:user)
    allow(SendWelcomeEmail).to receive(:call)
    allow(CrmNotifier).to receive(:new)
      .and_return(instance_double(CrmNotifier, notify_signup: nil))

    expect {
      described_class.new(params).call
    }.to change(User, :count).by(1)
      .and change(Wallet, :count).by(1)
  end
end
```

Здесь внешние вызовы подменены, а создание записей проверяется через базу данных. Это тест сценария с участием БД, а не изолированный unit-тест. Отдельно стоит проверять, что сервис передаёт нужного пользователя отправщику письма и CRM, а также что происходит при ошибках на каждом шаге.

---

## 🔥 Когда это превращается в антипаттерн

| Случай | Почему это плохо |
| --- | --- |
| В сервисе 300 строк и 5 уровней вложенности | Трудно понять границы сценария и проверить его отдельные шаги |
| Сервис сам создаёт все зависимости, которые нужно заменять в тестах | Подмена внешних интеграций становится неудобной; при необходимости их можно передавать в сервис извне |
| В проекте множество сервисов с названиями вроде `UserCreateStep42Service` | По названию трудно найти бизнес-сценарий и понять ответственность класса |

Ещё одна боль — **неоднозначные пространства имён**. Где искать `BanUserService`: в `app/services/ban/`, `users/` или `actions/`? Об этом стоит договориться внутри команды.

---

## 🎤 Что сказать на собесе

> — Почему вы не пишете всю логику в моделях?

— Сложные сценарии можно вынести в сервисы, чтобы контроллеры не управляли каждым шагом, а модели не отвечали за внешние интеграции. Это также позволяет проверять сценарий отдельно, хотя само по себе не гарантирует простых тестов.

---

## 🧾 Вывод

Service Object помогает явно описать многосоставный бизнес-сценарий. Но новый класс не решает проблему автоматически: следите за его ответственностью и отдельно продумывайте ошибки на границе между базой данных и внешними сервисами.
