Сборка Docker-образа может замедлиться, если небольшое изменение в коде заставляет заново устанавливать все зависимости. А итоговый образ — разрастись из-за инструментов сборки и файлов, которые приложению не нужны. Разберём, как устроить Dockerfile, чтобы избежать этих проблем.

---

## 🐢 Почему образы собираются медленно?

Типичные причины:

1. **Частая инвалидация кэша** — если скопировать весь код до установки зависимостей, изменение файла приложения приведёт к повторному выполнению следующих команд.
2. **Лишняя работа при сборке** — установка пакетов и сборка приложения выполняются заново, когда нужные слои недоступны в кэше, например на новом CI-раннере.
3. **Лишние файлы в образе** — в финальный образ попадают инструменты сборки, кэши и файлы из контекста, которые не нужны при запуске.

Пример проблемного порядка команд:

```dockerfile
FROM ubuntu:latest
WORKDIR /app
COPY . .
RUN apt-get update && apt-get install -y ruby-dev nodejs
RUN bundle install
RUN npm install
CMD ["rails", "server"]
```

Здесь `COPY . .` стоит перед установкой зависимостей: изменение скопированного файла может сбросить кэш всех следующих шагов. Кроме того, этот фрагмент не стоит использовать как готовый Dockerfile для Rails: наличие `ruby-dev` само по себе не означает, что установлены Ruby и Bundler.

---

## 🧠 Принцип: «Меняется редко — ставь выше»

Docker проверяет кэш инструкций по порядку. Если кэш для одной инструкции не подходит, следующие инструкции тоже придётся выполнять заново — если не используются дополнительные механизмы кэширования.

Поэтому системные пакеты и зависимости приложения удобно устанавливать до копирования часто меняющегося кода. Важен не только порядок команд: не копируйте в образ файлы, которые не нужны для сборки.

---

## 🛠️ Практика: оптимизированный Dockerfile

Пример для приложения с `Gemfile.lock` и `yarn.lock`:

```dockerfile
FROM ruby:3.2-alpine

WORKDIR /app

# Пакеты для сборки гемов, работы с PostgreSQL и установки JS-зависимостей
RUN apk add --no-cache build-base nodejs yarn postgresql-dev

# Гемы переустанавливаются при изменении файлов Bundler
COPY Gemfile Gemfile.lock ./
RUN bundle install --jobs=4 --retry=3

# JS-зависимости переустанавливаются при изменении их манифестов
COPY package.json yarn.lock ./
RUN yarn install --frozen-lockfile

# Код приложения меняется чаще зависимостей
COPY . .

CMD ["bundle", "exec", "rails", "server", "-b", "0.0.0.0"]
```

**Что изменилось:**

- Взяли образ с Ruby вместо установки его поверх Ubuntu.
- Скопировали манифесты зависимостей отдельно от кода, чтобы изменения в приложении не заставляли повторять `bundle install` и `yarn install`.
- Перенесли `COPY . .` ближе к концу.

Это пример порядка сборки, а не универсальный набор пакетов для Rails: системные зависимости и команды установки нужно согласовать с конкретным приложением. Такой Dockerfile ускоряет повторную сборку, когда нужные слои доступны в кэше, но инструменты компиляции пока остаются в финальном образе.

## 🐘 Как уменьшить вес образа?

1. **Многоступенчатая сборка** — не переносим инструменты сборки в финальный этап.
2. **Очистка при установке** — если пакетный менеджер сохраняет кэш, удаляем его в той же инструкции `RUN`, где он появился. `apk add --no-cache` не сохраняет индекс пакетов.
3. **`.dockerignore`** — не отправляем в контекст сборки локальные зависимости, логи и другие ненужные файлы.

Пример для Rails-приложения, которое собирает assets с помощью Yarn:

```dockerfile
FROM ruby:3.2-alpine AS builder

WORKDIR /app
RUN apk add --no-cache build-base nodejs yarn postgresql-dev

COPY Gemfile Gemfile.lock ./
RUN bundle install --jobs=4 --retry=3

COPY package.json yarn.lock ./
RUN yarn install --frozen-lockfile

COPY . .
RUN bundle exec rails assets:precompile

# В этом примере JS-зависимости нужны только для сборки assets.
RUN rm -rf node_modules tmp/cache

FROM ruby:3.2-alpine

WORKDIR /app
RUN apk add --no-cache postgresql-libs

# В официальном Ruby-образе гемы по умолчанию находятся в /usr/local/bundle.
# Проверьте путь, если приложение задаёт собственный BUNDLE_PATH.
COPY --from=builder /usr/local/bundle /usr/local/bundle
COPY --from=builder /app /app

CMD ["bundle", "exec", "rails", "server", "-b", "0.0.0.0"]
```

Здесь оба этапа используют одно семейство образов и версию Ruby. Финальному образу всё равно нужны системные библиотеки, от которых зависят native-гемы; `postgresql-libs` покрывает только зависимость от PostgreSQL. Если приложению нужен Node.js при запуске, удалять `node_modules` и не устанавливать Node.js в финальном этапе нельзя. Для `assets:precompile` также могут потребоваться переменные окружения и настройка, зависящие от приложения.

Добавьте `.dockerignore`, например для `.git`, `node_modules`, `log`, `tmp` и локальных файлов с секретами. Проверьте список исключений: нужные при сборке файлы должны оставаться в контексте. Размер итогового образа зависит от приложения и его зависимостей.

## 🔥 Антипаттерны

| Ошибка | Последствия | Как исправить |
|---|---|---|
| `COPY . .` до установки зависимостей | Изменение скопированных файлов сбрасывает кэш последующих шагов | Сначала копировать манифесты и устанавливать зависимости, затем — код |
| Не очищать кэши пакетного менеджера | В слоях остаются ненужные файлы | Очищать их в той же инструкции `RUN`, где они появились; для Alpine использовать `apk add --no-cache` |
| Объединять несвязанные операции в один огромный `RUN` | При изменении части команды весь шаг выполняется заново | Разделять независимые шаги, но установку пакетов и очистку её кэша оставлять вместе |

## 🚀 Продвинутая оптимизация: базовые образы

**Задача:** на CI-раннерах не всегда доступен кэш слоёв с системными зависимостями.

Один из вариантов — собрать базовый образ и разместить его в registry:

```dockerfile
# Dockerfile.base
FROM ruby:3.2-alpine
RUN apk add --no-cache build-base nodejs yarn postgresql-dev
```

Сборка и публикация:

```bash
docker build -t my-registry/base-rails:latest -f Dockerfile.base .
docker push my-registry/base-rails:latest
```

Теперь его можно использовать в основном Dockerfile:

```dockerfile
FROM my-registry/base-rails:latest
```

Это избавляет основную сборку от установки системных пакетов, если готовый образ доступен. Но базовый образ нужно обновлять и учитывать время его загрузки. Для воспроизводимой сборки вместо изменяемого `latest` фиксируйте конкретный тег или digest. Кэш базового образа сам по себе не сохраняет результаты установки гемов и JS-зависимостей приложения.

## 🤖 CI/CD: стратегии сборки

На CI-раннере с постоянным Docker-кэшем обычная сборка уже может использовать сохранённые слои. Если раннер каждый раз получает чистое окружение, одного локального кэша недостаточно:

```yaml
# .gitlab-ci.yml: пример без внешнего кэша сборки
build:
  stage: build
  script:
    - docker build -t my-registry/my-app:latest .
    - docker push my-registry/my-app:latest
```

Для такого окружения можно хранить кэш BuildKit в registry:

```yaml
# .gitlab-ci.yml: пример с кэшем сборки в registry
build:
  stage: build
  script:
    - docker buildx create --use
    - docker buildx build --cache-from type=registry,ref=my-registry/my-app:buildcache --cache-to type=registry,ref=my-registry/my-app:buildcache,mode=max -t my-registry/my-app:latest --push .
```

Для второго примера раннеру нужны доступ к Docker, `buildx`, возможность записи в registry и аутентификация. Здесь кэш относится к сборке приложения, а не только к его базовому образу. Изменяемый тег `latest` в примере нужно заменить подходящей вашему процессу схемой тегирования.

## 🧪 Проверка эффективности

Полезные команды для анализа:
{% raw %}
```bash
# Показывает образы и их размер
docker images

# Показывает историю слоёв и размер, связанный с каждым шагом
docker history --no-trunc my-app

# Показывает размер образа в байтах
docker image inspect my-app --format='{{.Size}}'
```
{% endraw %}

`docker history` помогает найти тяжёлые шаги, но не показывает, какие файлы внутри них занимают место. Чтобы оценить выигрыш по времени, сравнивайте сборки в одинаковых условиях: с доступным кэшем или без него.

## 🎤 Что сказать на собеседовании

> — Как вы оптимизируете Docker-образы для production?

— Сначала проверяю, какие шаги пересобираются и что занимает место в образе. Затем выношу установку зависимостей до копирования кода, настраиваю `.dockerignore` и при необходимости использую многоступенчатую сборку. Если CI-раннеры не сохраняют локальный кэш, рассматриваю кэш в registry. Результат проверяю на сборках конкретного приложения.

## 🧾 Вывод

**Оптимизация Docker — это баланс между повторным использованием кэша и составом финального образа.** Порядок инструкций помогает не переустанавливать неизменные зависимости, а многоступенчатая сборка и `.dockerignore` не дают унести в production лишние файлы.

Главное: сначала найдите шаг, который отнимает время или место, затем меняйте Dockerfile и проверяйте результат в условиях вашего CI/CD.
