Если два запроса одновременно читают и меняют одну запись, один из них может перезаписать результат другого. Rails предлагает два подхода к таким конфликтам: **пессимистичную блокировку** строки на время транзакции и **оптимистичную блокировку** с проверкой версии записи.

---

## 🤔 Что такое пессимистичная блокировка?

Пессимистичная блокировка нужна, когда запись следует защитить на время операции: сначала прочитать её, затем изменить в рамках одной транзакции.

```ruby
User.transaction do
  user = User.lock.find(42)
  user.update!(name: "New name")
end
```

`User.lock` запрашивает строку с `SELECT ... FOR UPDATE`. Блокировка действует до завершения транзакции. Другая транзакция, которая попытается заблокировать или изменить ту же строку, будет ждать освобождения блокировки. Обычное чтение без блокировки при этом не останавливается.

Подход полезен, когда операция зависит от текущего состояния записи и конфликты вероятны. Транзакцию лучше держать короткой: длительные действия внутри неё увеличивают время ожидания для других запросов.

---

## 😌 Что такое оптимистичная блокировка?

Оптимистичная блокировка не удерживает строку за одним запросом. Вместо этого Rails проверяет перед сохранением, не изменилась ли запись с момента чтения.

### Шаг 1: Добавь `lock_version`

```ruby
rails generate migration AddLockVersionToUsers lock_version:integer
```

В созданной миграции задай столбцу значение по умолчанию и запрет `NULL`, в том числе для существующих записей:

```ruby
add_column :users, :lock_version, :integer, default: 0, null: false
```

Когда у модели есть `lock_version`, Active Record использует его для проверки версии при обычном сохранении записи:

```ruby
user1 = User.find(1)
user2 = User.find(1)

user1.update!(name: "Alice") # версия записи изменится
user2.update!(name: "Bob")   # ActiveRecord::StaleObjectError
```

`user2` была загружена до изменения `user1`, поэтому Rails обнаружит устаревшую версию и не сохранит `Bob`. Такой подход удобен, когда конфликты редки и приложение может показать их пользователю или повторить операцию после повторного чтения записи. Повторять изменение автоматически стоит только тогда, когда его можно безопасно применить к новым данным.

---

## 🔍 Когда использовать какой подход?

| Подход | Применять, если… |
| --- | --- |
| Пессимистичный (`lock`) | Нужно выполнить чтение и изменение записи в одной транзакции, а конкурирующие операции должны дождаться её завершения. |
| Оптимистичный (`lock_version`) | Конфликты ожидаются редко, и приложение готово обработать `ActiveRecord::StaleObjectError`. |

---

## ⚠️ Предупреждения

* Используй `lock` внутри транзакции, охватывающей всё чтение и изменение: вне неё блокировка освободится до последующего сохранения.
* При конфликте версий `ActiveRecord::StaleObjectError` возникает и с `update!`, и с `update`. Разница между ними касается, в частности, ошибок валидации: `update` возвращает `false`, а `update!` выбрасывает исключение.
* Оптимистичная блокировка работает, только если изменения записи участвуют в проверке и обновлении `lock_version`. Прямое изменение строки через SQL без учёта версии может обойти этот механизм.

Если в админке, фоновой задаче или API возможны конкурирующие изменения, выбирай подход по тому, нужно ли ждать завершения другой операции или обнаружить конфликт при сохранении.
