Индексы помогают ускорять запросы, но подходящий тип зависит от данных и условий поиска. Разберём B-tree, GIN, GiST и BRIN, покажем миграции Rails и посмотрим, как проверить результат.

---
Индексы — полезные друзья, но друзья бывают разные. Кто-то всегда рядом (`btree`), кто-то помогает искать внутри документа (`gin`), а кто-то тихо следит за диапазонами блоков (`brin`).

Разбираемся, **какие индексы** бывают в PostgreSQL и **как добавлять их в Rails**.

## 🧱 `btree`: универсальный солдат

Это индекс **по умолчанию**, если ты пишешь:

```ruby
add_index :users, :email
```

PostgreSQL создаёт B-tree — структуру, в которой значения упорядочены, как в телефонной книге.

* Подходит для `=`, `<`, `>`, `BETWEEN`.
* Может помочь с `ORDER BY`, если порядок столбцов и условия запроса позволяют использовать индекс.
* Занимает место и требует обновления при изменении индексируемых данных.

📌 Для обычного поиска по `email` это естественный первый вариант. Но даже подходящий индекс не гарантирует, что планировщик выберет его для каждого запроса.

---

## 🌲 `GIN`: поиск внутри JSON и массивов

Если `metadata` — столбец типа `jsonb`, запрос на проверку содержимого может выглядеть так:

```ruby
where("metadata @> ?", { status: "ok" }.to_json)
```

`GIN` (Generalized Inverted Index) хранит связи между элементами значения и строками, в которых они встречаются. Для такого запроса можно добавить индекс:

```ruby
add_index :logs, :metadata, using: :gin
```

* Применяется, в частности, к `jsonb`, массивам и `tsvector`.
* Поддерживаемые операции зависят от типа данных и класса операторов. Для `jsonb` индекс с классом операторов по умолчанию поддерживает `@>`.
* Занимает место и добавляет работу при записи; выигрыш зависит от запросов и данных.

📌 Если столбец имеет тип `json`, этот пример с GIN к нему напрямую не подходит: для показанного индекса нужен `jsonb`.

---

## 🌀 `GiST`: если у тебя PostGIS и шпионские координаты

`GiST` — расширяемая индексная структура для операций, которым не всегда подходит B-tree. Её используют, например, для пространственных данных PostGIS, диапазонов и иерархических путей `ltree`.

```ruby
add_index :places, :location, using: :gist
```

* Для геоданных нужны соответствующий тип столбца и расширение PostGIS; для `ltree` — расширение `ltree`.
* Польза индекса зависит от операторов в запросе и доступного для них класса операторов.

📌 Одного `using: :gist` недостаточно: сначала проверь, что тип столбца и условия запроса совместимы с таким индексом.

---

## 🔎 `BRIN`: спящий агент

Если таблица большая, а значения `created_at` примерно соответствуют физическому порядку строк, стоит рассмотреть BRIN:

```ruby
add_index :events, :created_at, using: :brin
```

BRIN (Block Range INdex) хранит сводную информацию о диапазонах блоков: например, минимальное и максимальное значение `created_at` для каждого диапазона.

* Обычно занимает меньше места, чем B-tree на том же столбце.
* Помогает пропускать диапазоны блоков, которые не могут содержать нужные строки.
* Может включить в кандидаты лишние блоки, поэтому PostgreSQL перепроверяет найденные строки.

📌 Если значения перемешаны по таблице или запрос выбирает небольшое число строк, B-tree может оказаться полезнее. Размер таблицы сам по себе не делает BRIN лучшим выбором.

---

## 🧠 Вся суть — в выборе под задачу

| Тип    | Когда рассмотреть |
| ------ | ----------------- |
| B-tree | `=`, `<`, `>`, `ORDER BY`, `BETWEEN` |
| GIN    | Поддерживаемые операции с `jsonb`, массивами, полнотекстовый поиск по `tsvector` |
| GiST   | Пространственные данные, диапазоны, иерархические пути `ltree` |
| BRIN   | Большие таблицы, где значения связаны с физическим порядком строк |

---

## 🛠️ Как в Rails?

Тип индекса задаётся в миграции через `using`:

```ruby
add_index :logs, :metadata, using: :gin
add_index :events, :created_at, using: :brin
```

Можно индексировать и выражение:

```ruby
add_index :documents, "to_tsvector('english', content)", using: :gin, name: :idx_fts
```

Чтобы этот индекс помогал полнотекстовому поиску, выражение в запросе должно ему соответствовать, включая конфигурацию `'english'`.

## 💡 Индексы ≠ магия. Проверяй EXPLAIN

Чтобы посмотреть фактический план выполнения запроса, используй:

```sql
EXPLAIN ANALYZE SELECT * FROM logs WHERE metadata @> '{"status": "ok"}';
```

Здесь предполагается, что `metadata` имеет тип `jsonb`. `EXPLAIN ANALYZE` выполняет запрос, поэтому учитывай это, когда проверяешь не только `SELECT`.

Для GIN в плане может появиться `Bitmap Index Scan`, для других индексов — `Index Scan`. `Seq Scan` не обязательно означает ошибку: например, последовательное чтение может быть выгоднее на маленькой таблице или когда условию соответствует большая часть строк. Сравнивай планы и время для своих данных и запросов.

---

## 🚨 Частые ошибки

* Добавить индекс, не проверив, поддерживает ли он оператор из запроса. Например, показанный GIN-индекс на `jsonb` подходит для `@>`, но это не значит, что он ускорит любое условие по `metadata`.
* Ожидать, что GIN-индекс из примера заработает на столбце типа `json`. Проверь тип столбца и при необходимости выбери подходящий тип данных или выражение для индекса.
* Полагаться на устаревшую статистику после крупных изменений данных. PostgreSQL обычно обновляет её автоматически, но если оценки в плане явно не соответствуют данным, проверь статистику и при необходимости выполни `ANALYZE`.
* Считать индекс бесплатным. Он занимает место и добавляет работу при `INSERT` и `UPDATE`; лишние индексы стоит пересматривать.
