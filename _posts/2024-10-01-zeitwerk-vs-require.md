В Ruby-проекте легко забыть `require` или ошибиться в относительном пути. Zeitwerk снимает часть этой работы: он связывает имена файлов с константами и загружает нужный код при обращении к ним. Разберём, как это устроено и в каких случаях одного соглашения об именах недостаточно.

---

## 🧠 Теория: от `require` к autoload

### Старая школа: ручное подключение

```ruby
# app/models/user.rb
require_relative "account"
require_relative "../../lib/validators/email_validator"

class User
  # ...
end
```

**Ограничения:**
- **Легко пропустить зависимость:** без нужного `require` обращение к константе может закончиться `NameError`.
- **Нужно следить за путями:** при переносе файла относительный путь придётся обновить.
- **Загрузка происходит при выполнении `require`:** даже если константа понадобится позже или не понадобится вовсе.

Это не делает `require` плохим инструментом: он по-прежнему нужен, например, для подключения библиотек, которые не управляются автозагрузчиком.

### Новый мир: autoload в Ruby

Ruby давно поддерживает встроенный `autoload`. Для него нужно явно указать константу и файл: `autoload :User, "models/user"`. Он работает и внутри модулей, но сам не выводит соответствие между деревом файлов и пространствами имён. Перезагрузку изменённых файлов для режима разработки тоже нужно организовывать отдельно.

## 🚀 Zeitwerk: как это работает

Zeitwerk — gem, который используется для автозагрузки в Rails начиная с версии 6. Он:
1. Обходит настроенные директории и регистрирует автозагрузку констант.
2. Сопоставляет имена файлов с константами: `user.rb` → `User`, `users/admin.rb` → `Users::Admin` при соответствующей корневой директории.
3. Загружает файл при первом обращении к его константе. При необходимости файлы можно загрузить заранее.

**Пример для самостоятельного Ruby-проекта:**

```ruby
# boot.rb в корне проекта
require "zeitwerk"

loader = Zeitwerk::Loader.new
loader.push_dir(File.expand_path("app/models", __dir__))
loader.push_dir(File.expand_path("lib", __dir__))
loader.setup

user = User.new # загрузится app/models/user.rb
```

Корневые директории здесь задают пространства имён: `app/models/user.rb` должен определять `User`, а `lib/validators/email_validator.rb` — `Validators::EmailValidator`. В Rails создавать такой загрузчик в инициализаторе не нужно: автозагрузчиками управляет сам Rails. Дополнительные директории подключают через его конфигурацию.

## 🔥 Большие боли маленьких проектов

### 1. Конфликты именования

```text
app/
  models/
    user.rb
    user/
      admin.rb
```

Если `app/models` — корневая директория загрузчика, `user/admin.rb` соответствует `User::Admin`, а не `UserAdmin`. Файл `user.rb` при этом должен определять `User` как класс или модуль, в котором может находиться `Admin`.

Если промежуточную директорию не нужно превращать в часть имени константы, её можно свернуть:

```ruby
loader.collapse("app/models/user") # user/admin.rb теперь соответствует Admin
```

Это меняет ожидаемое имя константы, поэтому применять `collapse` стоит только тогда, когда такая структура действительно нужна. В примере с `User::Admin` сворачивать директорию не требуется.

### 🗂️ Файлы без ожидаемой константы

Допустим, в `app/models/` лежит `old_service.rb`, но он не определяет `OldService`. Само сканирование при `setup` не обязательно обнаружит эту ошибку. Она проявится при обращении к `OldService` или при предварительной загрузке файлов через `loader.eager_load`.

Если файл должен участвовать в автозагрузке, исправьте имя файла или объявляемой константы. Если это неуправляемый код, исключите его из загрузчика:

```ruby
loader.ignore("app/models/old_service.rb")
```

Для целой директории можно указать путь к ней. В Rails соответствие файлов и констант удобно проверять командой `bin/rails zeitwerk:check`.

### 🚗 Проблемы с STI (Single Table Inheritance)

```ruby
# app/models/vehicle.rb
class Vehicle < ApplicationRecord
end

# app/models/vehicle/car.rb
class Vehicle::Car < Vehicle
end
```

При корректной настройке автозагрузки обращение к `Vehicle::Car` загрузит нужные файлы. Добавлять `require "vehicle"` в файл подкласса ради этого не нужно.

Сложность STI в другом: пока подкласс не загружен, его может не быть в `Vehicle.descendants`. Это важно, если код рассчитывает получить полный список подклассов, ещё не обращаясь к ним. В таком случае подклассы нужно предварительно загрузить — целенаправленно или вместе со всем приложением. Цена предварительной загрузки — больше работы при запуске и использование памяти.

## 🧪 Тестирование с Zeitwerk

### RSpec + Zeitwerk = ❤️

Для самостоятельного проекта загрузчик можно настроить до загрузки тестируемого кода:

```ruby
# spec/spec_helper.rb
require "zeitwerk"

loader = Zeitwerk::Loader.new
loader.push_dir(File.expand_path("../app/models", __dir__))
loader.setup
```

Тесты, которые обращаются только к отдельным константам, не проверят остальные файлы. Если нужно проверить соответствие файлов ожидаемым константам, вызовите `loader.eager_load` в отдельной проверке. В Rails используйте уже настроенную загрузку приложения, а не создавайте второй загрузчик для тех же директорий.

`require_relative` в тестах сам по себе не запрещён. Но вручную подключать им файлы, которыми управляет Zeitwerk, обычно не стоит: такой тест обходит обычный путь автозагрузки и может скрыть ошибку в именовании.

## ⚡ Производительность: мифы и реальность

**Миф:** «Zeitwerk при каждом обращении к константе заново проверяет все файлы».

**Реальность:** при настройке загрузчик обходит директории и регистрирует автозагрузку; нужный файл загружается при обращении к константе. В режиме разработки Rails может настраивать автозагрузку заново при перезагрузке кода. В окружении с предварительной загрузкой файлы, наоборот, загружаются заранее. Поэтому вывод о скорости без конкретного проекта и режима работы делать нельзя.

Если отдельную директорию самостоятельного загрузчика не нужно загружать заранее, у Zeitwerk есть `do_not_eager_load`:

```ruby
loader.do_not_eager_load("app/models/concerns")
```

Она не отключает автозагрузку: константы из директории по-прежнему смогут загружаться при обращении. Применять настройку стоит, только если код не зависит от того, что эти константы уже загружены. В Rails сначала нужно учитывать настройки его собственных загрузчиков и предварительной загрузки.

## 🎤 Что сказать на собеседовании

> — Как вы организуете автозагрузку кода в Rails?

— Используем Zeitwerk, который работает в Rails начиная с версии 6. Он сопоставляет пути с константами и загружает код по требованию. Для особых структур директорий настраиваем загрузчик, а соответствие файлов и констант проверяем отдельно. `require` оставляем там, где подключаем код вне его управления.

## 🧾 Вывод

Zeitwerk избавляет от ручного подключения многих файлов приложения, но требует согласованной структуры директорий и имён констант. Он не отменяет `require` для внешнего или исключённого из автозагрузки кода и не решает задачи архитектуры проекта.

Если проект пока использует `require_relative`, переходить на автозагрузку лучше после проверки структуры файлов, пространств имён и мест, где код рассчитывает на предварительную загрузку констант.
