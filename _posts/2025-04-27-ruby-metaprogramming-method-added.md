Ruby позволяет узнать, когда в классе появляется новый метод или у объекта удаляется синглтон-метод. Для этого есть специальные методы-хуки. Разберёмся, на какие изменения они реагируют и как пользоваться ими без вреда для кодовой базы.

---
Вы только что добавили `def calculate_tax` в класс `Invoice`…  
А диагностический код уже об этом знает. Магия? Нет, просто `method_added`.

---

## 🧠 Теория: что за специальные методы?

Это **хуки**, которые Ruby вызывает при определённых изменениях методов класса или объекта. С их помощью можно:

* Логировать добавление и удаление методов
* Проверять имена новых методов
* Сбрасывать кеши, зависящие от реализации метода
* Замечать отмену определения метода

Хуки сообщают об уже произошедшем изменении. Это полезные сигналы для метапрограммирования, но не механизм предварительного запрета операции.

---

## 🔍 Разбираем методы

### 1. `method_added(name)`
Срабатывает при добавлении **метода экземпляра** в класс или модуль. Имя приходит как символ. При определении метода самого объекта, в том числе метода класса, используется `singleton_method_added`.

```ruby
class MethodWatcher
  def self.method_added(method_name)
    puts "Добавлен метод: #{method_name}"
    super
  end

  def log(message)
    puts message
  end
end
# => Добавлен метод: log
```

**Где использовать:**  
- Диагностика методов, создаваемых динамически  
- Проверка соглашений об именовании

---

### 2. `singleton_method_added(name)`
Отслеживает добавление **синглтон-метода конкретного объекта**. Для метода класса этим объектом будет сам класс.

```ruby
obj = Object.new

def obj.singleton_method_added(name)
  puts "Синглтон-метод #{name} добавлен!"
  super
end

def obj.hello
  "world"
end
# => Синглтон-метод hello добавлен!
```

**Где использовать:**  
- Отладка методов, создаваемых динамически  
- Наблюдение за методами, определяемыми непосредственно на объекте

Методы модуля, подключённого через `obj.extend(Admin)`, доступны объекту через цепочку предков, но не определяются на нём заново. Не стоит рассчитывать, что каждый из них вызовет `singleton_method_added`.

---

### 3. `method_removed(name)` и `method_undefined(name)`
Разница тонкая, но важная:

| Хук | Когда срабатывает |
|------|-------------------|
| `method_removed` | После `remove_method` |
| `method_undefined` | После `undef_method` |

`remove_method` удаляет определение из текущего класса: после этого может стать доступен одноимённый метод предка. `undef_method` блокирует поиск метода с этим именем в предках, пока метод не будет определён заново.

```ruby
class CleanupWatcher
  def self.method_undefined(name)
    puts "Метод #{name} больше не доступен через этот класс"
    super
  end

  def calculate
    42
  end

  undef_method :calculate
end
# => Метод calculate больше не доступен через этот класс
```

**Где использовать:**  
- Диагностика изменений методов в плагинах  
- Обнаружение удаления критичных методов

Исключение из такого хука само по себе не откатит `remove_method` или `undef_method`. Если операцию нужно запретить, проверяйте её до изменения класса.

---

### 4. `singleton_method_removed` и `singleton_method_undefined`
Аналогичные уведомления для синглтон-методов. Они тоже вызываются **после** изменения:

```ruby
admin = Object.new

def admin.grant_access
  true
end

def admin.singleton_method_removed(name)
  warn "Удалён синглтон-метод: #{name}"
  super
end

admin.singleton_class.remove_method(:grant_access)
# Предупреждение: Удалён синглтон-метод: grant_access
```

Такой хук помогает заметить удаление, но не предотвращает его.

## 🧪 Практика: кейсы из жизни

### Кейс 1: Валидация API-методов

```ruby
class ApiEndpoint
  def self.method_added(name)
    unless name.to_s.match?(/\A[a-z_][a-z_0-9]*\z/)
      raise "Используй имена из строчных латинских букв, цифр и подчёркиваний!"
    end
    super
  end

  def getUsers
  end
end
# => Ошибка: Используй имена из строчных латинских букв, цифр и подчёркиваний!
```

Это пример **строгого правила для конкретного API**, а не полного определения `snake_case`: он также отклонит допустимые в Ruby имена методов с `?`, `!` и `=`. `method_added` получает символ, поэтому перед проверкой он преобразуется в строку. Ошибка прервёт выполнение определения класса, но метод к этому моменту уже добавлен; хук не заменяет предварительную проверку кода.

### 🧹 Кейс 2: Сброс кеша при изменении метода

```ruby
class Product
  @cache = {}

  def self.method_added(name)
    @cache.clear if name.to_s.start_with?("calculate_")
    super
  end
end
```

Так можно сбрасывать **кеш, зависящий от реализации** методов `calculate_*`, когда один из них определяют или переопределяют. Хук не реагирует на изменение данных товара и сам по себе не реализует кеширование.

## 💣 Антипаттерны

1. **Рекурсия**: если при каждом вызове `method_added` без проверки вызывать `define_method`, добавление нового метода снова вызовет хук — и так по кругу.

2. **Тяжёлая логика**: операции ввода-вывода внутри хука замедляют каждое подходящее определение метода. Например, не стоит без необходимости обращаться к базе данных прямо здесь:
   ```ruby
   def self.method_added(name)
     SaveMethodToDatabase.call(name)
     super
   end
   ```

3. **Игнорирование `super`**: если хук переопределяет поведение предка, отсутствие `super` прервёт цепочку его обработчиков. Это важно, когда библиотека или базовый класс тоже использует такие хуки.

---

## 🎤 Что сказать на собеседовании

> — Как можно отследить добавление метода в рантайме?

— В Ruby `method_added` сообщает о добавлении метода экземпляра в класс или модуль, а `singleton_method_added` — о добавлении синглтон-метода объекта. Оба хука вызываются после добавления метода, поэтому проверка внутри них не отменяет изменение автоматически.

---

## 🧾 Вывод

Специальные методы — это **стетоскоп для ваших классов**. Они помогают при отладке метапрограммирования, документировании динамических методов и обнаружении нежелательных изменений. Но для защиты критичных методов одного хука недостаточно: он сообщает о событии, а не останавливает его. Не превращайте такие обработчики в свалку бизнес-логики.
