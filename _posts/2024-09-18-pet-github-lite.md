Git отслеживает изменения в коде, а GitHub хранит удалённый репозиторий. Если вы ведёте небольшой pet-проект в одиночку, можно начать с одной ветки `main`: добавлять изменения, делать коммиты и отправлять их без сложного workflow.

---

Вы только что написали код. Дальше — короткий цикл:

1. Проверить изменения и добавить нужные файлы.
2. Сделать коммит с понятным сообщением.
3. Отправить его в `main`.
4. Вернуться к работе.

Для этого не обязательно сразу осваивать `rebase`, `squash` и `cherry-pick`. Но перед отправкой стоит убедиться, что в коммит не попали лишние файлы или секреты.

---

## 🧠 Теория: почему main?

**Главный принцип для такого проекта:** готовые изменения отправляем в `main`. Незаконченная работа может оставаться локально; если нужно сохранить её в удалённом репозитории отдельно от готового кода, пригодится ветка.

Одна ветка упрощает историю и избавляет от слияния собственных рабочих веток. Но она не защищает от конфликтов, если в удалённом `main` появились новые коммиты, и не делает любой коммит готовым к деплою.

**Когда это работает?**

- Вы один ведёте небольшой pet-проект.
- Вы отправляете небольшие, понятные изменения.
- Вам не нужно отделять незавершённый код от версии, которая развёртывается из `main`.

Если над репозиторием работают другие люди или деплой идёт прямо из `main`, договоритесь о порядке изменений и проверках до отправки. Работать только в одной ветке в этих условиях уже не всегда удобно.

## 🔧 Практика: базовые команды

### 1. Добавляем изменения

```bash
git status
git add .  # или конкретные файлы: git add app/models/user.rb
git diff --cached
```

`git add .` добавляет изменения в текущем каталоге и его подкаталогах, в том числе новые файлы, которые не исключены через `.gitignore`. `git status` и `git diff --cached` помогут увидеть, что попадёт в коммит.

### 2. Коммитим

```bash
git commit -m "Добавил валидацию email в User"
```

Пишите конкретно, что изменили; если причина неочевидна, укажите и её.

❌ Плохо: `fix bug`  
✅ Лучше: `Исправил N+1 запрос в списке пользователей`

### 3. Пушим

```bash
git push origin main
```

Команда отправляет локальную ветку `main` в `origin`. Если удалённая ветка успела измениться, обычный push будет отклонён: сначала нужно получить и согласовать изменения.

### 4. А как же `git pull origin main`?

Если вы один работаете на одном компьютере и никто больше не меняет удалённый `main`, перед каждым push обновлять локальную ветку обычно незачем. Если вы работаете с разных компьютеров, принимаете изменения через GitHub или делите репозиторий с кем-то ещё, перед продолжением работы обновляйте локальную ветку:

```bash
git pull origin main
```

`pull` получает удалённые изменения и интегрирует их в текущую ветку; способ интеграции зависит от настроек Git. Если возник конфликт, его придётся разрешить до отправки своих коммитов.

## 💡 Антипаттерны

### 1. «Я потом разберусь с конфликтами»

Допустим, удалённый `main` изменился, и ваш push отклонён. Не пытайтесь решить это принудительной отправкой:

```bash
# Так делать не надо:
git push --force
```

Такая команда может заменить историю удалённой ветки и убрать из неё коммиты, которых нет у вас локально. То, что код работает на вашем компьютере, об этом ничего не говорит.

### ✅ Правильный путь

Находясь в локальной ветке `main`, получите удалённые изменения и объедините их со своими:

```bash
git fetch origin
git merge origin/main
# или, если хотите перенести свои локальные коммиты поверх удалённых:
git rebase origin/main
```

Если возникнут конфликты, разрешите их, завершите merge или rebase и только затем повторите `git push origin main`. Rebase меняет идентификаторы перенесённых коммитов, поэтому не применяйте его без согласования к истории, на которую уже опираются другие.

`git push --force-with-lease` проверяет, не изменилась ли удалённая ветка по сравнению с известным вам состоянием, но всё равно переписывает её историю. Для обычной работы с `main` он не нужен.

### 2. Мега-коммиты

```bash
git commit -m "Всё сразу: и фронт, и бэк, и фиксы"
```

Несвязанные изменения в одном коммите сложнее проверять и откатывать по отдельности. Когда возможно, делите работу на небольшие осмысленные коммиты.

### 3. Ветки «на всякий случай»

```bash
git checkout -b experimental-refactoring-2024
```

Для каждого мелкого изменения отдельная ветка не нужна. Но для долгого эксперимента или работы, которую пока нельзя отправлять в `main`, ветка полезна — это не антипаттерн само по себе.

## 🧪 Обязательно `.gitignore`: меньше мусора в репозитории

`.gitignore` помогает не добавлять случайно локальные файлы, результаты сборки и секреты. Это не гарантия защиты: файл, который уже отслеживается Git, не перестанет отслеживаться после добавления его пути в `.gitignore`. Перед коммитом всё равно проверяйте список файлов.

### 📄 Пример `.gitignore` для pet-проекта:

```gitignore
# Локальные конфигурации и секреты
.env
config/database.yml
config/master.key

# Временные файлы
/tmp
/log
/storage
.byebug_history

# Сборка фронтенда
/node_modules
/public/packs
/public/assets

# Системные файлы
.DS_Store
.idea
.vscode
```

Это пример, а не универсальный список: оставляйте исключения только для файлов, которые не должны храниться в вашем репозитории. Если команде нужна конфигурация, можно хранить её шаблон без секретов.

> 💡 Если используете Docker, проверьте, нужно ли исключить локальные файлы вроде `*.local.yml`, `docker-compose.override.yml` и содержимое `secrets/`.

## ❗ А если уже добавил что-то чувствительное?

### 🧷 Сценарий А: секрет попал в локальный коммит, который ещё не отправлен

1. Уберите файл из индекса, не удаляя локальную копию, и добавьте путь в `.gitignore`:

   ```bash
   git rm --cached config/database.yml
   echo "config/database.yml" >> .gitignore
   git add .gitignore
   ```

2. Удалите секрет из коммита, где он появился. Если это последний коммит, исправьте его через `git commit --amend --no-edit`. Если секрет попал в более ранний коммит, нужно исправить и его в локальной истории **до отправки**.

Новый коммит с удалением файла не убирает секрет из предыдущего коммита. Если секрет мог стать доступен кому-то ещё, отзовите его и выпустите новый.

### ☠️ Сценарий B: уже **сделал push** в репозиторий

Если опубликованное значение — действующий ключ, пароль или токен, **сначала отзовите или замените его**. Удаление файла не отменяет утечку.

Затем уберите файл из отслеживаемых и добавьте в `.gitignore`:

```bash
git rm --cached .env
echo ".env" >> .gitignore
git add .gitignore
git commit -m "Убрал .env из репозитория"
git push origin main
```

Это сохранит локальный `.env`, но удалит файл только из новых состояний репозитория — старые коммиты останутся. При необходимости удалить секрет из опубликованной истории согласуйте переписывание истории со всеми, кто использует репозиторий: оно затронет их клоны и само по себе не гарантирует удаления всех копий. Отзыв секрета остаётся обязательным.

## ✅ Вывод

* Создайте подходящий `.gitignore` до первого коммита и проверяйте, что добавляете в индекс.
* Не храните действующие ключи и пароли в репозитории.
* Если секрет уже опубликован, отзовите его: удаления файла недостаточно.

## 🔥 Экстренные случаи

### Отмена последнего коммита (ещё не запушили):

```bash
git reset --soft HEAD~1
```

Команда отменит последний коммит, но оставит его изменения в индексе. Она не подходит для отмены единственного коммита в репозитории.

### Вернуть удалённый файл:

Если удаление ещё не добавлено в индекс, верните версию файла из последнего коммита:

```bash
git restore --source=HEAD -- app/controllers/users_controller.rb
```

Если удаление уже добавлено в индекс, восстановите и индекс, и рабочий файл:

```bash
git restore --source=HEAD --staged --worktree -- app/controllers/users_controller.rb
```

## 🧾 Вывод

**GitHub — инструмент, а не ритуал.** Для небольшого проекта с одним автором можно начать с `main`: делать понятные коммиты, проверять их содержимое и отправлять обычным push. Когда в удалённой ветке появятся другие изменения или незавершённую работу понадобится отделить от готовой, дополните этот простой процесс pull или рабочей веткой.
