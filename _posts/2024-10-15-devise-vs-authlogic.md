Выбор системы аутентификации для Rails-приложения — выбор между готовым набором функций и более явной настройкой. Devise и Authlogic решают задачу входа пользователей по-разному. Разберём, что потребуется для запуска каждого варианта и где легко ошибиться. Речь именно об аутентификации: права доступа к данным и действиям придётся продумывать отдельно.

---

## 🧠 Теория: два пути аутентификации

### Devise: «Всё включено»

**Плюсы:**
- Генераторы, маршруты и готовые контроллеры для типовых сценариев входа
- Модули для регистрации, восстановления пароля и подтверждения email; для входа через внешних провайдеров можно подключить OmniAuth
- Можно начать с типовой конфигурации и менять её по мере необходимости

**Минусы:**
- Для нетипового сценария нужно разобраться в модулях, хуках и работе Warden
- Готовое поведение легко усложнить чрезмерным переопределением контроллеров
- Часть возможностей может не понадобиться небольшому приложению

### Authlogic: «Лего для взрослых»

**Плюсы:**
- Даёт модель аутентификации и сессий без готового набора контроллеров и форм
- Удобен, когда поток входа нужно собрать под требования приложения

**Минусы:**
- Контроллеры, маршруты и интерфейс придётся писать самостоятельно
- Нужно внимательно настроить модель пользователя и проверить весь поток входа
- Меньше готовых сценариев, чем у Devise

## 🔧 Практика: установка и настройка

### Devise: типовая настройка

```ruby
# Gemfile
gem 'devise'
```

```sh
rails generate devise:install
rails generate devise User
rails db:migrate
```

Генератор модели добавляет `devise_for :users` в маршруты. Доступные действия зависят от модулей, включённых в модели `User`: для типовой конфигурации это, в частности, `/users/sign_in` и, если включён `registerable`, `/users/sign_up`. Восстановление пароля требует модуля `recoverable`. Формы можно сгенерировать и изменить отдельно, если стандартного интерфейса недостаточно.

### Authlogic: собираем поток входа

```ruby
# Gemfile
gem 'authlogic'
```

Для пользователя нужны поля, с которыми работает Authlogic. Один из вариантов начальной миграции:

```sh
rails generate model User login:string crypted_password:string password_salt:string persistence_token:string
rails db:migrate
```

В реальном приложении стоит также предусмотреть уникальный индекс для `login` в миграции: одной проверки на уровне модели недостаточно, чтобы исключить дубликаты при параллельных запросах.

```ruby
# app/models/user.rb
class User < ApplicationRecord
  acts_as_authentic
end

# app/models/user_session.rb
class UserSession < Authlogic::Session::Base
end

# app/controllers/application_controller.rb
class ApplicationController < ActionController::Base
  before_action :activate_authlogic
end

# app/controllers/user_sessions_controller.rb
class UserSessionsController < ApplicationController
  def create
    @user_session = UserSession.new(user_session_params)

    if @user_session.save
      redirect_to root_url
    else
      render :new, status: :unprocessable_entity
    end
  end

  private

  def user_session_params
    params.require(:user_session).permit(:login, :password)
  end
end
```

Это фрагменты настройки, а не готовая форма входа: ещё нужны маршруты, действия для показа формы и выхода, а также сам интерфейс. Поля формы должны соответствовать параметрам `login` и `password`.

## 🛡 Безопасность: где подводные камни?

### Devise: настройка вместо патчей наугад

Devise использует настраиваемые механизмы хранения паролей, но смена алгоритма хеширования — не просто замена названия в конфигурации. Нужно учесть проверку уже сохранённых паролей и переход пользователей на новый формат. Не стоит считать, что подключение `devise-security` решит задачу миграции хешей: этот пакет предназначен для дополнительных правил безопасности, а не для автоматического перевода существующих паролей на другой алгоритм.

### Authlogic: не отключайте проверки без замены

Например, настройка `c.validate_password_field = false` отключает встроенную валидацию поля пароля в модели. Сама по себе она не отключает проверку пароля при входе, но при создании или изменении пользователя может позволить сохранить данные, которые приложение не собиралось принимать, если взамен нет собственной проверки.

```ruby
acts_as_authentic do |c|
  c.validate_password_field = false # Только если проверка реализована отдельно
end
```

Если меняете встроенные валидации, проверьте регистрацию, изменение пароля, восстановление доступа и ошибки ввода. Алгоритм хранения паролей тоже не стоит заменять самописной криптографией.

## 📈 Производительность: PostgreSQL-специфика

### Devise

Модуль `trackable` хранит сведения о входах, включая время и IP-адрес. Если эти данные не нужны, не включайте модуль: обновление записи пользователя при входе — дополнительная работа с базой. Это не означает, что Devise всегда генерирует «тяжёлые SQL-запросы» или что отказ от `trackable` заметно ускорит любое приложение.

```ruby
devise :database_authenticatable,
       :registerable,
       :trackable # Включайте, если нужны данные о входах
```

### Authlogic

Меньшее число готовых функций само по себе не делает запросы быстрее. Поведение зависит от схемы, настроек сессий и кода приложения. `session_store :cache_store` — настройка хранения Rails-сессий, а не способ добавить Authlogic кеширование и не универсальное решение проблем производительности. Сравнивать варианты имеет смысл на сценариях и нагрузке своего приложения.

## 💀 Антипаттерны

### Для Devise

1. **Большое переопределение контроллеров без необходимости**  
   Если в `RegistrationsController` накапливается много прикладной логики, вынесите её в отдельные объекты. Переопределяйте действия Devise там, где действительно нужно изменить поток регистрации, а не только ради вызова сервисного объекта.

2. **Отсутствие защиты от перебора паролей**  
   `lockable` — один из возможных механизмов, но блокировка учётной записи может быть неудобной для пользователей и использована для отказа в доступе. Выберите подходящую защиту от перебора с учётом требований приложения; не считайте `lockable` обязательным для каждого проекта.

### Для Authlogic

1. **Самописное хеширование паролей**  
   Не заменяйте проверенный механизм собственной криптографической реализацией без веской причины и плана миграции существующих паролей.

2. **Смешение сессии и записи пользователя**  
   `UserSession` описывает вход пользователя, а `User` — его учётную запись. Не сохраняйте объект сессии как атрибут `User`; управляйте входом и выходом через модель сессии и контроллер.

## 🎯 Когда что выбирать?

| Критерий | Devise | Authlogic |
|---|---|---|
| Быстрый запуск типового входа | Многое уже предусмотрено | Потребуются свои контроллеры, маршруты и формы |
| Нетиповой сценарий входа | Возможен, но придётся учитывать устройство модулей | Больше кода приложения, зато поток задаёте сами |
| Подтверждение email и восстановление пароля | Есть готовые модули | Реализацию нужно планировать отдельно |
| Вход через внешнего провайдера | Можно интегрировать с OmniAuth | Интеграцию нужно строить в приложении |

**Вывод:** если подходят готовые сценарии, начните с Devise. Если вход существенно отличается от них и команда готова поддерживать собственный код, рассмотрите Authlogic. Нагрузка, архитектура приложения и «полный контроль над безопасностью» сами по себе не делают один из вариантов автоматическим победителем.

# Gemfile

## 🧾 Итог

1. **Не усложняйте:** если подходят типовые сценарии Devise, не пишите их заново без причины.
2. **Проверяйте весь поток входа:** создание пользователя, восстановление доступа, выход, обработку ошибок и защиту от перебора.
3. **Документируйте настройки:** особенно собственные проверки и изменения стандартного поведения Authlogic или Devise.

> Лучшая система аутентификации — та, поведение и ограничения которой команда понимает и может поддерживать.
