Паттерн Command представляет действие отдельным объектом с понятной точкой входа. В Ruby для этого часто используют `.call`. Разберём, когда такой объект помогает отделить логику от вызывающего кода, а когда лишь добавляет лишний класс.

---
Вы наверняка встречали такой код:

```ruby
class SendWelcomeEmail
  def self.call(user)
    new(user).call
  end

  def initialize(user)
    @user = user
  end

  def call
    Mailer.welcome(@user).deliver_later
  end
end
```

Он короткий, лаконичный и… выглядит так, будто его писал кто-то, кто читал про паттерны. Это распространённая в Ruby форма объекта действия. Она близка к Command, но одного метода `.call` недостаточно, чтобы получить все возможности классического паттерна. Давайте разберёмся, зачем нужен такой объект и когда лучше обойтись без него.

---

## 🧠 Теория: что такое Command?

Command (он же «Команда») — поведенческий паттерн из классической «банды четырёх». Он представляет запрос на выполнение действия отдельным объектом: такой объект можно передать другому коду, который решит, когда его выполнить.

В Ruby объект действия часто выглядит как класс с `.call`. Но откладывание выполнения, логирование или отмена не появляются автоматически: для них нужны отдельные механизмы. Например, `deliver_later` в первом примере ставит в очередь отправку письма, а не сам объект `SendWelcomeEmail`.

---

## 🔧 Как выглядит Command в Ruby?

```ruby
class DeactivateUser
  def self.call(user)
    new(user).call
  end

  def initialize(user)
    @user = user
  end

  def call
    @user.update!(active: false)
    Audit.log(@user, "deactivated")
  end
end
```

### Зачем?

* Читаемость: `DeactivateUser.call(user)` называет действие в месте вызова.
* Тестируемость: операцию можно проверять отдельно от контроллера.
* Повторное использование: её можно вызвать из джоба, rake-задачи или другого кода.

При этом две строки в `call` не образуют атомарную операцию. Если `Audit.log` завершится ошибкой после успешного `update!`, пользователь уже будет деактивирован. Если запись аудита должна сохраняться вместе с изменением пользователя, нужно отдельно продумать транзакцию; она поможет, только если обе записи выполняются в одной базе данных.

---

## 📦 Когда применять?

Объект действия полезен, когда:

* У операции есть понятное имя и несколько шагов или зависимостей.
* Логику нужно вынести из контроллера и вызывать из разных мест.
* В месте вызова важно явно назвать операцию: `ApproveInvoice.call(invoice)`.

Сам по себе `.call` не делает систему декларативнее. Выбор между объектом действия и методом модели зависит от того, где проще поддерживать логику и её зависимости.

---

## 💣 Когда это антипаттерн

Не всё, что можно положить в `.call`, стоит туда класть.

### 🚫 Если:

* Класс лишь пересылает вызов `UserMailer.welcome(user).deliver_later` и не добавляет полезной границы для операции, он может быть лишним.
* В проекте уже есть интеракторы или сервисы с той же ролью, новый слой может дублировать существующий.
* `CreateUserCommand`, `DeleteUserCommand` и `UpdateUserCommand` появляются только ради единообразия, хотя каждый содержит по одной строке, — количество классов растёт без заметной пользы.

---

## 🧪 Тестируемость

Операцию можно проверять отдельно от контроллера. В примере важно проверить и изменение пользователя, и вызов аудита:

```ruby
describe DeactivateUser do
  it "deactivates user and logs the action" do
    user = create(:user, active: true)

    expect(Audit).to receive(:log).with(user, "deactivated")
    expect { described_class.call(user) }
      .to change { user.reload.active }.from(true).to(false)
  end
end
```

Такой тест проверяет вызов `Audit.log`, но не сохранение записи аудита. Если важен результат записи или поведение при ошибке, их нужно проверять отдельно. Размещать тест можно в `spec/services/`, если это соответствует структуре проекта.

---

## 🎤 На собеседовании

> — Вы используете Service Objects?
>
> — Да. Для операции с понятной задачей иногда выделяем объект с `.call`. Если нужны очередь или отмена, проектируем их отдельно: сам метод этого не обеспечивает.

---

## 🧾 Вывод

**Объект действия — способ дать имя операции и вынести её из вызывающего кода.** Если `BanUser.call(user)` помогает понять назначение и повторно использовать логику, отдельный класс может быть полезен.

Но не превращайте проект в коллекцию `XxxCommand` ради шаблона: иногда обычный метод будет проще.
