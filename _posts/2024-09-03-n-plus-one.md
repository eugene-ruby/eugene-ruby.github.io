Проблема N+1 возникает, когда Active Record загружает записи одним запросом, а затем обращается к базе за связанной записью для каждой из них. Разберём, как заметить такие запросы и когда использовать `includes`, `preload` и `eager_load`.

---
Всё было хорошо… пока ты не загрузил 100 пользователей с их компаниями — и не получил 101 SQL-запрос. Добро пожаловать в **мир N+1**.

## 💥 Что такое N+1?

```ruby
User.all.each do |user|
  puts user.company.name
end
```

Если ассоциация `company` не загружена заранее, Active Record сначала запросит пользователей, а затем будет загружать компанию при обращении к `user.company`. Для 100 пользователей с разными компаниями это может дать **101 запрос**: один за пользователями и 100 за компаниями. Пример предполагает, что у каждого пользователя есть компания; иначе вызов `name` для `nil` завершится ошибкой.

---

## 🕵️ Как найти N+1?

1. В логах Rails ищи повторяющиеся запросы к одной таблице, которые выполняются при обходе коллекции, например `SELECT ... FROM companies WHERE companies.id = ...`.
2. Гем [`bullet`](https://github.com/flyerhzm/bullet) может обнаруживать N+1 и сообщать, какую ассоциацию стоит загрузить заранее. Способ вывода предупреждения зависит от его настройки.

---

## 🛡 Как бороться?

### ✅ includes

```ruby
User.includes(:company).each do |user|
  puts user.company.name
end
```

В этом примере `includes` обычно выполнит **два запроса**: один за пользователями и один за их компаниями. При других условиях запроса Active Record может выбрать загрузку через `JOIN`.

### ✅ preload / eager_load

| Метод | Как работает |
| --- | --- |
| `includes` | Выбирает способ загрузки в зависимости от запроса |
| `preload` | Загружает ассоциацию отдельным запросом; для примера выше получится два запроса |
| `eager_load` | Загружает записи и ассоциацию через `LEFT OUTER JOIN` |

`eager_load` не обязательно быстрее: соединение, особенно для `has_many`, может заметно увеличить число строк в результате SQL-запроса. Выбирай способ загрузки с учётом ассоциаций и условий выборки.

---

## 🧠 Полезные советы

* Если условие по таблице ассоциации задано строкой SQL вместе с `includes`, укажи `references`, чтобы Active Record подключил эту таблицу через `JOIN`:

  ```ruby
  User.includes(:company)
      .where("companies.name = ?", "Acme")
      .references(:company)
  ```

  Для условия в виде хеша, например `where(companies: { name: "Acme" })`, явно вызывать `references` не требуется. В обоих случаях условие влияет и на то, какие пользователи попадут в результат.
* **Проверяй вложенные ассоциации**: если для каждого комментария нужен его автор, загрузи обе связи заранее:

  ```ruby
  Post.includes(comments: :author)
  ```
* **Разделяй задачи инструментов**: `bullet` помогает заметить N+1, а `EXPLAIN` показывает план отдельного SQL-запроса. Сам по себе `EXPLAIN` не обнаружит серию одинаковых запросов в цикле.

---

## 🚀 Когда пригодится .pluck

Если от пользователей нужны только отдельные поля, можно не создавать объекты моделей:

```ruby
User.where(active: true).pluck(:id, :email)
```

Здесь `pluck` получит значения одним запросом. Но он **не заменяет предварительную загрузку ассоциаций** в примере с `user.company`: это решение для другой задачи.
