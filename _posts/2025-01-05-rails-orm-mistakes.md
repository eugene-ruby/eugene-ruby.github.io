ActiveRecord в Ruby on Rails упрощает работу с базой данных, но не избавляет от необходимости следить за запросами. Разберём 10 ошибок, из-за которых код работает не так, как ожидается, или делает лишнюю работу с PostgreSQL.

---

## 1. 🔁 N+1 при `each`

```ruby
User.all.each { |u| puts u.company.name }
# Запрос пользователей, затем отдельный запрос компании для каждого пользователя
```

Если `company` не загружена заранее, обращение к ней внутри цикла создаёт N+1 запросов. Когда компании нужны для всех пользователей, загрузи связь заранее:

```ruby
User.includes(:company).each { |u| puts u.company.name }
```

---

## 2. 💥 `pluck(:id)` в подзапросах

```ruby
Post.where(user_id: User.active.pluck(:id))
```

`pluck` сначала получает все ID активных пользователей в массив Ruby, а уже потом они используются в запросе постов. При большом числе пользователей это расходует память и передаёт в следующий запрос длинный список значений. Если ID нужны только для фильтрации, оставь выборку подзапросом:

```ruby
Post.where(user_id: User.active.select(:id))
```

`.ids` тоже возвращает ID в Ruby и не заменяет подзапрос в этом случае.

---

## 3. 🧊 Потеря полей при `select(...)`

```ruby
User.select(:id).first.name # ActiveModel::MissingAttributeError
```

`select` создаёт объект модели только с выбранными полями. Обращение к невыбранному `name` вызовет ошибку, а не вернёт `nil`. Выбирай все поля, которые понадобятся объекту; если нужны только значения без объектов моделей, используй `pluck`.

---

## 4. 🤷‍♂️ Забыл `.save` или `.update`

```ruby
user.name = "John"
# Значение изменилось в объекте, но ещё не сохранено в базе
```

Присваивание само по себе не записывает изменение в базу. Вызови `user.save` или `user.update(name: "John")` и учитывай, что сохранение может не пройти валидации. Если при неудаче нужно исключение, используй `save!` или `update!`.

---

## 5. 🧠 Делаешь запросы в цикле

```ruby
users.each { |u| u.posts.count }
```

`count` запрашивает количество постов в базе для каждого пользователя. Если сами посты тоже нужны, загрузи их заранее и считай уже загруженную коллекцию:

```ruby
users = User.includes(:posts)
users.each { |u| puts u.posts.size }
```

Если нужны только количества, загрузка всех постов может обойтись дороже. В таком случае лучше получить количества сгруппированным запросом или рассмотреть `counter_cache`, если условия его применения подходят модели.

---

## 6. ⚠️ Используешь `default_scope`

`default_scope` применяется к запросам модели не только там, где фильтр очевиден из кода. Из-за этого легко забыть об условии при чтении или изменении данных.

Если условие требуется не всегда, предпочти явный scope:

```ruby
scope :active, -> { where(active: true) }
```

Сам по себе `default_scope` не ошибка: он уместен, когда поведение по умолчанию действительно нужно для модели. Важно учитывать его действие во всех запросах.

---

## 7. 🧱 Забыл `.readonly` в сложных `joins`

Обычный `joins` не требует `.readonly`: полученные записи можно изменять как обычно. Но если запрос возвращает частичные или вычисленные данные и его результат предназначен только для чтения, случайная попытка сохранить такой объект может быть ошибкой. Обозначь намерение явно:

```ruby
User.joins(:posts)
    .select("users.id, COUNT(posts.id) AS posts_count")
    .group("users.id")
    .readonly
```

`.readonly` запрещает сохранять полученные объекты; он не исправляет сам запрос и не нужен для каждого соединения таблиц.

---

## 8. 📉 Используешь `.count` на коллекции

```ruby
users = User.all
users.count        # Запрос COUNT(*) к базе
users.to_a.count   # Загрузка записей и подсчёт в Ruby
```

Для количества строк без загрузки объектов используй `count`. Но если записи уже загружены и нужно посчитать их в памяти, `count` у relation сделает отдельный запрос. В таком случае подойдёт `size`: у загруженной relation он считает элементы коллекции, а у незагруженной получает количество из базы.

---

## 9. 🌀 Путаешь `joins` и `includes`

```ruby
User.joins(:posts).where(posts: { title: "foo" })
User.includes(:posts).where(posts: { title: "foo" })
```

`joins` соединяет таблицы для фильтрации, но не загружает `posts` в ассоциацию пользователя. `includes` предназначен для предварительной загрузки; при таком условии по связанной таблице Rails может построить запрос с `JOIN`. Поэтому правило «для фильтрации всегда `joins`, для загрузки всегда `includes`» слишком грубое.

Если нужно только отфильтровать пользователей, используй `joins`. Если после фильтрации понадобятся их посты, добавь предварительную загрузку и проверь получившиеся запросы. Учитывай также, что `joins` может вернуть одного пользователя несколько раз, если условию соответствуют несколько его постов; когда нужны уникальные пользователи, добавь `distinct`.

---

## 10. 🚀 Не замеряешь запросы

По виду Ruby-кода не всегда ясно, сколько SQL-запросов он выполнит и какой из них окажется дорогим. Смотри SQL в логах Rails; для поиска N+1 и анализа времени запросов могут помочь `bullet` и `rack-mini-profiler`. План конкретного запроса к PostgreSQL исследуй с помощью `EXPLAIN ANALYZE`. Помни, что `ANALYZE` выполняет запрос, поэтому не запускай его бездумно для операций, меняющих данные.

## 📌 Резюме

| Ситуация | Что проверить или сделать |
| --- | --- |
| N+1 при обращении к связи | Заранее загрузить связь через `includes` или `preload` |
| ID нужны только для фильтрации | Использовать `select(:id)` как подзапрос вместо `pluck(:id)` |
| Частичная выборка полей | Выбрать нужные поля или получить значения через `pluck` |
| Изменение осталось только в объекте | Вызвать `save` или `update` и проверить результат |
| Подсчёт связанных записей в цикле | Выбрать между предварительной загрузкой, групповым запросом и `counter_cache` |
| Неочевидный `default_scope` | Использовать явный scope, если условие нужно не всегда |
| Вычисленные данные только для чтения | При необходимости пометить relation как `.readonly` |
| Подсчёт уже загруженных записей | Использовать `size`, чтобы не делать отдельный `COUNT(*)` |
| Фильтрация по связанной таблице | Различать `joins` и предварительную загрузку; при необходимости использовать `distinct` |
| Непонятно, где тратится время | Изучить SQL и план конкретного запроса |
