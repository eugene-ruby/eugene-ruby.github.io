Когда нужно быстро проверить выражение или разобраться, что происходит с объектом, удобно открыть интерактивную консоль. В Ruby для этого есть встроенный IRB и устанавливаемый отдельно Pry. Посмотрим, чем они отличаются и когда выбирать каждый.

---

## 🧠 Теория: зачем вообще нужны REPL?

REPL (Read-Eval-Print Loop) — интерактивная среда, где можно:
- **Быстро проверить идею** без создания файлов
- **Исследовать объекты** на лету
- **Разбирать поведение кода** в доступном контексте

|               | IRB                     | Pry                    |
|---------------|-------------------------|------------------------|
| **Доступность** | Поставляется с Ruby   | Требует установки      |
| **Базовый сценарий** | Проверка выражений и работа с объектами | Исследование кода и объектов с помощью команд Pry |
| **Расширение** | Возможности зависят от окружения и установленных инструментов | Дополнительные команды доступны через плагины |

## 🔧 Практика: базовое использование

### IRB: как старый друг

```text
$ irb
irb(main):001> 2 + 2
=> 4
irb(main):002> class Foo; def bar; "baz"; end; end
=> :bar
```

### Pry: как швейцарский нож

Установите гем и запустите консоль:

```text
$ gem install pry
$ pry
[1] pry(main)> 2 + 2
=> 4
[2] pry(main)> ls Hash
```

Команда `ls` помогает исследовать методы и другие элементы объекта. Внешний вид вывода зависит от настроек терминала.

## 💡 Ключевые отличия

### 1. Интроспекция объектов

В Pry для исследования доступны отдельные команды:

```text
pry(main)> cd ActiveRecord::Base
pry(ActiveRecord::Base):1> ls -M

pry(main)> show-method User#save
```

Примеры с `ActiveRecord::Base` и `User` предполагают загруженное Rails-приложение с моделью `User`. В IRB тоже можно исследовать методы средствами Ruby, например вызвать `User.instance_methods.sort` или найти определение метода через `User.instance_method(:save).source_location`. Команды Pry удобны тем, что собирают такие действия в интерактивном интерфейсе.

### 2. Отладка и стек вызовов

Точку остановки можно поставить прямо в методе:

```ruby
def problematic_method
  binding.pry # Остановка здесь, если Pry загружен
  some_buggy_code
end
```

В открывшейся консоли `whereami` покажет код рядом с точкой остановки. Но команды `up` и `down` для перехода между кадрами стека не входят в базовый Pry: нужен отладочный плагин, например `pry-byebug` в совместимом окружении, либо другой подходящий инструмент. Один лишь вызов `binding.pry` не делает этот пример пошаговым отладчиком.

IRB не ограничен вызовом `caller`: для остановки и пошаговой отладки Ruby-кода можно использовать отдельный отладчик. Выбор здесь скорее между привычными инструментами и командами, чем между «отладкой» и её отсутствием.

## ⚠️ Боль и антипаттерны

### Когда Pry может навредить

1. **В production.** Забытый `binding.pry` может остановить обработку запроса или фоновой задачи в ожидании ввода. Удаляйте интерактивные точки останова перед развёртыванием; удалённый доступ к консоли требует отдельной оценки безопасности.
2. **При работе с потоками.** Если несколько потоков попадут в интерактивные точки останова, управлять ими через общий ввод-вывод будет трудно. Для воспроизведения такой проблемы может быть удобнее изолированный запуск или сбор диагностических данных.
3. **Когда важен быстрый запуск.** Дополнительные плагины, например `pry-rails` и `pry-byebug`, добавляют зависимости и могут влиять на время запуска. Если нужно только проверить выражение, достаточно IRB.

### Когда хочется исследовать объект подробнее

В IRB можно искать методы обычным Ruby-кодом:

```text
irb(main):001> user = User.first
irb(main):002> user.methods.grep(/name/)
```

В Pry можно перейти в контекст объекта и посмотреть доступные методы:

```text
pry(main)> user = User.first
pry(main)> cd user
pry(#<User>):1> ls
```

Здесь `User` также предполагает консоль приложения, где модель уже загружена.

## 🛠 Интеграция с Rails

### Pry + Rails = ❤️

Для проекта, где используются эти гемы, добавьте в `Gemfile`:

```ruby
group :development do
  gem 'pry-rails'
  gem 'pry-byebug'
end
```

После установки зависимостей `pry-rails` подключает Pry к `rails console`. `pry-byebug` добавляет команды пошаговой отладки, в том числе `next` и `step`, в поддерживаемом им окружении. Эти команды нужны в точке остановки, а не просто для работы с выражениями в консоли.

### IRB: минималистичный подход

Если дополнительные команды Pry не нужны, используйте обычную консоль Rails без `pry-rails`. Она уже загружает окружение приложения: добавлять в `.irbrc` строки `require 'rails/console/app'` и `require 'rails/console/helpers'` ради его загрузки не требуется.

## 🎤 Что сказать на собеседовании

> — Почему вы используете Pry вместо стандартного IRB?

— Мне удобны команды Pry для исследования объектов и исходного кода. Для пошаговой отладки подключаю подходящий отладочный инструмент. Если нужно быстро проверить выражение, хватает IRB.

## 🧪 Сценарий: сбой фоновой задачи

**Ситуация:** фоновая задача падает с ошибкой вызова метода у `nil`. Хочется узнать, какая переменная получила неожиданное значение.

Вместо добавления `binding.pry` в production сначала проверьте место ошибки по стеку вызовов и доступным логам. Если данных не хватает, добавьте адресную диагностику или воспроизведите задачу в безопасном окружении, где можно поставить интерактивную точку останова.

`pry-remote` даёт удалённый доступ к процессу, но не превращает интерактивную отладку в безопасный способ диагностики production: процесс может остановиться в ожидании подключения, а сама консоль открывает доступ к состоянию приложения. Используйте такой инструмент только при наличии подходящих ограничений доступа и понимании последствий для работающей задачи.

## 🧾 Вывод

Выбирайте инструмент под задачу:
- **IRB** — для быстрых проверок и работы без дополнительного гема.
- **Pry** — когда удобны его команды исследования кода и объектов. Для пошаговой отладки понадобятся дополнительные инструменты.
