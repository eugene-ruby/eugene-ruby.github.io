YJIT может ускорить выполнение Ruby-кода, но не любую работу приложения. Прежде чем включать его в продакшене, стоит понять, где сервис проводит время и как проверить эффект на своей нагрузке.

---

## 🔎 Боль: Ruby и производительность — вечная история

Когда Rails-сервис начинает тормозить, первым делом полезно выяснить причину: это могут быть запросы к базе данных, обработка данных в Ruby или ожидание внешнего сервиса.

```ruby
# Участок, в котором стоит отдельно оценить время SQL и Ruby-кода
User.joins(:posts).where("posts.created_at > ?", 1.week.ago).each do |user|
  user.calculate_loyalty_score
end
```

Здесь `joins` может вернуть одного пользователя несколько раз, если условию соответствуют несколько его постов. Если расчёт должен выполняться один раз на пользователя, запрос нужно скорректировать, например добавить `distinct`. YJIT не исправит такую ошибку и не ускорит выполнение SQL на стороне базы.

В Ruby и раньше существовал JIT-компилятор MJIT. Начиная с Ruby 3.1 доступен также **YJIT**. Вопрос не в том, какой компилятор обещает больше, а в том, помогает ли YJIT конкретному приложению.

---

## 🚀 Что такое YJIT?

**YJIT (Yet Another Just-In-Time Compiler)** — JIT-компилятор для CRuby, доступный начиная с Ruby 3.1. Во время работы программы он компилирует часто выполняемые участки Ruby-кода в машинный код.

Это может уменьшить затраты на выполнение Ruby-кода, в том числе внутри Rails. Но результат зависит от нагрузки и версии Ruby, а сгенерированный код требует дополнительной памяти. Время, которое приложение ждёт ответа от базы или внешнего API, YJIT напрямую не сокращает.

---

## 🔧 Как включить YJIT?

Для Ruby с поддержкой YJIT его можно включить при запуске процесса:

```bash
RUBYOPT="--yjit" bundle exec rails server
```

Проверить состояние в запущенном процессе можно так:

```ruby
RubyVM::YJIT.enabled? # => true, если YJIT включён
```

Проверку выполняйте в том процессе, производительность которого оцениваете: включение YJIT в одной консоли не включает его в уже работающем сервере. Возможность включить YJIT из кода через `RubyVM::YJIT.enable` зависит от версии Ruby; запуск с `--yjit` удобнее для сравнения отдельных процессов.

## 🏎️ Сценарии для проверки: YJIT и без него

Следующие примеры показывают, какие участки стоит измерять. Числа ускорения заранее предсказать нельзя.

### 1. Циклы с бизнес-логикой

```ruby
def calculate_stats
  users = User.active.limit(10_000)
  users.each { |user| user.update!(score: complex_calculation(user)) }
end
```

Здесь вычисления чередуются с чтением и записью в базу. Если основное время уходит на `complex_calculation`, YJIT может помочь. Если на `update!` и запросы — эффект может быть небольшим. Перед замером стоит также проверить, не выполняет ли цикл лишние запросы.

### 2. Рендеринг JSON API

```ruby
get "/api/v1/posts" do
  Post.limit(100).to_json
end
```

Время ответа складывается из запроса к базе, создания объектов и сериализации. Сравнивайте не только RPS, но и время ответа при одинаковой нагрузке: прирост зависит от того, какая часть работы приходится на Ruby.

### 3. ActiveRecord-запросы

```ruby
User.includes(:posts).where(posts: { likes_count: 100.. }).find_each(&:profile)
```

YJIT не ускоряет SQL, выполняемый базой. Кроме того, `includes(:posts)` не загружает `profile`: если это ассоциация, обращение к ней для каждого пользователя может создать N+1 запросов. Такой участок сначала стоит проверить по логам запросов и профилю выполнения.

---

## 📉 Когда YJIT может не окупиться

1. **Короткоживущие процессы** — например, некоторые CLI-скрипты и Rake-задачи. Процесс может завершиться раньше, чем окупятся затраты на компиляцию. Это нужно проверять на конкретной задаче.
2. **Приложения, ограниченные ожиданием SQL или внешних сервисов.** Если время уходит на N+1 запросы, сначала устраняйте их.
3. **Системы с ограниченной памятью.** YJIT использует память для скомпилированного кода; допустимые затраты зависят от нагрузки и числа процессов.
4. **Среды без поддержки YJIT.** Нужна подходящая версия и сборка Ruby. Возможности и производительность YJIT также различаются между версиями Ruby 3.x.

## 🧪 Антипаттерны использования

### 1. Включение «на всякий случай»

```ruby
# config/initializers/yjit.rb
RubyVM::YJIT.enable if Rails.env.production?
```

Этот вариант зависит от версии Ruby и не даёт понять, помогает ли YJIT. Если метод доступен, такое включение происходит уже после начала запуска приложения. Для сравнения режимов удобнее включать YJIT при старте процесса и наблюдать за метриками.

### 2. Ожидание чуда

Если приложение тормозит из-за запросов, ожидания сети или неудачного алгоритма, один только JIT проблему не решит. Сначала найдите участок, на котором теряется время.

### 3. Перенос результатов между версиями Ruby

Изменения YJIT между версиями Ruby могут влиять на результат. Не считайте замер на одной версии доказательством того, что на другой эффект будет таким же.

## 🛠️ Практика: как проверить эффект

1. **Сравните одинаковую нагрузку в отдельных процессах.** Не переключайте YJIT внутри одного замера: прогрев, порядок запусков и состояние приложения исказят сравнение. Для локального фрагмента Ruby можно использовать `benchmark-ips`, подставив вместо `some_code` воспроизводимую работу:

```ruby
require 'benchmark/ips'

Benchmark.ips do |x|
  x.report('workload') { some_code }
end
```

```bash
bundle exec ruby bench.rb
RUBYOPT="--yjit" bundle exec ruby bench.rb
```

`benchmark-ips` измеряет выполнение фрагмента, но не заменяет проверку всего сервиса. Для поиска узкого места под нагрузкой пригодится профилирование, например с `rbspy`.

2. **Наблюдайте за приложением.** Сравнивайте время ответа, пропускную способность, загрузку CPU и потребление памяти при сопоставимой нагрузке. Трейсинг в Datadog или New Relic поможет понять, сколько времени уходит на Ruby, SQL и внешние вызовы.

3. **При необходимости сравните группы серверов.** Можно запустить часть процессов с YJIT, а часть — без него. Условия должны быть сопоставимы: версия Ruby, код, ресурсы и входящий трафик.

---

## 🧮 Вывод: стоит ли?

**YJIT стоит проверить**, если приложение работает на Ruby с его поддержкой, заметная часть времени уходит на Ruby-код и есть запас памяти. Решение принимайте по замерам на своей нагрузке.

Если сервис в основном ждёт SQL или внешние API, начните с этих ограничений. Для разового скрипта отдельно оцените, успевает ли выгода перекрыть затраты на компиляцию.

P.S. Перед настройкой YJIT, возможно, стоит сначала починить N+1 запросы. 😉
