Вы написали Rails-проект: локально он запускается, а на другой машине сборка гема завершается `Gem::Ext::BuildError` или приложение не может подключиться к PostgreSQL. Docker помогает воспроизвести окружение, но не устраняет ошибки настройки автоматически. Разберём минимальный пример для локальной разработки.

---

## 🐋 Почему Docker — это не «для продвинутых»

### Миф: «Я же только учусь, зачем мне Docker?»

Контейнеры позволяют описать версию Ruby, зависимости приложения и PostgreSQL в файлах проекта. Другому разработчику не придётся устанавливать эти компоненты вручную, хотя Docker и другие требования самого проекта ему всё равно понадобятся.

Пример проблемы без настроенного окружения:

```bash
rails db:migrate
# => PG::ConnectionBad: FATAL: database "myapp_development" does not exist
```

Контейнер сам по себе не исправит эту ошибку: базу нужно создать или подготовить. Ниже настроим её создание и выполним команду Rails.

## 🛠️ Практика: Docker для Rails + Postgres

Пример рассчитан на Rails-проект с `Gemfile.lock` и настройкой PostgreSQL. Для другого набора зависимостей Dockerfile может потребовать дополнительных пакетов.

### Шаг 1. Установка Docker

- Установите Docker по [официальной инструкции](https://docs.docker.com/get-docker/) для вашей ОС.
- Проверьте команды: `docker --version` и `docker compose version`.

### Шаг 2. Создаём `Dockerfile`

В корне проекта:

```dockerfile
# Используем образ Ruby
FROM ruby:3.2

# Устанавливаем зависимости
RUN apt-get update && apt-get install -y \
    build-essential \
    libpq-dev \
    nodejs

WORKDIR /app

# Сначала устанавливаем гемы, чтобы использовать кеш сборки
COPY Gemfile Gemfile.lock ./
RUN bundle install

COPY . .

EXPOSE 3000
CMD ["rails", "server", "-b", "0.0.0.0"]
```

Версия Ruby в образе должна подходить вашему проекту. Если сборка JavaScript требует других инструментов, одного `nodejs` может быть недостаточно — сверяйтесь с зависимостями приложения.

🤓 Загляни в полезную статью: [Как не собирать жирный Docker образ](/posts/slow-fat-docker-image.html)

### Шаг 3. Пишем `docker-compose.yml`

```yaml
services:
  db:
    image: postgres:15
    volumes:
      - postgres_data:/var/lib/postgresql/data
    environment:
      POSTGRES_PASSWORD: password
      POSTGRES_DB: myapp_development
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d myapp_development"]
      interval: 5s
      timeout: 5s
      retries: 5

  web:
    build: .
    command: bash -c "rm -f tmp/pids/server.pid && rails server -b 0.0.0.0"
    volumes:
      - .:/app
    ports:
      - "3000:3000"
    depends_on:
      db:
        condition: service_healthy
    environment:
      DATABASE_URL: postgres://postgres:password@db:5432/myapp_development

volumes:
  postgres_data:
```

`db` — имя сервиса, по которому приложение найдёт PostgreSQL внутри сети Compose. `POSTGRES_DB` создаёт базу при первой инициализации пустого тома; если том уже существует, изменение этой переменной не создаст в нём новую базу.

Настройка Rails тоже должна использовать это подключение. Если в проекте уже есть `config/database.yml`, согласуйте его с примером ниже из раздела о типичных ошибках.

### Шаг 4. Запускаем!

```bash
docker compose up -d --build db
docker compose run --rm web bin/rails db:prepare
docker compose up -d web
```

`db:prepare` подготавливает базу приложения и применяет миграции. После этого проект должен быть доступен на `localhost:3000`, если приложение успешно запустилось и порт свободен. Проверить его вывод можно командой `docker compose logs web`.

## 💡 Лайфхаки для новичков

### 1. Как работать с базами данных

**Проблема:** «Где мои данные? Они исчезают при перезапуске?»  
**Решение:** именованный том `postgres_data` сохраняет файлы PostgreSQL при пересоздании контейнера. Но удаление тома удалит и данные — например, при запуске `docker compose down -v`.

### 2. Как дебажить

```bash
# Открыть оболочку в запущенном контейнере приложения:
docker compose exec web bash

# Посмотреть логи PostgreSQL:
docker compose logs db
```

### 3. Как не пересобирать образ при каждом изменении кода

Код примонтирован в `web` через `volumes`, поэтому изменения файлов видны в контейнере без пересборки образа. Если изменились `Gemfile` или системные зависимости в `Dockerfile`, образ нужно пересобрать.

## 🔥 Типичные ошибки

| Ошибка | Что проверить |
|---|---|
| Приложение не подключается к базе | Имя хоста `db`, имя базы в `DATABASE_URL`, состояние контейнера и логи `db`. `depends_on` с проверкой готовности ожидает PostgreSQL при запуске, но не заменяет диагностику ошибок подключения. |
| Сборка останавливается на `Gemfile.lock` | Совпадают ли версия Ruby и платформа гемов с образом. Не удаляйте lock-файл наугад: при необходимости обновите его для целевой платформы. |
| Порт уже занят | Измените левую часть записи `3000:3000` в `ports`, например на `3001:3000`, и открывайте соответствующий порт на хосте. |

Пример секции для среды разработки в `config/database.yml`, использующей адрес из Compose:

```yaml
default: &default
  adapter: postgresql
  encoding: unicode
  pool: 5

development:
  <<: *default
  url: <%= ENV.fetch("DATABASE_URL") %>
```

Если запускаете Rails также вне Docker, предусмотрите для этого отдельную настройку подключения: имя `db` доступно контейнерам Compose, но не обязательно доступно вашей хостовой системе.

## 🚀 **Деплой на VPS**:

Показанный `docker-compose.yml` — конфигурация для разработки, а не готовый сценарий деплоя. В нём пароль указан прямо в файле, код примонтирован с хоста, а Rails запускается как сервер разработки. Не переносите эту конфигурацию на публичный VPS без отдельной настройки окружения, секретов, доступа к базе и запуска приложения для продакшена.
