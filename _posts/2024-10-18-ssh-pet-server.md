SSH-ключи позволяют входить на сервер без ввода пароля учётной записи при каждом подключении. Для этого нужно создать пару ключей на своём компьютере и добавить публичный ключ на сервер. Приватный ключ остаётся у тебя; его стоит защитить парольной фразой.

---

## 🔐 Почему SSH-ключи, а не пароли?

Представь: ты подключаешься к серверу с Rails-приложением. Можно каждый раз вводить пароль учётной записи или настроить вход по ключу. Во втором случае сервер проверяет, что у тебя есть приватный ключ, соответствующий публичному ключу в списке разрешённых.

Пара состоит из двух частей:
- **Приватный ключ** хранится на твоём компьютере. Его нельзя передавать другим или публиковать.
- **Публичный ключ** добавляется на сервер. Сам по себе он не даёт доступа к учётной записи.

Вход по ключу не отменяет необходимость защищать компьютер и приватный ключ: если злоумышленник получит доступ к ключу, он может попытаться использовать его для входа.

---

## 🛠 Генерация ключа: RSA или ed25519?

Открой терминал и введи:

```bash
ssh-keygen -t ed25519 -C "your_email@example.com"
```

`ed25519` — удобный выбор, если его поддерживают SSH-клиент и сервер: ключи компактны. Подсказка `ssh-keygen` предложит путь для сохранения и парольную фразу. Если по выбранному пути уже есть ключ, не перезаписывай его случайно.

**Если сервер не поддерживает ed25519**, проверь, какой тип ключа он принимает. Один из вариантов для совместимых конфигураций — RSA:

```bash
ssh-keygen -t rsa -b 4096 -C "backup_key@example.com"
```

Сам по себе RSA не означает небезопасное подключение: важны параметры ключа и поддержка алгоритмов на обеих сторонах.

---

## 📂 Где лежат ключи?

Если при генерации принять путь по умолчанию для ed25519:
- **Приватный ключ**: `~/.ssh/id_ed25519` — никому не показывать.
- **Публичный ключ**: `~/.ssh/id_ed25519.pub` — его можно добавлять на серверы, где нужен доступ.

Пример публичного ключа (строка сокращена, копировать её для настройки нельзя):

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIJu7X... your_email@example.com
```

## 🚪 Добавляем ключ на сервер

Нужен доступ к нужной учётной записи на сервере — например, по паролю или через консоль провайдера. Публичный ключ добавляется в `~/.ssh/authorized_keys` **на сервере**, у пользователя, под которым ты собираешься входить.

### Вариант 1: Вручную

1. Посмотри содержимое публичного ключа на своём компьютере:
   ```bash
   cat ~/.ssh/id_ed25519.pub
   ```
2. Подключись к серверу доступным способом и выполни под нужным пользователем:
   ```bash
   mkdir -p ~/.ssh
   chmod 700 ~/.ssh
   cat >> ~/.ssh/authorized_keys
   ```
   Вставь **полную строку** публичного ключа, нажми Enter, затем `Ctrl+D`. После этого установи права:
   ```bash
   chmod 600 ~/.ssh/authorized_keys
   ```

Не вставляй в `authorized_keys` содержимое приватного ключа.

### Вариант 2: через ssh-copy-id

Если на твоём компьютере есть `ssh-copy-id`, он добавит публичный ключ после успешного входа на сервер:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server_ip
```

Этот способ тоже требует уже доступного способа аутентификации, например пароля учётной записи.

---

## 🔌 Подключаемся по ключу

Теперь попробуй:

```bash
ssh user@server_ip
```

Если ключ сохранён не по стандартному пути или SSH не выбирает нужный ключ, укажи приватный ключ явно:

```bash
ssh -i ~/.ssh/id_ed25519 user@server_ip
```

Если сервер по-прежнему запрашивает пароль учётной записи, проверь пользователя, содержимое `authorized_keys` и права на `~/.ssh` и файл ключей. Для диагностики подключения можно использовать `ssh -v user@server_ip`. Запрос *парольной фразы ключа* — другое дело: она защищает приватный ключ на твоём компьютере.

## 🧩 Интеграция с Ruby-проектами

### 1. Capistrano

Если для подключения к серверу нужен конкретный ключ, укажи его в `deploy.rb`:

```ruby
set :ssh_options, keys: %w(~/.ssh/id_ed25519)
```

Проброс SSH-агента (`forward_agent`) для самого входа на сервер не нужен. Включай его отдельно, только если серверу во время деплоя требуется доступ к ресурсам через твой агент и ты доверяешь этому серверу.

### 2. Git over SSH

Для приватного репозитория, к которому твоему ключу предоставлен доступ:

```bash
git clone git@github.com:user/repo.git
```

Ключ для входа на твой сервер не начинает автоматически работать с GitHub: его публичную часть нужно отдельно добавить в настройках доступа к репозиторию или учётной записи.

## 💥 Антипаттерны

| Ошибка | Последствия |
|--------|-------------|
| `chmod 777 ~/.ssh` | Другие пользователи машины получат доступ к каталогу; SSH также может отказаться использовать небезопасно настроенные файлы. |
| Использовать один ключ для всех доступов | При компрометации приватного ключа придётся отзывать его во всех местах, где он разрешён. |
| Хранить приватный ключ в репозитории | Ключ попадёт к тем, у кого есть доступ к репозиторию, и может остаться в истории Git даже после удаления файла. |

## 🛡️ Безопасность: что делать с ключами?

- **Задай парольную фразу** при генерации. Не передавай её через параметр `-N` в команде: так она может остаться в истории оболочки или оказаться видна другим процессам. Для отдельного ключа проекта:
  ```bash
  ssh-keygen -t ed25519 -C "email" -f ~/.ssh/project_deploy
  ```
- **Используй SSH-агент**, чтобы не вводить парольную фразу при каждом подключении:
  ```bash
  eval "$(ssh-agent -s)"
  ssh-add ~/.ssh/id_ed25519
  ```
  Если создал ключ `project_deploy`, передай `ssh-add` путь к нему вместо `id_ed25519`. Агент хранит разблокированный ключ для текущего сеанса, поэтому не оставляй доступный сеанс без присмотра.

---

## 🧾 Вывод

Создай пару ключей, добавь публичный ключ в `authorized_keys` нужного пользователя и проверь вход. Приватный ключ оставь на своём компьютере, защити парольной фразой и не добавляй в репозиторий.
