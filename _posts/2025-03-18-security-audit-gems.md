Безопасность Ruby-приложения — это не только HTTPS и пароли. Уязвимость может оказаться в коде Rails или в установленной зависимости. Разберём инструменты, которые помогают находить такие проблемы, и настроим проверки в CI.

---

## 🔍 Почему стандартных практик недостаточно?

Вы уверены, что:
- Для версий гемов из `Gemfile.lock` нет опубликованных предупреждений об уязвимостях?
- В шаблонах нет небезопасного вывода пользовательских данных?
- В новом контроллере параметры не передаются модели без проверки?

На глаз это определить трудно. Автоматические проверки не заменяют ревью, но помогают не пропустить известные проблемы.

---

## 🛡️ Brakeman: статический анализатор для Rails

### Что делает?
Сканирует Rails-код и ищет потенциально опасные конструкции, например:
- SQL-инъекции (`User.where("name = '#{params[:name]}'")`),
- XSS (`<%= raw @comment.text %>`),
- передачу непроверенных параметров модели (`@user.update(params[:user])`).

Список категорий предупреждений есть в [документации Brakeman](https://brakemanpro.com/security_warnings). Предупреждение указывает на место, которое нужно проверить: само по себе оно ещё не доказывает, что уязвимость можно эксплуатировать.

### Установка:
```bash
gem install brakeman
brakeman -o report.html
```

### Пример предупреждения:

Если параметр запроса напрямую подставлен в SQL, Brakeman может указать на строку с запросом и присвоить предупреждению уровень уверенности. Например, конструкция `User.where("login LIKE '%#{params[:q]}%'")` опасна тем, что пользовательский ввод становится частью SQL. Здесь нужны параметры запроса, а для поиска по `LIKE` — ещё и корректная обработка специальных символов шаблона.

### Интеграция в CI:
```yaml
- name: Brakeman
  run: brakeman -z --no-pager
```

С `-z` команда завершится с ошибкой при найденных предупреждениях. Такой шаг имеет смысл после установки Ruby и зависимостей проекта.

**Плюсы:**
- Не требует запуска приложения.
- Проверяет типичные для Rails источники уязвимостей.

**Ограничения:**
- Возможны ложные срабатывания; каждое предупреждение нужно разбирать в контексте кода.
- Не ищет проблемы в JavaScript и не гарантирует отсутствия уязвимостей в приложении.

## 📦 Bundler Audit: проверка зависимостей

### Зачем?
Уязвимой может оказаться версия гема, зафиксированная в `Gemfile.lock`. При этом устаревшая версия не обязательно уязвима: для вывода о риске нужно сверить её с опубликованным предупреждением и условиями его применимости.

### Использование:
```bash
gem install bundler-audit
bundle-audit check --update
```

Команда обновляет базу предупреждений и проверяет зависимости из `Gemfile.lock`. Если найдена известная уязвимость, изучите затронутые версии и доступное исправление, затем обновите зависимость и проверьте приложение. В CI нужна сеть для обновления базы.

### Автоматизация:
Добавьте в `Rakefile`:
```ruby
task :security do
  sh "bundle-audit check --update"
end
```

Запускайте задачу в CI или по расписанию. Рассчитывать на запуск проверки после каждого `bundle install` через `post_install`-хук не стоит: такой хук не является стандартным механизмом Bundler для проекта.

## 🔎 Другие инструменты

### 1. `ruby_audit`
Проверяет установленную версию Ruby на известные уязвимости:
```bash
gem install ruby_audit
ruby-audit check
```

Эта проверка дополняет аудит гемов: `Gemfile.lock` не описывает все риски, связанные с самой версией Ruby.

### 2. 🔄 `bundle outdated`
Показывает доступные обновления гемов, а не только версии с известными уязвимостями:
```bash
bundle outdated --strict
```

`bundle outdated` — команда Bundler, отдельный гем `bundler-outdated` для неё не нужен. Вывод команды не заменяет проверку предупреждений о безопасности.

### 3. `rails_best_practices`
Ищет некоторые спорные конструкции в Rails-коде:
```bash
gem install rails_best_practices
rails_best_practices .
```

Например, предупреждение о `default_scope` помогает заметить неочевидное поведение запросов, но само по себе не означает уязвимость:
```text
Don't use default_scope (app/models/user.rb:5)
```

## 💀 Антипаттерны безопасности

### 1. «У нас маленький проект — зачем аудит?»
Размер проекта не защищает от автоматического поиска уязвимых приложений. Регулярная проверка полезна и для небольшого сервиса.

### 2. «Обновим гемы, когда будет время»
При появлении предупреждения проверьте, используется ли затронутая версия и какой путь исправления рекомендован. Например, запись о [CVE-2019-5421](https://nvd.nist.gov/vuln/detail/CVE-2019-5421) сама по себе не говорит, что уязвимо любое Rails-приложение: важны версия и условия применения. Откладывать обновление без оценки риска — плохая идея.

### 3. «Brakeman ругается — отключим его в CI»
Сначала разберите предупреждение. Если это ложное срабатывание, зафиксируйте решение для конкретного случая, например через файл игнорирования Brakeman, и оставьте пояснение для команды. Отключение целой проверки скроет и будущие предупреждения этого типа.

## 🛠️ Практика: настраиваем пайплайн

1. **Локально**: перед отправкой изменений запускайте `brakeman -z --no-pager` и `bundle-audit check --update`. Проверку можно добавить в локальные хуки, но CI всё равно должен запускать её независимо от настроек разработчика.

2. **CI**: отдельное задание для проверок:

```yaml
# .github/workflows/security.yml
name: Security
on: [push, pull_request]
jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: ruby/setup-ruby@v1
        with:
          bundler-cache: true
      - run: gem install brakeman bundler-audit
      - run: brakeman -z --no-pager
      - run: bundle-audit check --update
```

Здесь предполагается, что в репозитории есть `Gemfile.lock`: он нужен для проверки зависимостей. Если проверки требуют особых системных пакетов или переменных окружения, добавьте их в задание отдельно.

3. **Мониторинг**: запускайте аудит зависимостей по расписанию, чтобы получать предупреждения и между изменениями кода. Уведомления, например в Slack, настраиваются отдельно.

## 🎯 Вывод

- **Brakeman** помогает находить потенциально опасные конструкции в Rails-коде.
- **Bundler Audit** сверяет версии зависимостей с известными предупреждениями об уязвимостях.
- **Автоматизация** делает проверки регулярными, но не отменяет разбор предупреждений и обновление приложения.
