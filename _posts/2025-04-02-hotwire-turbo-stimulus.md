Hotwire, Turbo и Stimulus помогают строить интерактивные Rails-интерфейсы, в которых сервер по-прежнему рендерит HTML. Разберём, за что отвечает каждый инструмент, как их подключить и где такой подход может усложнить приложение.

---
Вы только что закончили рефакторинг монолитного `application.js`, удалили 3000 строк jQuery-кода…  
А теперь клиент просит «интерактивности как в React».  
Не паникуйте — для части таких задач подойдёт Hotwire.

---

## ⚖️ Почему не React/Vue/Angular?

Если основная работа приложения — показывать серверные страницы и обрабатывать формы, отдельный SPA-фронтенд может добавить работы:

1. **Два слоя приложения**: Rails предоставляет API, а фронтенд отдельно загружает данные и отображает их.
2. **Дополнительная настройка для страниц, доступных поисковикам**: нужно продумать, как отдавать содержимое и метаданные.
3. **Согласование поведения**: навигацию и формы Rails приходится увязывать с клиентским приложением.

Это не недостатки SPA сами по себе: при сложном клиентском состоянии такой подход может быть оправдан. Hotwire предлагает другой вариант — сервер рендерит HTML, а JavaScript отвечает за навигацию, обновление страницы и локальное поведение.

---

## 🚀 Что такое Hotwire?

**Hotwire (HTML Over The Wire)** — набор технологий для интерактивного интерфейса с серверным рендерингом:

- **Turbo**: навигация без полной перезагрузки страницы и обновление отдельных частей DOM.
- **Stimulus**: небольшие JavaScript-контроллеры для поведения элементов.
- **Strada**: мост для интеграции веб-интерфейса с нативными мобильными компонентами.

Основная идея: сервер возвращает HTML, а браузер с помощью Turbo вставляет его в нужное место. Когда требуется поведение на клиенте, его добавляют через Stimulus.

---

## 🌀 Turbo: двигатель Hotwire

### Turbo Drive (бывший Turbolinks)

При переходе по поддерживаемой ссылке Turbo Drive запрашивает следующую HTML-страницу, обрабатывает её `<head>`, заменяет `<body>` и обновляет историю браузера. Это позволяет избежать полной перезагрузки страницы, но не отменяет серверный запрос и рендеринг HTML.

**Плюс**: переходы могут ощущаться плавнее.  
**Ограничение**: скрипты, рассчитанные только на первоначальную загрузку страницы, могут не инициализироваться после перехода. Для такого поведения удобно использовать жизненный цикл Stimulus-контроллеров.

### Turbo Frames

```erb
<!-- Частичное обновление блока -->
<turbo-frame id="messages">
  <%= render @messages %>
</turbo-frame>

<!-- Ссылка обновит только этот фрейм -->
<%= link_to "Обновить", messages_path, data: { turbo_frame: "messages" } %>
```

Чтобы обновление сработало, ответ `messages_path` должен содержать `<turbo-frame id="messages">` с новым содержимым. Фреймы подходят, например, для вкладок и фильтров, когда результат можно вернуть как HTML.

### Turbo Streams

```ruby
# В действии create после сохранения сообщения:
respond_to do |format|
  format.turbo_stream # Использует шаблон create.turbo_stream.erb
end
```

Шаблон `create.turbo_stream.erb`:

```erb
<!-- Добавляет сообщение в элемент с id="messages" -->
<%= turbo_stream.append "messages", @message %>
```

Здесь действие `append` добавит HTML в существующий элемент `messages`. Доступны и другие действия, в том числе `prepend`, `replace` и `remove`. Turbo Stream можно вернуть в ответ на обычный HTTP-запрос; для рассылки обновлений клиентам в реальном времени потребуется отдельное соединение, например через Action Cable.

## 🎛 Stimulus: JavaScript для локального поведения

Когда Turbo недостаточно, подключаем **Stimulus**:

```js
// app/javascript/controllers/search_controller.js
import { Controller } from "@hotwired/stimulus"

export default class extends Controller {
  static targets = ["input", "results"]

  async search() {
    const query = new URLSearchParams({ q: this.inputTarget.value })
    const response = await fetch(`/search?${query}`)
    if (!response.ok) return

    this.resultsTarget.innerHTML = await response.text()
  }
}
```

Подключаем в HTML:

```html
<div data-controller="search">
  <input data-search-target="input" data-action="input->search#search">
  <div data-search-target="results"></div>
</div>
```

Такой пример предполагает, что `/search` возвращает HTML для вставки в страницу. Вставлять через `innerHTML` можно только ответ, которому приложение доверяет: пользовательские данные в нём должны быть безопасно экранированы. Для реального поиска также стоит учитывать частые запросы и ситуацию, когда ответ на старый запрос приходит позже нового.

**Чем это отличается от jQuery-кода без общей структуры?**

- Поведение привязано к контроллеру, действиям и целевым элементам.
- Stimulus вызывает методы жизненного цикла при подключении и отключении контроллера. Собственные обработчики событий и другие ресурсы, созданные вручную, при необходимости нужно освобождать самостоятельно.
- Контроллеры можно использовать с принятой в проекте системой подключения JavaScript.

## 🧩 Антипаттерны

### 1. «Турбо-ад» (Turbo Overuse)

```erb
<!-- Сложность растёт, когда у вложенных фреймов есть ещё и независимые обновления -->
<turbo-frame id="user">
  <turbo-frame id="posts">
    <!-- ... -->
  </turbo-frame>
</turbo-frame>
```

Вложенные фреймы допустимы, но взаимодействие их навигации и обновлений бывает трудно отлаживать. Если для блока требуется много согласованных изменений, проверьте, не проще ли обновлять его целиком.

### 2. «Стимьюлище» (Stimulus as React)

```js
// Состояние страницы начинает расползаться по data-атрибутам
this.element.dataset.page = 2
```

`data`-атрибуты полезны для небольшого состояния и параметров контроллера. Если от общего состояния зависят многие части интерфейса, оцените другой способ управления им — вплоть до отдельного клиентского приложения. Сам по себе JSON API или дополнительная библиотека эту сложность не устраняет.

### 3. Игнорирование прогрессивного улучшения

```html
<!-- Без JavaScript кнопка не отправит форму -->
<button type="button" data-action="click->post#save">Сохранить</button>
```

Если форма должна работать без JavaScript, используйте обычную отправку формы, а клиентское поведение добавляйте поверх неё. Атрибут `data-turbo="false"` сам по себе не ломает такой сценарий: он отключает Turbo для элемента, но не стандартное поведение браузера.

## 🔧 Интеграция с Rails

### 1. Установка

Если Turbo и Stimulus ещё не подключены в проекте, установите соответствующие Rails-гемы и запустите их установщики:

```bash
bundle add turbo-rails stimulus-rails
bin/rails turbo:install
bin/rails stimulus:install
```

Перед установкой проверьте `Gemfile`: в проекте эти зависимости уже могут быть. Установщики настраивают подключение библиотек в соответствии с конфигурацией приложения; шаблоны `turbo_stream.erb` для своих действий вы создаёте сами.

### 2. Работа с формами

Для отправки через Turbo не нужно принудительно задавать форме формат `:turbo_stream`:

```erb
<%= form_with(model: @post) do |form| %>
  <%= form.text_field :title %>
  <%= form.submit "Сохранить" %>
<% end %>
```

После успешного сохранения действие контроллера может ответить Turbo Stream, а для обычного HTML-запроса оставить переход на страницу записи:

```ruby
respond_to do |format|
  format.turbo_stream
  format.html { redirect_to @post }
end
```

Например, шаблон `create.turbo_stream.erb` добавит запись в существующий элемент с `id="posts"`:

```erb
<%= turbo_stream.append "posts", @post %>
```

Ошибки валидации обрабатывайте отдельно: форму нужно показать снова вместе с ошибками, а не возвращать ответ об успешном сохранении.

### 3. Кастомные события

Stimulus-контроллер может реагировать на событие Turbo после отправки формы. Обработчик удобно объявить через `data-action`, чтобы не регистрировать и не удалять слушатель вручную:

```html
<div data-controller="post" data-action="turbo:submit-end->post#onSubmitEnd">
  <!-- форма -->
</div>
```

```js
// Метод контроллера post
onSubmitEnd(event) {
  if (event.detail.success) {
    this.showConfirmation()
  }
}
```

Здесь `showConfirmation()` — метод отображения подтверждения, который нужно реализовать в контроллере.

## 🧪 Тестирование

### Тест запроса с Turbo Stream

В исходном примере используется `post`, поэтому это тест запроса, а не системный тест браузера. Он проверяет ответ действия `create`, которое добавляет запись в `posts`:

```ruby
test "create post with Turbo Stream" do
  post posts_path, params: { post: { title: "New" } }, as: :turbo_stream

  assert_turbo_stream action: "append", target: "posts"
end
```

Для `assert_turbo_stream` нужен тестовый хелпер Turbo. Такой тест проверяет серверный ответ, но не работу Stimulus и обновление DOM в браузере.

### Тесты Stimulus-контроллеров

Контроллер поиска можно проверять в JavaScript-тесте с DOM-окружением: подставить ответ `fetch`, вызвать событие `input` и проверить содержимое `results`. Не забудьте остановить приложение Stimulus после теста, чтобы контроллеры не оставались подключёнными между проверками.

## 🎤 Что сказать на собеседовании

> — Почему вы выбрали Hotwire вместо React?

— В нашем интерфейсе основная работа — страницы и формы, которые уже рендерит Rails. Turbo позволяет обновлять их без отдельного клиентского слоя данных, а Stimulus покрывает локальное поведение. Если требования к состоянию на клиенте изменятся, этот выбор придётся пересмотреть.

---

## 🧾 Вывод

**Hotwire — один из вариантов между обычной постраничной навигацией и полноценным SPA.** Turbo отвечает за переходы и обновления HTML, Stimulus — за локальное поведение. Насколько это упростит проект, зависит от самого интерфейса, а не от универсального соотношения строк кода.

**Когда Hotwire может не подойти:**

- Интерфейсом управляет сложное общее состояние на клиенте, как в графическом редакторе.
- Отдельный фронтенд уже является архитектурным требованием проекта.

Для приложения, где серверный HTML остаётся основой интерфейса, Hotwire стоит рассмотреть до разработки отдельного SPA.
