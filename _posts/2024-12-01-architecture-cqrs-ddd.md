CQRS разделяет операции чтения и записи; Event Sourcing хранит последовательность событий как источник состояния, а DDD помогает описывать предметную область. Разберём, как эти подходы соотносятся в Rails-приложении и какую сложность добавляют.

---
При переходе от монолита к микросервисам недостаточно разнести CRUD-контроллеры по разным приложениям. Нужно понять, где проходят границы ответственности и как сервисы обмениваются изменениями. Здесь могут пригодиться CQRS, Event Sourcing и DDD — но ни один из этих подходов не обязателен для каждого микросервиса.

## 🧠 Зачем это вообще нужно

ActiveRecord удобен для хранения данных, но бизнес-правила не всегда удобно держать в моделях, которые одновременно отвечают за работу с базой. Разделение ответственности становится полезным, когда нужно:

* отдельно развивать **операции изменения и чтения данных** — без обязательного выделения их в разные сервисы;
* **фиксировать и передавать изменения** другим частям системы;
* описать **границы контекстов**: одно и то же слово может означать разные вещи в разных частях бизнеса.

Это разные задачи. CQRS, Event Sourcing и DDD можно сочетать, но внедрение одного не требует внедрять остальные.

---

## 🟪 CQRS: Command Query Responsibility Segregation

CQRS разделяет операции на две стороны:

* **Команды** (Command) запрашивают изменение состояния. Они могут вернуть результат выполнения или идентификатор созданной записи, но не служат способом получить модель для чтения.
* **Запросы** (Query) читают данные и не должны менять состояние.

Упрощённый пример разделения в одном Rails-приложении:

```ruby
class CreateUserCommand
  def call(name:, email:)
    User.create!(name: name, email: email).id
  end
end

class UserQuery
  def self.active
    User.where(active: true)
  end
end
```

Обе стороны здесь используют ActiveRecord и одну базу. Отдельные модели хранения и сервисы для чтения и записи — возможное развитие, а не обязательное условие CQRS.

---

## 🟧 Event Sourcing: не меняем — фиксируем

При Event Sourcing источником состояния служит упорядоченная последовательность событий. Чтобы получить текущее состояние, события применяют по порядку; сохранённое отдельно представление текущего состояния может ускорять чтение, но не заменяет историю событий.

```ruby
UserEvent.create!(user_id: 1, sequence: 1, event_type: 'created', data: { name: 'Alice' })
UserEvent.create!(user_id: 1, sequence: 2, event_type: 'activated', data: {})
```

Здесь предполагается модель `UserEvent` с полями `user_id`, `sequence`, `event_type` и `data`. Для воспроизведения состояния нужны обработчики событий и гарантированный порядок событий одного пользователя. В Rails поле `type` по умолчанию используется для STI, поэтому для вида события в примере выбрано `event_type`.

История событий помогает разбирать изменения и строить новые представления данных. Но она не делает аудит автоматически полным, откат — простым, а интеграцию между сервисами — надёжной. Нужно продумать запись событий при конкурентных командах, изменение их формата со временем и доставку потребителям. Если события лишь дублируют обновления обычной модели, это журнал изменений, а не Event Sourcing.

## 🟥 DDD: Domain Driven Design

Сложную систему полезно описывать в терминах предметной области, а не только таблиц базы данных. DDD предлагает:

* выделять **ограниченные контексты** (bounded contexts) со своими моделями и терминами;
* выражать бизнес-правила в доменной модели, в том числе с помощью **объектов-значений** (value objects), а не раскладывать их по контроллерам;
* при необходимости использовать **доменные события** для обозначения произошедших изменений.

Доменные события не требуют Event Sourcing: их можно публиковать, продолжая хранить текущее состояние в обычных таблицах. Например, командный объект может проверять правило активации и сообщать об успешном изменении:

```ruby
class ActivateUser < ApplicationCommand
  def call(user:)
    return failure('already active') if user.active?

    user.activate!
    publish(UserActivated.new(user_id: user.id))
  end
end
```

Это схема взаимодействия, а не готовая реализация: `failure`, `publish`, `activate!` и `UserActivated` здесь предполагают код приложения. Проверку и изменение состояния нужно защитить от конкурентных вызовов. Если событие публикуется во внешнюю систему, сбой между сохранением пользователя и публикацией может оставить их в разных состояниях; для надёжной доставки нужен отдельный механизм, например transactional outbox.

---

## 💡 В Rails это возможно

Можно сохранить миграции, ActiveRecord и rake-задачи, постепенно отделяя бизнес-правила от доступа к данным и команды от запросов. Начать стоит с границ домена и конкретной проблемы: CQRS помогает, когда чтение и запись требуют разных моделей; Event Sourcing оправдан, когда важна сама история изменений как источник состояния. За это придётся платить дополнительным кодом и правилами согласования данных — особенно между микросервисами.
