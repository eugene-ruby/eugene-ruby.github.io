Helm помогает собирать манифесты Kubernetes в чарты, задавать параметры для разных окружений и управлять установками приложения как релизами. Разберём базовую структуру чарта, работу с `values.yaml` и команды для проверки и деплоя.

Вы только что написали `kubectl apply -f deployment.yaml` в третий раз за час, потому что забыли изменить число реплик или версию образа.  
Похоже, пора познакомиться с Helm.

---

## 🧠 Теория: что такое Helm?

Helm — **пакетный менеджер для Kubernetes**, который:
- Объединяет шаблоны манифестов и настройки в **чарты**.
- Подставляет параметры из **values.yaml** и файлов переопределений.
- Хранит историю установок и обновлений **релиза** — экземпляра чарта в кластере.

Helm готовит манифесты и отправляет их в Kubernetes; работу приложения в кластере обеспечивает сам Kubernetes.

---

## 🔧 Первый чарт: от `helm create` до деплоя

Создаём скелет чарта:

```bash
helm create my-rails-app
```

Среди созданных файлов и каталогов будут:

```
my-rails-app/
├── charts/          # Зависимости
├── Chart.yaml       # Метаданные чарта и список зависимостей
├── templates/       # Шаблоны манифестов
│   ├── deployment.yaml
│   ├── service.yaml
│   └── ...
└── values.yaml      # Значения по умолчанию
```

---

## 💡 Как работает values.yaml?

В `values.yaml` задают значения по умолчанию, которые можно переопределить при установке или обновлении релиза. Например:

```yaml
# values.yaml
replicaCount: 3
image:
  repository: myregistry/rails-app
  tag: v1.2.3
  pullPolicy: IfNotPresent
service:
  type: ClusterIP
  port: 3000
```

А в шаблоне `templates/deployment.yaml` обращаются к ним через `.Values`. Фрагмент спецификации Deployment может выглядеть так:

{% raw %}
```yaml
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - name: rails-app
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
```
{% endraw %}

Это именно фрагмент: для рабочего Deployment нужны и другие поля, в том числе `selector` и метки шаблона Pod. В чарте, созданном через `helm create`, шаблон уже содержит необходимую обвязку.

## 🚀 Проверка шаблонов и деплой

1. **Проверка рендеринга без установки релиза**:
   ```bash
   helm install --dry-run --debug my-release ./my-rails-app
   ```
   Команда покажет сгенерированные манифесты, но не установит приложение.

2. **Установка или обновление релиза**:
   ```bash
   helm upgrade --install my-release ./my-rails-app \
     --set image.tag=v1.2.4 \
     --set replicaCount=5
   ```
   `--install` создаст релиз, если его ещё нет. Для реального деплоя одной команды недостаточно: чарты и доступность приложения тоже нужно проверять.

3. **Через CI/CD** (например, GitLab, если чарт лежит в `./my-rails-app`, а у задания есть доступ к кластеру):
   ```yaml
   deploy:
     script:
       - >-
         helm upgrade --install "$CI_PROJECT_NAME" ./my-rails-app
         --set-string image.tag="$CI_COMMIT_SHA"
   ```
   Такой тег должен существовать в реестре к моменту деплоя.

## 🧪 Тестирование: от линтеров до интеграции

1. **Проверка чарта линтером**:
   ```bash
   helm lint ./my-rails-app
   ```
   Линтер помогает найти ошибки в чарте, но не заменяет проверку работы приложения в кластере.

2. **Unit-тест шаблона** с отдельным плагином `helm-unittest`. Например, файл `my-rails-app/tests/deployment_test.yaml`:

   ```yaml
   suite: test deployment
   templates:
     - deployment.yaml
   tests:
     - it: should have 3 replicas
       set:
         replicaCount: 3
       asserts:
         - equal:
             path: spec.replicas
             value: 3
   ```

   После установки плагина тесты запускаются командой `helm unittest ./my-rails-app`. Проверка относится к шаблону Deployment; она не подтверждает, что приложение успешно запустится в кластере.

## 🔥 Антипаттерны

| Ошибка | Последствия | Что делать |
|---|---|---|
| Все настройки окружений в одном `values.yaml` | Сложнее понять, какие значения попадут в релиз | Оставить общие значения в `values.yaml`, различия вынести в файлы вроде `values-prod.yaml` и передавать через `-f` |
| Подвижный тег образа, например `latest` | При повторном деплое результат может зависеть от того, на какой образ указывает тег и что закешировано на узлах | Использовать конкретную версию или digest образа |
| Неиспользуемые или плохо контролируемые зависимости | Сложнее обновлять чарт | Пересматривать зависимости в `Chart.yaml` и фиксировать их разрешённые версии в `Chart.lock` |

---

## 🎤 Что сказать на собеседовании

> — Как вы управляете конфигами для разных окружений?

— Мы используем несколько слоёв значений: `values.yaml` как базу, `values-prod.yaml` для продакшна через `-f`, а `--set` — для отдельных параметров при запуске команды. Для более сложного управления несколькими релизами можно использовать `helmfile`.

## 🧾 Вывод

Helm помогает хранить шаблоны и значения рядом с кодом, проверять итоговые манифесты и обновлять приложение одной командой. При этом предсказуемость деплоя зависит не только от Helm: важно фиксировать образы, проверять чарт и следить за результатом установки в кластере.
