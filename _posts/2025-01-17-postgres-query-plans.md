PostgreSQL — мощная СУБД, но без понимания планов выполнения запросов трудно разобраться, почему запрос Rails-приложения тормозит. Разберём основные способы соединения таблиц (Nested Loop, Hash Join, Merge Join) и доступа к данным (Index Scan, Seq Scan, Bitmap Scan), а также посмотрим, на что обращать внимание в `EXPLAIN ANALYZE`.

---

Когда смотришь на `EXPLAIN ANALYZE`, легко растеряться. Вот краткий словарь, который поможет читать планы PostgreSQL.

## 🔁 Nested Loop

Цикл в цикле: для **каждой строки** из внешнего источника PostgreSQL просматривает или ищет совпадения во внутреннем.

```text
Nested Loop
  -> Seq Scan on orders
  -> Index Scan on users ...
```

Если внешних строк много, внутренний узел выполняется многократно — это видно по `loops` в `EXPLAIN ANALYZE`. Но это **не отдельные SQL-запросы**: вся работа происходит внутри одного запроса. Nested Loop может быть удачным выбором, когда внешних строк мало, а внутренние быстро находятся по индексу.

🛠 Проверь количество строк и повторов, а также индекс для поиска во внутренней таблице. `LIMIT` помогает лишь тогда, когда запрос действительно может остановиться после получения нужного числа строк; сам по себе он не исправляет дорогой поиск.

---

## 🧠 Hash Join

PostgreSQL строит **хеш-таблицу** по одному из источников, затем ищет в ней совпадения для строк другого источника.

```text
Hash Join
  -> Seq Scan on users
  -> Hash
       -> Seq Scan on orders
```

📌 Может быть выгоден для больших наборов строк. Если хеш-таблица не помещается в доступную для операции память, обработка может потребовать записи на диск. Поэтому `work_mem` имеет значение, но увеличивать его без оценки нагрузки не стоит.

---

## 📚 Merge Join

Источники подаются **в порядке ключей соединения**, и PostgreSQL сопоставляет их строки, продвигаясь по обоим наборам.

```text
Merge Join
  -> Index Scan using users_pkey on users
  -> Index Scan using index_orders_on_user_id on orders
```

⚡ Может быть выгоден, если нужный порядок уже обеспечивает индекс, как в условном примере соединения `users.id = orders.user_id`. Если порядок не готов, план может включать `Sort`; сортировка тоже требует времени и памяти.

---

## 🔍 Index Scan

PostgreSQL использует **индекс** для поиска подходящих строк.

```text
Index Scan using users_pkey on users
```

📌 Полезен, когда индекс подходит к условию и нужно получить сравнительно мало строк. Обычный Index Scan может также обращаться к таблице за данными, поэтому при большом числе совпадений он не обязательно быстрее Seq Scan.

---

## 👣 Seq Scan

PostgreSQL **последовательно читает таблицу**.

```text
Seq Scan on users
```

📌 Это не всегда признак проблемы: такой план может быть выгоден для небольшой таблицы или запроса, которому нужна значительная часть её строк. Если же таблица велика, а условие возвращает мало строк, стоит проверить оценки планировщика и подходящий индекс.

---

## 🧮 Bitmap Index Scan

`Bitmap Index Scan` находит подходящие строки по индексу, а `Bitmap Heap Scan` затем читает нужные страницы таблицы.

```text
Bitmap Heap Scan on users
  -> Bitmap Index Scan on index_users_on_email
```

📌 Такой план может быть выгоден, когда совпадений слишком много для обычного Index Scan, но читать всю таблицу не нужно. При очень большой доле подходящих строк планировщик может предпочесть Seq Scan.

---

## 🧰 Что влияет на выбор плана

* Оценка количества строк, которые нужно прочитать и вернуть
* Наличие и состав индексов
* Статистика таблиц и столбцов, обновляемая командой `ANALYZE`
* Настройки памяти, в том числе `work_mem` для операций, которым она нужна
* Условия `JOIN` и `WHERE`

---

## 🧪 Как проверять план через EXPLAIN ANALYZE

`EXPLAIN ANALYZE` **выполняет запрос** и показывает не только оценки планировщика, но и фактическое число строк и повторов (`actual rows`, `loops`). Сравни их с оценкой `rows`, особенно у узлов, после которых резко растёт объём работы. `cost` — оценка затрат планировщика, а не время в миллисекундах.

Для запросов, меняющих данные, помни о побочных эффектах: `EXPLAIN ANALYZE` действительно выполняет `INSERT`, `UPDATE` или `DELETE`. Если нужно изучить план без сохранения изменений, выполняй такой запрос в транзакции с последующим `ROLLBACK`, учитывая, что откат транзакции не устраняет все возможные внешние побочные эффекты.

## 🧭 Запомни

| Термин | Что это | Когда может быть выгоден |
| --- | --- | --- |
| Nested Loop | Повторный поиск или просмотр внутреннего источника | Мало внешних строк, быстрый поиск во внутреннем источнике |
| Hash Join | Поиск совпадений через хеш-таблицу | Много строк, а хеш-таблица обрабатывается без дорогого сброса на диск |
| Merge Join | Сопоставление упорядоченных источников | Нужный порядок уже есть или его недорого получить |
| Seq Scan | Последовательное чтение таблицы | Небольшая таблица или нужна значительная часть строк |
| Index Scan | Поиск строк по индексу | Подходящий индекс и сравнительно мало совпадений |
| Bitmap Index Scan | Поиск строк по индексу для последующего чтения через Bitmap Heap Scan | Совпадений достаточно много для обычного Index Scan, но читать всю таблицу не нужно |
