Выбор между очередью и потоком событий — не выбор между «надёжной» и «быстрой» доставкой. Важнее понять, кто должен получить сообщение, понадобится ли перечитывать историю и что произойдёт при сбое обработчика. Разберём это на примерах из Rails-приложений.

---

Вы добавили вызовы `Sidekiq.perform_async` в десятки мест, а задачи аналитики, писем и обработки заказов конкурируют за одни и те же воркеры. Сначала стоит разделить очереди и настроить конкуренцию в Sidekiq. Если же события должны получать независимые сервисы или их нужно перечитывать, пора разобраться, когда нужны **очереди**, а когда — **потоки событий**.

---

## 🧠 Теория: очереди vs потоки

### RabbitMQ (очереди)
- **Обработка задач**: сообщение из очереди получает один из её потребителей. При ручных подтверждениях неподтверждённое сообщение может быть доставлено повторно — обработчик должен учитывать дубликаты.
- **Маршрутизация**: отправитель публикует сообщение через обменник, а правила привязки определяют, в какие очереди оно попадёт. Отправителю необязательно знать конкретного получателя.
- **Гибкость**: обменники, routing keys и dead-letter очереди помогают организовать доставку и обработку ошибок.

### Kafka (потоки)
- **Лог событий**: сообщения хранятся в топике в пределах настроенного срока или объёма хранения. Потребитель может читать их с нужного смещения, пока они доступны.
- **Независимые подписчики**: разные группы потребителей читают один топик независимо; внутри группы разделы топика распределяются между потребителями.
- **Пропускная способность**: Kafka подходит для потоков событий, но реальная нагрузка зависит от числа разделов, размера сообщений и конфигурации кластера.

## 🔧 Практика в Rails

### RabbitMQ + Bunny
```ruby
# Подключение и объявление очереди
conn = Bunny.new(host: 'rabbitmq')
conn.start
channel = conn.create_channel
channel.prefetch(10)
queue = channel.queue('orders', durable: true)

# Отправка
 def publish_order(queue, order_id)
  queue.publish({ order_id: order_id }.to_json, persistent: true)
end

publish_order(queue, 42)

# Получение: этот фрагмент запускают в отдельном процессе-воркере
queue.subscribe(manual_ack: true, block: true) do |delivery_info, _properties, body|
  OrderProcessor.call(JSON.parse(body))
  channel.ack(delivery_info.delivery_tag)
end
```

Подтверждать сообщение нужно **после** успешной обработки. Если воркер завершится до `ack`, сообщение может прийти снова, в том числе после того, как побочный эффект уже произошёл. Для заказов и платежей поэтому нужны идемпотентная обработка и защита от повторного выполнения. В рабочем воркере также предусмотрите обработку исключений: решение о повторной доставке, ограничение числа попыток и маршрут для неисправимых сообщений. `durable: true` и `persistent: true` полезны для сохранения сообщений при перезапуске брокера, но сами по себе не подтверждают издателю, что публикация принята; если это важно, настройте publisher confirms.

### Kafka + rdkafka-ruby
```ruby
# Producer
producer = Rdkafka::Config.new({ "bootstrap.servers" => "kafka:9092" }).producer

def publish_signup(producer, user_id)
  producer.produce(
    topic: "user_events",
    payload: { event: "signup", user_id: user_id }.to_json
  )
end

publish_signup(producer, 123)
producer.flush(5)

# Consumer: этот фрагмент запускают в отдельном процессе
consumer = Rdkafka::Config.new({
  "bootstrap.servers" => "kafka:9092",
  "group.id" => "analytics",
  "enable.auto.commit" => false
}).consumer
consumer.subscribe("user_events")

begin
  loop do
    message = consumer.poll(1)
    next unless message

    Analytics.track(JSON.parse(message.payload))
    consumer.commit(message: message, asynchronous: false)
  end
ensure
  consumer.close
end
```

`produce` ставит сообщение на отправку; `flush` даёт продюсеру время завершить её перед выходом из процесса. Для обработки с ручным коммитом смещение фиксируется после `Analytics.track`. Сбой между обработкой и коммитом всё равно приведёт к повторной обработке, поэтому идемпотентность важна и здесь. Порядок сообщений Kafka сохраняет в пределах раздела, а не всего топика.

## 💡 Когда что выбрать?

### RabbitMQ если:
- Нужна очередь **фоновых задач** для воркеров, например генерации PDF.
- Нужны маршрутизация и контроль подтверждения обработки; для платежей это не отменяет идемпотентность и согласование с базой данных.
- Задачи обрабатываются долго и для них требуется продуманная политика повторов. Для отложенного выполнения потребуется отдельно выбрать подходящий механизм.

### Kafka если:
- Нужна доступная для повторного чтения **история событий** — с учётом настроенного хранения.
- Одни события читают несколько **независимых групп потребителей**, например аналитика и уведомления.
- Есть большой поток событий, а разделение на топики и разделы соответствует требованиям к порядку обработки и масштабированию.

Если задача — лишь разгрузить веб-запросы в одном Rails-приложении, переход с Sidekiq на другой брокер может быть лишним. Ни RabbitMQ, ни Kafka сами по себе не защитят PostgreSQL от перегрузки: число одновременно работающих обработчиков и объём их запросов всё равно нужно ограничивать.

## 🧪 Тестирование

### 🧪 RabbitMQ: проверяем публикацию
Вынесите публикацию в метод или сервис и подставляйте в тесте очередь. Для `publish_order` из примера выше проверка выглядит так:

```ruby
let(:queue) { instance_double(Bunny::Queue) }

it "публикует заказ в очередь" do
  expect(queue).to receive(:publish)
    .with('{"order_id":42}', persistent: true)

  publish_order(queue, 42)
end
```

### Kafka (мокаем producer)
```ruby
let(:fake_producer) { instance_double(Rdkafka::Producer) }

it "публикует событие регистрации" do
  expect(fake_producer).to receive(:produce).with(
    topic: "user_events",
    payload: '{"event":"signup","user_id":123}'
  )

  publish_signup(fake_producer, 123)
end
```

Эти модульные тесты проверяют формирование сообщения и вызов клиента, но не доставку, подтверждения или работу потребителя. Для проверки взаимодействия с брокером нужны отдельные интеграционные тесты.

## 🔥 Антипаттерны

| Ошибка | Последствия | Как исправить? |
|---|---|---|
| Публиковать крупные JSON-сообщения в Kafka, не учитывая ограничения размера | Публикация может завершиться ошибкой; хранение и передача больших сообщений увеличивают нагрузку | Проверять размер и конфигурацию; если уместно, передавать ссылку на данные во внешнем хранилище |
| Создавать отдельную очередь RabbitMQ на каждую задачу без необходимости | Растёт сложность конфигурации и мониторинга | Разделять очереди там, где действительно нужны разные маршрутизация или параметры обработки |
| Подписывать потребителя Kafka на ненужные топики | Потребитель тратит ресурсы на лишние сообщения | Подписываться на нужные топики; при необходимости пересмотреть схему событий |
| Рассчитывать на однократную обработку после `ack` или коммита смещения | Сбой между побочным эффектом и подтверждением может привести к повторной обработке | Подтверждать после обработки и делать обработчик устойчивым к дубликатам |

## 🎤 Что сказать на архитектурном ревью

> — Почему не используем RabbitMQ для аналитики?

— Если нескольким независимым потребителям нужна возможность читать и перечитывать события за период хранения, Kafka подходит под эту модель. Если требуется просто передать задачу свободному воркеру, очередь RabbitMQ может быть проще. Выбор зависит от требований к истории, маршрутизации и обработке сбоев.

---

## 🧾 Вывод

**RabbitMQ удобен для маршрутизации и обработки задач через очереди, Kafka — для потока событий, который читают независимые группы потребителей.** Ни один брокер не делает бизнес-операцию автоматически «ровно один раз»: подтверждения и коммиты нужно сочетать с идемпотентностью и согласованием изменений в базе данных.

> P.S. Если приложение пока решает задачу фоновым выполнением в Sidekiq, начните с настройки его очередей и воркеров. К RabbitMQ или Kafka стоит переходить под конкретные требования, а не из-за появления слова «микросервисы».
