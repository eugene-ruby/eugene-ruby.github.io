Почему `bundle install` иногда проходит быстро, а иногда упирается в конфликт зависимостей? Разберём, что попадает в Ruby-гем, за что отвечает `gemspec` и как Bundler работает с версиями.

---

## 🧩 Что такое RubyGem?

**Ruby-гем** — пакет с кодом и метаданными. Его можно подключить к проекту, версионировать и распространять через [rubygems.org](https://rubygems.org) или другой источник.

Гемом может быть и небольшая утилита, и фреймворк вроде Rails. При сборке получается архив `.gem`: в него входят файлы, перечисленные в спецификации, и метаданные пакета.

---

## 📦 Анатомия гема

Один из вариантов структуры проекта, созданного через `bundle gem my_gem`:

```
my_gem/
├── lib/
│   ├── my_gem.rb         # Главный файл
│   └── my_gem/           # Дополнительные модули
├── spec/                 # Тесты, если выбран соответствующий шаблон
├── Gemfile               # Зависимости для разработки
├── my_gem.gemspec        # Метаданные гема
└── README.md             # Документация
```

Состав файлов зависит от выбранного шаблона. **Сердце гема** — `.gemspec`: спецификация сообщает RubyGems, как называется пакет, какую версию и какие файлы включать в сборку.

---

## 🔧 Gemspec: инструкция по сборке

Пример `my_gem.gemspec`:

```ruby
Gem::Specification.new do |s|
  s.name        = "my_gem"
  s.version     = "0.1.0"
  s.summary     = "Делает магию"
  s.authors     = ["Вася Пупкин"]
  s.files       = Dir["lib/**/*.rb"] # Эти файлы попадут в гем
  s.license     = "MIT"
end
```

Если гему нужны другие файлы во время работы, их тоже нужно включить в `s.files`. Перед публикацией полезно проверить содержимое собранного `.gem`: наличие файла в репозитории ещё не означает, что он попал в пакет.

### Частые ошибки:

1. **Не включили нужные файлы в `s.files`.** Гем может установиться, но `require` завершится ошибкой, если загружаемого файла нет в пакете. Проверьте список файлов в спецификации и содержимое сборки.
2. **Слишком жёстко ограничили зависимости**, например `s.add_dependency "rails", "7.0.8"`. Приложение, которому нужна другая совместимая версия Rails, не сможет выбрать её. Диапазон версий задавайте по реальной совместимости гема, а не просто по версии, установленной у разработчика.
3. **Не указали `s.required_ruby_version`, хотя код требует определённую версию Ruby.** Тогда установщик не сможет заранее отсеять неподходящий Ruby, и ошибка проявится при загрузке или работе гема. Указывайте ограничение, если знаете минимальную поддерживаемую версию.

## 🧠 Bundler: дирижёр зависимостей

Bundler подбирает набор версий, который удовлетворяет ограничениям из `Gemfile`, спецификаций гемов и, если он есть, `Gemfile.lock`. Зафиксированные в lock-файле версии обычно сохраняются, пока их не потребуется изменить; цель `bundle install` — не просто установить самые свежие релизы.

Если подбор затягивается или заканчивается ошибкой, проверьте ограничения зависимостей и lock-файл. По одному лишь долгому выполнению команды нельзя понять, сколько вариантов перебрал Bundler и в чём причина задержки.

## 💀 Реальные боли

### 1. **Волосатый граф зависимостей**

Простой пример несовместимых требований в `Gemfile`:

```ruby
gem "rails", "~> 7.0"
gem "railties", "< 7.0"
```

Rails 7 требует соответствующую версию `railties`, а второе ограничение её запрещает. Bundler не сможет подобрать набор версий. В настоящем проекте несовместимое требование может прийти и через другой гем — это будет видно в сообщении об ошибке.

**Что делать:** найдите ограничения, которые противоречат друг другу, и измените или обновите зависимость, задающую неподходящий диапазон. `bundle update --conservative devise` может помочь, когда подходящая версия `devise` существует, но в lock-файле зафиксирована старая. Команда не исправит противоречие в самих требованиях к версиям.

### 2. **Гем-призрак**

После удаления гема из `Gemfile` его файлы могут оставаться среди установленных гемов. Запустите `bundle install`, чтобы обновить `Gemfile.lock`: если гем больше не нужен ни одной зависимости, он исчезнет из списка разрешённых версий.

`bundle clean` удаляет установленные гемы, которые не входят в текущий набор Bundler, а не записи из lock-файла. Применяйте его отдельно, когда действительно нужно освободить место; перед `bundle clean --force` убедитесь, что удаляемые гемы не нужны другим проектам в том же окружении.

### 3. **Локальная разработка**

Хотите проверять гем прямо в своём проекте? Укажите путь к нему:

```ruby
# Gemfile
gem "my_gem", path: "../my_gem"
```

Так проект использует локальный исходный код, а не опубликованный пакет. Перед релизом отдельно проверьте сборку: файлов, доступных по локальному пути, может не оказаться внутри `.gem`.

## 🛠️ Антипаттерны

1. **Гем-монстр**
   - Много зависимостей
   - Много кода
   - Проекту нужна лишь небольшая часть возможностей

   → Сначала оцените, можно ли сделать отдельные компоненты необязательными. Разделение на несколько гемов полезно не всегда: оно добавляет работу с версиями и поддержкой пакетов.

2. **Версия зависит от Git при чтении `gemspec`**

   ```ruby
   s.version = `git describe --tags`.strip
   ```

   Bundler и RubyGems читают спецификацию не только перед публикацией. Если в окружении нет Git или нужных тегов, результат изменится либо команда не сработает. Храните версию так, чтобы спецификация читалась без обращения к Git.

3. **Одна политика для `Gemfile.lock` в приложении и библиотеке**
   - Для приложения обычно коммитят lock-файл, чтобы фиксировать выбранные версии зависимостей.
   - Для гема решение зависит от процесса разработки: lock-файл помогает воспроизводить локальное окружение, но проверять совместимость с другими версиями зависимостей всё равно нужно отдельно. Не считайте зафиксированные версии в lock-файле диапазоном поддержки гема.

## 🎓 Продвинутые трюки

### 1. Зависимости для разработки и поддерживаемый Ruby

```ruby
# gemspec
s.add_development_dependency "sqlite3" # Если он нужен для тестов
s.required_ruby_version = ">= 3.1" # Только если гем действительно требует Ruby 3.1+
```

Не добавляйте runtime-зависимость условием вида `if RUBY_VERSION >= "3.1"` внутри `gemspec`: тогда состав метаданных будет зависеть от Ruby, на котором спецификацию прочитали или собрали. Если зависимость нужна гему при работе, задайте её явно и укажите поддерживаемые версии Ruby.

### 2. Скрываем ненужные файлы

```ruby
s.files -= Dir["test/**/*"] # Не включаем тесты в релиз
```

Это имеет смысл, только если файлы тестов уже попали в `s.files` до этой строки. В примере выше `s.files` включает лишь Ruby-файлы из `lib/`, поэтому вычитать из него нечего.

### 3. Собственные источники гемов

```ruby
# Gemfile
source "https://rubygems.org"

source "https://gems.my-company.com" do
  gem "internal_gem"
end
```

Здесь общий источник задан отдельно, а внутренний гем привязан к частному источнику.

## 🧪 Тестируем гем правильно

Если гем поддерживает несколько версий зависимости, `appraisal` помогает описать отдельные наборы для проверок:

```ruby
# Appraisals
appraise "rails-7" do
  gem "rails", "~> 7.0"
end
```

Само описание набора ещё не запускает тесты: для этого нужна настроенная тестовая команда. Проверяйте совместимость с теми версиями, которые заявлены в `gemspec`.

### 🚀 Публикация

`gem-release` может автоматизировать изменение версии и публикацию:

```bash
gem bump -v minor && gem release
```

Это отдельный инструмент, который должен быть установлен и настроен. `gem release` выполняет публикацию, поэтому перед запуском проверьте версию, содержимое пакета и результаты своих тестов.

---

## 🏁 Вывод

1. **Gemspec** задаёт метаданные, зависимости и файлы гема. Проверяйте не только исходный каталог, но и содержимое собранного пакета.
2. **Bundler** выбирает версии с учётом ограничений и `Gemfile.lock`. Если выбор невозможен, ищите противоречащие требования, а не пытайтесь лечить их произвольным обновлением.
3. **Локальная разработка** через `path` удобна, но не заменяет проверки собранного гема и заявленного диапазона зависимостей.
