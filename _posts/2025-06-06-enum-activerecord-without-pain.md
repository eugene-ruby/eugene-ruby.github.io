Enum в Rails кажется простым: объявил статусы — получил удобные методы. Но выбор значений для хранения, ограничения в базе и бизнес-логика переходов требуют отдельных решений. Разберём их на примере статуса статьи.

---

Когда-то я думал, что `enum status: %i[draft published archived]` — это вершина элегантности. Пока не обнаружил в коде `article.update(status: :published)` в 15 разных местах, `scope :visible, -> { where(status: [:published, :archived]) }` и проверки вроде `article.draft? && project.published?`.

Пришло время разобраться, где enum помогает, а где его возможностей уже недостаточно.

## 🧠 Теория: зачем нужны enum?

**Enum (перечисление)** в ActiveRecord связывает имена состояний со значениями в столбце БД. Значения могут быть целыми числами или строками — в зависимости от схемы и объявления. Rails добавляет:

- **Методы-предикаты** (`article.published?`)
- **Методы смены состояния** (`article.published!`)
- **Скоупы** (`Article.published`)
- Проверку значений при присваивании через модель: неизвестное значение по умолчанию вызовет `ArgumentError`

Но проверка в модели не заменяет ограничение в БД: прямой SQL и другие приложения могут записать значение в обход ActiveRecord.

---

## 🔧 Базовый пример (и где подвох)

```ruby
class Article < ApplicationRecord
  enum status: {
    draft: 0,
    published: 1,
    archived: 2
  }
end
```

Здесь нужен целочисленный столбец `status`. **Что получаем из коробки:**

```ruby
article.published!   # Меняет статус и сохраняет запись
article.published?   # Предикат
Article.published    # Скоуп
article.status       # => "published" (в БД хранится 1)
```

Если задать значения массивом (`%i[draft published archived]`), числа зависят от порядка элементов. Перестановка статусов изменит смысл уже сохранённых данных. Явное соответствие имён и значений защищает от такой ошибки.

---

## 💡 Лучшие практики

### 1. Явно указывайте значения

Если нужны читаемые значения в БД, можно использовать строковый столбец `status` и строковое соответствие:

```ruby
enum status: {
  draft: "draft",
  published: "published",
  archived: "archived"
}, _prefix: true
```

Это не замена типа столбца одной строкой кода: для такого объявления `status` должен хранить строки. Если столбец уже целочисленный, оставьте явное числовое соответствие из базового примера или отдельно планируйте миграцию данных.

Строки удобно читать в БД, но они не делают хранение или поиск автоматически быстрее. `_prefix: true` добавляет к методам имя enum: например, `article.status_published?` вместо `article.published?`. Это полезно, если возможны конфликты имён; менять уже используемые методы ради префикса не обязательно.

### 2. 🐘 PostgreSQL enum — когда нужна проверка в БД

Если допустимые статусы должны контролироваться самой PostgreSQL, один из вариантов — её тип enum. Пример для **новой** колонки `status`:

```ruby
# Миграция:
def up
  execute <<-SQL
    CREATE TYPE article_status AS ENUM ('draft', 'published', 'archived');
    ALTER TABLE articles ADD COLUMN status article_status;
  SQL
end

# Модель:
enum status: {
  draft: "draft",
  published: "published",
  archived: "archived"
}, _prefix: true
```

PostgreSQL отклонит значение, которого нет в `article_status`, в том числе при записи в обход модели. Внутри этот тип хранит идентификатор значения фиксированного размера, а при чтении показывает его текстовое имя; называть его обычным целочисленным столбцом нельзя.

У примера есть ограничения: миграция не подойдёт без изменений, если колонка `status` уже существует; для обратимой миграции потребуется также `down`. Добавление и изменение набора значений PostgreSQL enum требует отдельных миграций. Если нужна лишь проверка допустимых значений, стоит сопоставить этот вариант со строковым столбцом и ограничением `CHECK`.

## 🧪 Тестирование enum

Тест, который только повторяет всё объявление, мало говорит о поведении модели:

```ruby
it "has statuses" do
  expect(Article.statuses).to eq({ "draft" => 0, "published" => 1, "archived" => 2 })
end
```

Проверяйте то, на что опирается код. Например, если используются методы с префиксом и строковые значения из примера выше:

```ruby
describe "status" do
  it "maps published to the stored value" do
    expect(described_class.statuses.fetch("published")).to eq("published")
  end

  context "when draft" do
    let(:article) { build(:article, status: :draft) }

    it { expect(article).to be_status_draft }
    it { expect(article).not_to be_status_published }
  end
end
```

Такой тест соответствия полезен, если на конкретное значение завязаны данные или интеграции. Набор проверок должен соответствовать объявлению enum: для числового примера ожидаемое значение и имена методов будут другими.

## 🔥 Антипаттерны

### 1. Enum как замена State Machine

```ruby
class Order < ApplicationRecord
  enum status: {
    created: 0,
    approved: 1,
    rejected: 2,
    paid: 3,
    refunded: 4
  }
end

# Потом в коде:
if order.created? && can_approve?(order)
  order.approved!
  send_notification
elsif order.approved? && can_pay?(order)
  order.paid!
  # ...
end
```

**Проблема:** enum описывает состояния, но сам по себе не ограничивает переходы между ними. Если такие проверки разбросаны по приложению, один из путей записи может их пропустить. Соберите правила переходов в одном месте — например, в методах модели или сервисе. Когда нужны сложные правила и события переходов, можно рассмотреть специализированные инструменты вроде AASM или Statesman. Побочные эффекты, такие как уведомления, тоже требуют продуманной обработки ошибок и момента отправки.

### 2. Магические числа в коде

```ruby
scope :visible, -> { where(status: [1, 2]) } # 1 и 2 — это published и archived?
```

**Исправляем:**

```ruby
scope :visible, -> { where(status: [:published, :archived]) }
```

Теперь назначение фильтра видно без поиска соответствия чисел статусам.

### 3. Слишком много значений

```ruby
enum priority: {
  lowest: 0, low: 1, medium: 2, high: 3,
  urgent: 4, critical: 5, asap: 6, now: 7
}
```

**Проблема не в количестве самом по себе:** здесь трудно понять разницу между `urgent`, `critical`, `asap` и `now`. Если у вариантов нет разных правил обработки, объедините их. Если правила есть — опишите различия и проверьте, действительно ли все значения относятся к одной шкале приоритета.

---

## 🎤 Что сказать на собеседовании

> — Как вы работаете с enum в Rails?

— Явно задаём соответствие значений, чтобы порядок элементов не менял смысл данных. Тип столбца и ограничения БД выбираем под задачу; для сложных переходов выносим правила из разбросанных проверок в одно место.

---

## 🧾 Вывод

**Enum — не только удобные методы для статуса, но и часть решения о хранении данных.** Он делает проверки читаемыми (`article.published?` вместо сравнения с числом), однако ограничения на уровне БД и правила переходов нужно проектировать отдельно.

Коротко: enum отвечает на вопрос «какое состояние сейчас?». Если важен ещё и вопрос «как в него можно перейти?», одного enum недостаточно.
