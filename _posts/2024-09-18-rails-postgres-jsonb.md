Когда у пользователей появляются настройки с разным набором полей, добавлять колонку под каждый параметр неудобно. PostgreSQL JSONB позволяет хранить такие данные в одном столбце и запрашивать их из Rails. Но это не замена реляционной схеме для любых данных.

---
В статье разберём работу с JSONB в ActiveRecord, обновление вложенных значений и индексы для разных запросов.

## 🧠 Теория: JSONB vs JSON vs Hstore

PostgreSQL предлагает несколько типов для данных с гибкой структурой:

| Тип | Индексирование содержимого | Поддержка вложенности |
|-----|----------------------------|-----------------------|
| JSON | Индексы по отдельным выражениям | Да |
| JSONB | GIN и индексы по отдельным выражениям | Да |
| Hstore | GIN и GiST | Нет |

`hstore` требует одноимённого расширения и хранит плоские пары «ключ — значение». `json` сохраняет исходный текст документа, а `jsonb` — разобранное представление, удобное для поиска и индексирования. Оба типа проверяют корректность JSON, **но не проверяют схему настроек**: наличие `theme` и тип его значения придётся контролировать отдельно.

Индекс GIN для JSONB полезен, в частности, для запросов с оператором `@>`. Он не ускоряет автоматически любое обращение к вложенному полю: запросу через `->>` с сравнением может понадобиться индекс по соответствующему выражению. Индексы также занимают место и увеличивают стоимость записи.

## 🔧 Практика: добавляем JSONB в Rails

Допустим, у модели `User` есть динамические настройки:

```ruby
# Миграция
class AddPreferencesToUsers < ActiveRecord::Migration[7.0]
  def change
    add_column :users, :preferences, :jsonb, default: {}, null: false
    add_index :users, :preferences, using: :gin
  end
end
```

Индекс GIN здесь пригодится для подходящих запросов по содержимому JSONB, например с `@>`. Если таких запросов нет, добавлять его заранее необязательно.

Работать со значением можно как с хэшем. После чтения JSONB из базы ключи будут строками:

```ruby
user = User.create!(
  email: "dev@example.com",
  preferences: {
    "theme" => "dark",
    "notifications" => {
      "email" => true,
      "push" => false
    }
  }
)

user.preferences.dig("notifications", "email") # => true
```

## 💡 Когда использовать JSONB?

1. **Динамические атрибуты** — например, настройки, набор которых меняется.
2. **Метаданные или ответы API** — если их удобно хранить вместе с записью и не требуется постоянно обновлять отдельные поля.
3. **Прототипирование** — пока структура данных ещё уточняется.

Если поля участвуют в связях между сущностями, требуют ограничений на уровне базы или по ним часто строят сложные запросы, отдельные колонки и таблицы обычно удобнее.

## 🚀 Продвинутые фишки

### 1. Поиск по вложенным полям

```ruby
# Найти всех с тёмной темой; такой запрос может использовать GIN-индекс
User.where("preferences @> ?", { theme: "dark" }.to_json)

# Те, кто отключил email-уведомления
User.where("preferences->'notifications'->>'email' = ?", "false")
```

Для второго запроса показанный GIN-индекс сам по себе не подходит. Если фильтрация по этому значению нужна часто, можно рассмотреть индекс по выражению запроса.

### 2. Частичное обновление

`update!` не понимает путь к вложенному ключу в имени атрибута. Для обычного обновления измените хэш и передайте его целиком:

```ruby
preferences = user.preferences.deep_dup
preferences["notifications"]["push"] = true
user.update!(preferences: preferences)
```

Такой способ записывает значение столбца целиком. Если несколько процессов меняют разные настройки одной записи, обновление на основе устаревшего хэша может затереть чужое изменение. Когда нужно изменить значение по пути на стороне PostgreSQL, можно использовать `jsonb_set`:

```ruby
User.where(id: user.id).update_all(
  "preferences = jsonb_set(preferences, '{notifications,push}', 'true'::jsonb, true)"
)
user.reload
```

Здесь родительский объект `notifications` уже существует. `update_all` обходит валидации и колбэки модели; применяйте его, только если это допустимо для записи.

### 3. Дефолтные значения через модель

```ruby
class User < ApplicationRecord
  attribute :preferences, :jsonb, default: -> {
    {
      "theme" => "light",
      "notifications" => {
        "email" => true
      }
    }
  }
end
```

Дефолт модели не меняет уже сохранённые значения и не заменяет дефолт в базе для записей, созданных вне ActiveRecord. В миграции выше дефолт базы — пустой объект; если оба способа создания записей должны получать одинаковые настройки, согласуйте эти значения.

## 💣 Антипаттерны

### 1. JSONB как мусорка

```ruby
# Плохо: всё подряд, без общей задачи
{
  last_login_ip: "...",
  cached_api_response: "...",
  temp_flags: [...]
}

# Лучше: логически связанные настройки
{
  ui_settings: { ... },
  notification_rules: [ ... ]
}
```

### 2. Отсутствие схемы

Если к структуре есть требования, проверяйте их явно. Например, модель может требовать непустую тему:

```ruby
validate :preferences_schema

def preferences_schema
  unless preferences.is_a?(Hash) && preferences["theme"].present?
    errors.add(:preferences, "must include theme")
  end
end
```

Такая валидация работает при сохранении через модель, но не защищает от изменений в обход ActiveRecord. Если правило должно соблюдаться при любой записи в базу, понадобится ограничение на уровне PostgreSQL.

### 3. Игнорирование индексов

Если запрос часто сравнивает результат `preferences->>'theme'`, для него можно добавить индекс по тому же выражению:

```ruby
# В миграции
add_index :users, "(preferences->>'theme')", name: "index_users_on_preferences_theme"
```

Выбирайте индекс под реальные запросы: без подходящего индекса PostgreSQL может читать таблицу целиком, но сам факт наличия JSONB не означает, что любой поиск будет медленным.

## 🧪 Тестирование

```ruby
describe User do
  describe "preferences" do
    let(:user) do
      create(:user, preferences: {
        "theme" => "dark",
        "notifications" => { "email" => true }
      })
    end

    it "validates presence of theme" do
      user.preferences.delete("theme")
      expect(user).not_to be_valid
    end

    it "allows nested updates" do
      preferences = user.preferences.deep_dup
      preferences["notifications"]["email"] = false
      user.update!(preferences: preferences)

      expect(user.reload.preferences.dig("notifications", "email")).to eq false
    end
  end
end
```

## 🎤 Что сказать на собеседовании

> — Почему вы выбрали JSONB вместо отдельной таблицы для настроек?

— Настройки удобно хранить вместе с пользователем, а набор полей может меняться. JSONB позволяет запрашивать их через операторы PostgreSQL. Индексы подбираем под конкретные запросы: например, GIN для `@>` или индекс по выражению для сравнения значения через `->>`. Если понадобятся связи, ограничения или сложные запросы по этим данным, пересмотрим схему.

---

## 🧭 Вывод

JSONB полезен для данных с гибкой структурой, которые логически принадлежат одной записи. Но он не отменяет валидацию, выбор индексов и осторожность при одновременных обновлениях. Если структура устоялась, а поля активно участвуют в запросах и связях, обычные колонки или отдельная таблица могут оказаться проще.
