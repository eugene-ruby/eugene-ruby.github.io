Вы только что получили доступ к своему первому VPS на Ubuntu 24.04 — и теперь смотрите на чёрный экран терминала с чувством, будто открыли дверь в космический корабль. Не волнуйтесь! Разберём первые шаги для запуска Docker-контейнеров, например с Ruby on Rails и PostgreSQL. Само приложение и базу данных здесь разворачивать не будем.

---

## 🚀 Шаг 1: Первые команды после входа

Подключитесь к серверу через SSH, если провайдер выдал доступ для `root`:

```bash
ssh root@ваш_ip
```

**Что сразу сделать:**

1. **Обновить пакеты:**
   ```bash
   apt update && apt upgrade -y
   ```

2. **Создать пользователя для дальнейшей работы:**
   ```bash
   adduser deploy
   usermod -aG sudo deploy
   ```

Прежде чем отключать вход для `root` или по паролю, настройте доступ для `deploy`. Например, пока вход по паролю разрешён, на **своём компьютере** выполните `ssh-copy-id deploy@ваш_ip`, затем проверьте вход командой `ssh deploy@ваш_ip`. Если вход по паролю изначально недоступен, добавьте свой публичный ключ в `/home/deploy/.ssh/authorized_keys` на сервере и проверьте права на каталог и файл. Текущую root-сессию пока не закрывайте.

Дальше команды установки и настройки выполняйте с `sudo` от имени `deploy` либо в оставшейся root-сессии — в примерах ниже показан второй вариант.

---

## 🐳 Шаг 2: Установка Docker и Docker Compose

Для Ubuntu 24.04 установите Docker и плагин Compose из репозиториев Ubuntu:

```bash
apt install -y docker.io docker-compose-v2
```

Проверьте установку:

```bash
docker --version
docker compose version
```

От имени `deploy` запускайте команды Docker через `sudo`, например `sudo docker compose version`. Добавлять пользователя в группу `docker` для удобства необязательно: участники этой группы фактически получают доступ с правами уровня `root` на хосте.

---

## 🛠️ Шаг 3: Лайт-оптимизация для Docker

Docker можно настроить так, чтобы логи **новых контейнеров** не росли без ограничения. Откройте конфигурацию демона:

```bash
nano /etc/docker/daemon.json
```

Если файл уже содержит настройки, дополните существующий JSON, а не заменяйте его целиком. Пример конфигурации:

```json
{
  "default-ulimits": {
    "nofile": {
      "Name": "nofile",
      "Hard": 65536,
      "Soft": 65536
    }
  },
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

🧠 **Что здесь происходит:**

* `nofile` задаёт число файловых дескрипторов, доступных процессам контейнера по умолчанию. Значение 65536 не предотвращает утечки: оно повышает порог, при достижении которого возможна ошибка `EMFILE`. Если приложению достаточно текущего лимита, менять его не нужно.
* `json-file` — стандартный драйвер логов Docker. Параметры `max-size` и `max-file` настраивают ротацию его файлов: до 10 МБ на файл и до трёх файлов на контейнер. Это ограничивает рост таких логов, но не расход диска всем Docker или логами, которые приложение пишет в другие места.

После изменения конфигурации перезапустите Docker, учитывая возможное влияние перезапуска на работающие контейнеры:

```bash
systemctl restart docker
```

Настройки по умолчанию применяются при создании контейнера: уже созданные контейнеры потребуется пересоздать, если вы хотите применить к ним новые параметры логирования.

## 🌐 Опционально: NGINX как точка входа + HTTPS

Если приложению нужен доступ по HTTP/HTTPS, NGINX может принимать запросы и передавать их приложению на порту 3000. Сначала убедитесь, что приложение действительно слушает этот порт на хосте. При публикации порта контейнера только для локального прокси можно привязать его к `127.0.0.1`, а не ко всем сетевым интерфейсам.

Установите NGINX:

```bash
apt install nginx -y
```

Сохраните конфигурацию в `/etc/nginx/sites-available/myapp`, заменив `example.com` на свой домен:

```nginx
server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

Активируйте её:

```bash
ln -s /etc/nginx/sites-available/myapp /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
```

### 🔐 Let's Encrypt + Certbot

Когда домен указывает на сервер, а порты 80 и 443 доступны извне, можно запросить сертификат:

```bash
apt install certbot python3-certbot-nginx -y
certbot --nginx -d example.com
```

Certbot может настроить автоматическое продление через системный таймер или cron, но не стоит считать его работающим без проверки. Посмотрите, настроено ли продление в вашей системе, и при необходимости проверьте его командой `certbot renew --dry-run`.

## 🔐 Бонус: усиление безопасности сервера

> ⚠️ Изменения SSH и фаервола могут лишить вас доступа к серверу. Сначала проверьте вход для `deploy` по ключу и оставьте текущую сессию открытой, пока не убедитесь, что новые настройки работают.

### 🚪 Защита SSH: новый порт и ключи вместо пароля

После проверки входа `deploy` по ключу можно отключить вход по паролю и для `root`. Откройте конфигурацию SSH:

```bash
nano /etc/ssh/sshd_config
```

Задайте параметры:

```text
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
```

Перед применением проверьте конфигурацию и перезагрузите службу:

```bash
sshd -t && systemctl reload ssh
```

Проверьте вход по ключу в **новой** SSH-сессии. В Ubuntu настройки из `/etc/ssh/sshd_config.d/` тоже могут влиять на итоговую конфигурацию; действующие значения можно посмотреть через `sshd -T`.

Смена стандартного порта, например на 2222, — необязательная мера и не заменяет ключи. Если всё же меняете порт, сначала откройте его в фаерволе сервера и панели провайдера. Учтите, что в Ubuntu 24.04 SSH может использовать socket activation: в таком случае одной строки `Port 2222` в `sshd_config` может быть недостаточно. Не закрывайте доступ через порт 22, пока не проверите подключение к новому.

---

### 🔥 Базовая защита через UFW (фаервол)

Пока SSH работает на порту 22, разрешите его **до** включения UFW. Если используете NGINX, также откройте HTTP и HTTPS:

```bash
ufw allow 22/tcp
ufw allow 80,443/tcp
ufw enable
ufw status verbose
```

Если вы сменили порт SSH и проверили вход через него, разрешите новый порт в UFW, прежде чем удалять правило для старого. Открывайте только нужные порты; учитывайте и фаервол в панели провайдера, если он есть.

---

### 🛡️ Fail2Ban — баним брутфорсеров

Fail2Ban может временно блокировать адреса после неудачных попыток входа, если соответствующий jail включён и получает события SSH. Установки пакета самой по себе недостаточно, чтобы считать защиту работающей:

```bash
apt install fail2ban -y
systemctl enable fail2ban --now
```

Проверьте SSH-jail командой `fail2ban-client status sshd`. Если он не включён, настройте его в отдельном файле `/etc/fail2ban/jail.d/`, затем перезапустите Fail2Ban и проверьте статус снова.

## 💡 Антипаттерны новичков

1. **Постоянная работа от root**  
   *Проблема:* ошибочная команда получает полный доступ к системе.  
   *Решение:* для обычной работы используйте отдельного пользователя с `sudo` и выдавайте повышенные права там, где они нужны.
2. **Docker без лимитов ресурсов**  
   *Проблема:* контейнер с утечкой памяти может занять память хоста. Настройка ротации логов выше от этого не защищает.  
   *Решение:* задавайте лимит памяти для конкретного контейнера с учётом потребностей приложения, например `--memory=512m` в `docker run`.
