Вы только начали pet-проект: база работает, API отвечает, бот в Telegram шлёт котиков. И вдруг — случайный коммит с `TOKEN=abc123` в публичный репозиторий. Разберём минимальный набор мер, который помогает не допустить такой утечки в Ruby-проекте и заметить её, если она уже произошла.

---

## 💀 История из интернетов

```bash
+ Дедлайн через 2 часа
+ Надо срочно задеплоить фичу
+ git add . && git commit -m "fix auth"
+ git push
# Позже:
- "Почему наш бот рассылает рекламу? 🔞"
```

**Мораль**: секреты могут утечь по невнимательности. Защищать их стоит с первого коммита.

---

## 🧠 Теория: что такое секрет в XXI?

Это данные, которые дают доступ или позволяют выдавать себя за ваше приложение:

- API-ключи (Telegram Bot Token, OpenAI, Stripe)
- Учётные данные базы данных (`postgres://user:password@host`)
- Ключи подписи и шифрования (Rails `secret_key_base`)
- Секреты OAuth-клиентов (`GOOGLE_CLIENT_SECRET=abc123`)

**Главное правило**: секреты не должны попадать в Git-историю. Если секрет уже был закоммичен, одного удаления из файла недостаточно: он остаётся в истории и его нужно отозвать или заменить.

## 🛡️ Защитный стек для Ruby-проекта

### 1. `.env` + `dotenv` — локальная разработка

Для Rails добавляем гем:

```ruby
# Gemfile
gem 'dotenv-rails', groups: [:development, :test]
```

Создаём `.env` и заранее добавляем его в `.gitignore`:

```bash
# .env
DATABASE_URL="postgres://user:password@localhost:5432/pet_project"
TELEGRAM_TOKEN="123:abc"
```

`dotenv-rails` подгружает переменные при запуске Rails в указанных группах. Дополнительно вызывать `Dotenv::Railtie.load` в `config/application.rb` не нужно.

⚠️ **Проверьте**: `git check-ignore .env` должен вывести путь к файлу.

---

### 2. `.gitignore` — защита от случайного добавления

Правила ниже не дадут случайно добавить локальные файлы окружения через `git add .`:

```gitignore
# .gitignore
.env
*.env.local
.env*.local
```

Но `.gitignore` не действует на файлы, которые Git уже отслеживает. Проверьте это командой `git ls-files .env`. Если она вывела `.env`, уберите файл из индекса через `git rm --cached .env` и замените секреты, которые уже попали в историю. Правила выше также не покрывают все возможные имена файлов с секретами — добавляйте исключения под свой проект.

---

### ❌ Антипаттерн: молчать, если переменной окружения нет

Если пароль базы передаётся через `DB_PASS`, отсутствие переменной не должно незаметно превращаться в пустое значение:

```yaml
# config/database.yml — отсутствие DB_PASS останется незамеченным
production:
  password: <%= ENV['DB_PASS'] %>
```

Подставлять известный пароль по умолчанию для production ещё опаснее:

```yaml
# config/database.yml — плохо!
production:
  password: <%= ENV.fetch('DB_PASS', 'password') %>
```

---

### ✅ Как правильно: fail fast

Если конфигурация production действительно зависит от `DB_PASS`, требуйте её наличия:

```yaml
# config/database.yml
production:
  password: <%= ENV.fetch('DB_PASS') %>
```

При чтении конфигурации `ENV.fetch` вызовет ошибку, если переменная отсутствует. При этом он **не отвергает пустую строку**: если она недопустима, проверяйте значение отдельно. В примере выше используется `DB_PASS`; если приложение получает все параметры подключения через `DATABASE_URL`, настраивайте и проверяйте именно его, а не оба варианта без необходимости.

---

### 3. GitHub Secrets — передача секрета в деплой

Для GitHub Actions:

1. Добавляем секрет репозитория в `Settings → Secrets and variables → Actions`, например `PROD_DB_URL` или `RAILS_MASTER_KEY`.
2. Передаём его нужному шагу workflow через `secrets`.

{% raw %}
```yaml
# Фрагмент шага .github/workflows/deploy.yml
- name: Migrate database
  env:
    RAILS_ENV: production
    DATABASE_URL: ${{ secrets.PROD_DB_URL }}
  run: rails db:migrate
```
{% endraw %}

Этот фрагмент предполагает, что в job уже подготовлено окружение Ruby, установлены зависимости и есть доступ к базе. Секрет из GitHub Actions не обязан быть доступен каждому запуску workflow: учитывайте ограничения выбранного события и окружения деплоя.

**Важно**: не выводите секреты в логи. Не полагайтесь только на маскирование вывода GitHub Actions — приложение тоже может записать значение в собственный лог.

```ruby
# Плохо:
Rails.logger.info("Connected to #{ENV['DATABASE_URL']}")
# Хорошо:
Rails.logger.info("Connected to database")
```

## 💥 Сценарии утечек

### Кейс 1: Rails `secret_key_base` в открытом доступе

- **Что произошло**: разработчик закоммитил конфигурацию с production-ключом.
- **Чем опасно**: знание `secret_key_base` ставит под угрозу данные и механизмы аутентификации, защищённые этим ключом, в том числе подписанные Rails-куки.
- **Что делать**: заменить скомпрометированный ключ и проверить, какие данные и сессии зависят от него. Для хранения ключа можно использовать Rails credentials: `config/credentials.yml.enc` допустимо хранить в репозитории, а ключ расшифровки (`config/master.key` или соответствующий `RAILS_MASTER_KEY`) — нет.

### Кейс 2: ключи к AWS S3 с правами на запись

- **Что произошло**: ключи попали в историю Git.
- **Чем опасно**: тот, кто получил ключи, может использовать выданные им права, например записывать объекты в бакет, а это может привести и к расходам.
- **Что делать**: отозвать ключи, проверить действия с ними и выдать новые учётные данные с минимально необходимыми правами. Где доступна аутентификация через IAM-роли, она позволяет не хранить долгоживущие ключи приложения.

## 🧪 Проверяем безопасность

1. Ищем подозрительные строки в истории:

```bash
git log -p --all | grep -Ei 'password|token|key'
```

Это лишь грубая проверка: она пропустит секреты с другими именами и даст ложные срабатывания. Если секрет найден, отзовите или замените его; удаление строки новым коммитом не делает прежнее значение безопасным.

2. Отдельно проверяем зависимости и Rails-код:

```ruby
# Gemfile
gem 'bundler-audit', require: false
gem 'brakeman', require: false
```

`bundler-audit` ищет известные уязвимости в зависимостях, `brakeman` анализирует Rails-приложение. **Они не заменяют поиск секретов в Git-истории.**

3. Запускаем проверку зависимостей в CI, если гем установлен в окружении job:

```yaml
# Фрагмент steps в .github/workflows/security.yml
- name: Audit gems
  run: bundle audit check --update
```

## 🎤 Что сказать на собеседовании

> — Как вы храните секреты в проектах?

— Для локальной разработки используем `.env` и не добавляем его в Git. В Rails можем хранить конфигурацию в зашифрованных credentials, а в CI/CD передаём секреты через настройки платформы. Ограничиваем доступ к ключам; при утечке отзываем или заменяем их.

## 🧾 Вывод

**Секреты — как зубная щётка: нельзя давать другим, даже «на минуточку».**

Начните с `.gitignore` и безопасного способа передавать переменные в локальную среду и деплой. Проверяйте, что нужная конфигурация задана, а если ключ попал в историю — считайте его раскрытым и заменяйте.
