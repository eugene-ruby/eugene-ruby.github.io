PgBouncer помогает управлять соединениями с PostgreSQL, когда к базе одновременно обращаются веб-процессы, фоновые задачи и другие клиенты. Разберём, как выбрать режим пула, согласовать лимиты и учесть ограничения при работе с Rails.

---

> PgBouncer не ускоряет SQL-запросы сам по себе: он позволяет обслуживать клиентские подключения меньшим числом соединений с PostgreSQL.

## 🧠 Зачем нужен PgBouncer

Каждое соединение с PostgreSQL обслуживается отдельным серверным процессом и расходует ресурсы. Большое число соединений может стать проблемой, особенно если многие из них простаивают.

PgBouncer принимает подключения от Puma, Sidekiq и других клиентов и повторно использует соединения с базой. Сколько серверных соединений потребуется, зависит от режима пула, настроек и нагрузки — фиксированного числа вроде 5–10 здесь нет.

---

## ⚙️ Как работает

PgBouncer может работать в трёх режимах:

| Режим | Как работает | Когда использовать |
|-------|--------------|--------------------|
| `session` | закрепляет серверное соединение за клиентом до конца сессии | когда приложению нужны возможности, привязанные к сессии; помогает переиспользовать соединения между сессиями, но не освобождает их между транзакциями одного клиента |
| `transaction` | выдаёт серверное соединение на время транзакции; вне явной транзакции — на время отдельного запроса | когда приложение не полагается на состояние серверной сессии между транзакциями |
| `statement` | выдаёт соединение на время одного запроса | когда не нужны транзакции из нескольких запросов; для обычного Rails-приложения, как правило, не подходит |

## 🛠 Пример настройки

Пример для изолированного локального стенда:

```ini
# /etc/pgbouncer/pgbouncer.ini
[databases]
myapp = host=127.0.0.1 port=5432 dbname=myapp

[pgbouncer]
listen_port = 6432
listen_addr = 127.0.0.1
# trust не проверяет пароль клиента; допустим только на изолированном стенде.
auth_type = trust
# При trust в файле должны быть перечислены допустимые пользователи.
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 20
```

Аутентификацию PgBouncer при подключении к самому PostgreSQL нужно настроить отдельно. Для рабочего окружения вместо `trust` настройте проверку учётных данных клиента и защиту соединений в соответствии с вашей сетевой схемой.

В Rails для такого локального стенда:

```yaml
# config/database.yml
development:
  host: 127.0.0.1
  port: 6432
  pool: 20
  prepared_statements: false
```

Значение `pool` задаёт лимит подключений **для одного процесса Rails**, а не общий лимит приложения. `default_pool_size` ограничивает число серверных соединений в пуле PgBouncer для пары «база — пользователь»; если клиентов больше, они могут ждать свободного соединения. Подбирайте лимиты с учётом числа процессов, фоновых задач и доступных ресурсов PostgreSQL.

`prepared_statements: false` — простой способ избежать проблем с подготовленными запросами Active Record в режиме `transaction`: следующий запрос может попасть на другое серверное соединение. В конфигурациях PgBouncer, поддерживающих подготовленные запросы протокола, их можно использовать при соответствующей настройке; совместимость с приложением нужно проверять отдельно.

## 🪤 Ловушки

### 1. `ActiveRecord::Base.connection.active?` возвращает false

Сам по себе режим `transaction` не должен заставлять `active?` возвращать `false`: освобождение серверного соединения после транзакции не означает, что клиентское подключение Rails к PgBouncer закрылось. Если метод возвращает `false`, проверьте состояние этого подключения и журналы Rails и PgBouncer, а не списывайте результат на обычную работу пула.

---

### 2. PgHero ломается

Не всякая функция инструмента мониторинга совместима с режимом `transaction`: проблема возникает, если ей нужно состояние серверной сессии между запросами. Если PgHero выдаёт ошибки, проверьте используемую функцию и её подключение. Для операций, которым нужна постоянная серверная сессия, используйте отдельное подключение напрямую к PostgreSQL или через PgBouncer в режиме `session`.

---

### 3. Миграции и `rails db:prepare`

Rails-миграции могут выполнять несколько запросов в одной транзакции, поэтому режим `statement` для них не подходит: он не поддерживает транзакции из нескольких запросов. Выбирайте `transaction` либо запускайте миграции через отдельное подключение к PostgreSQL. Прямое подключение также пригодится миграциям, которым нужны возможности, привязанные к серверной сессии.

---

## 🧩 Вывод

PgBouncer помогает ограничить число соединений с PostgreSQL, но не заменяет настройку лимитов и проверку совместимости приложения с выбранным режимом. Для Rails обычно начинают с `transaction`, учитывая подготовленные запросы и операции, которым требуется состояние сессии.
