Деплой стоит настраивать в начале проекта: он проверяет то, чего не видно при локальном запуске, — серверное окружение, доступы, конфигурацию, хранение данных и обновление сервисов. Разберём этот подход на WordPress и MariaDB: сначала запустим их вручную на VPS, затем автоматизируем доставку через GitHub Actions. Готовые образы позволят сосредоточиться на процессе, а не на сборке приложения.

## 🎯 Основная идея

**Первый работающий деплой должен появиться раньше первой серьёзной функциональности.**

Это не значит, что в первый день нужны Kubernetes, несколько окружений и собственная платформа для разработчиков. Нужен короткий проверяемый путь от изменения в Git до работающего сервиса на сервере.

Когда этот путь откладывают, перед релизом приходится одновременно решать несколько разных задач:

- выяснять, почему приложение работает локально, но не запускается на сервере;
- разносить конфигурацию и секреты;
- определять, где живут постоянные данные;
- настраивать сетевой доступ;
- придумывать порядок обновления и проверку результата.

Каждая задача сама по себе обычно решаема. Проблема в том, что перед релизом они приходят всей компанией.

Ранний деплой уменьшает эту неопределённость. Сначала мы доставляем минимальный сервис, а затем развиваем и приложение, и способ его доставки. Выпуск новой версии постепенно становится обычной технической операцией, а не отдельным проектом.

## 🧱 Минимальная инфраструктура

Для примера понадобятся:

- GitHub-репозиторий с конфигурацией;
- GitHub Actions для проверки и запуска деплоя;
- VPS с Linux и доступом по SSH;
- Docker Engine и плагин Docker Compose v2 на сервере;
- Bash и `curl` на сервере;
- WordPress и MariaDB из официальных Docker-образов.

Схема получится такой:

```text
push в main
    ↓
GitHub Actions: проверка Compose
    ↓ SSH / SCP
VPS: получение конфигурации
    ↓
docker compose pull + up -d
    ↓
проверка HTTP-ответа
```

WordPress будет доступен только на loopback-интерфейсе VPS: `127.0.0.1:8080`. Для первого знакомства подключимся через SSH-туннель. Базу данных наружу публиковать не будем.

Это учебная односерверная схема, а не готовая отказоустойчивая платформа. Перед публичным использованием понадобятся домен, HTTPS, резервное копирование и проверенная процедура восстановления.

В репозитории будут четыре основных файла:

```text
compose.yaml
release.env
deploy.sh
.github/workflows/deploy.yaml
```

Файл `release.env` содержит ссылки на образы и хранится в Git. Пароли остаются на сервере в отдельном `secrets.env`.

## 🐳 Описываем сервисы и постоянные данные

Создадим `compose.yaml`:

```yaml
services:
  db:
    image: ${MARIADB_IMAGE:?Set MARIADB_IMAGE}
    restart: unless-stopped
    environment:
      MARIADB_DATABASE: wordpress
      MARIADB_USER: wordpress
      MARIADB_PASSWORD: ${DB_PASSWORD:?Set DB_PASSWORD}
      MARIADB_ROOT_PASSWORD: ${DB_ROOT_PASSWORD:?Set DB_ROOT_PASSWORD}
    volumes:
      - db_data:/var/lib/mysql

  wordpress:
    image: ${WORDPRESS_IMAGE:?Set WORDPRESS_IMAGE}
    restart: unless-stopped
    depends_on:
      - db
    ports:
      - "127.0.0.1:8080:80"
    environment:
      WORDPRESS_DB_HOST: db:3306
      WORDPRESS_DB_NAME: wordpress
      WORDPRESS_DB_USER: wordpress
      WORDPRESS_DB_PASSWORD: ${DB_PASSWORD:?Set DB_PASSWORD}
    volumes:
      - wordpress_data:/var/www/html

volumes:
  db_data:
  wordpress_data:
```

Здесь важны несколько решений.

**Сервисы общаются по внутренней сети Compose.** Имя `db` становится адресом базы для WordPress. Публикация порта `3306` на VPS для этого не нужна.

**Данные вынесены в именованные тома.** В `db_data` хранится база, в `wordpress_data` — файлы WordPress, включая загруженные материалы, темы и плагины. Пересоздание контейнера само по себе эти тома не удаляет.

**`depends_on` задаёт порядок запуска, но не готовность базы.** Запущенный процесс MariaDB ещё может выполнять первичную инициализацию. Поэтому сразу после `up -d` WordPress не обязательно готов отвечать: ниже будет отдельная проверка с повторными попытками.

**Отсутствующие переменные вызывают ошибку.** Конструкция `${DB_PASSWORD:?Set DB_PASSWORD}` не даёт незаметно запустить конфигурацию с пустым значением.

### 📌 Фиксируем образы

Не будем использовать плавающий `latest` при развёртывании. Запишем в `release.env` ссылки на конкретное содержимое образов — digest:

```dotenv
WORDPRESS_IMAGE=wordpress@sha256:<digest-выбранного-образа>
MARIADB_IMAGE=mariadb@sha256:<digest-выбранного-образа>
```

Это шаблон: значения в угловых скобках нужно заменить реальными digest. Выберите совместимые поддерживаемые выпуски по документации WordPress и MariaDB. Для приведённой конфигурации нужен вариант WordPress с Apache, обслуживающий HTTP на порту `80`, а не вариант с PHP-FPM.

Digest можно получить после загрузки выбранного образа. Например, следующая последовательность показывает механизм; тег MariaDB перед запуском нужно заменить:

```bash
WP_TAG='wordpress:apache'
DB_TAG='mariadb:<выбранный-тег>'

docker pull "$WP_TAG"
docker pull "$DB_TAG"

docker image inspect "$WP_TAG" --format '{{index .RepoDigests 0}}'
docker image inspect "$DB_TAG" --format '{{index .RepoDigests 0}}'
```

Полученные полные ссылки перенесите в `release.env`. Плавающий тег здесь используется только для выбора образа; при деплое будет использоваться зафиксированный digest.

Фиксация не делает обновления ненужными. Она делает их явными: новый образ появляется через изменение в Git, которое можно просмотреть до выкладки.

## 🖥️ Первый ручной запуск на VPS

Автоматизация должна повторять понятный рабочий процесс. Если ручной запуск ещё не работает, GitHub Actions лишь добавит к ошибке ещё один слой логов.

### 🔑 Готовим доступ и каталог

Установите Docker Engine и Compose по инструкции для выбранного дистрибутива. Универсальной команды установки для любого Linux нет. После установки проверьте:

```bash
docker version
docker compose version
```

Далее предполагается, что на сервере уже создан пользователь `deploy`, который входит по SSH и может выполнять команды Docker без `sudo`. Администратор может подготовить каталог так:

```bash
sudo install -d -m 0750 -o deploy -g deploy /opt/first-deploy
```

Важное ограничение: доступ к обычному системному Docker daemon практически равнозначен административному доступу к серверу. Отдельный пользователь удобен для управления ключами, но членство в группе `docker` не превращает его в изолированную учётную запись с минимальными правами.

### 🔐 Создаём секреты только на сервере

От имени `deploy` создайте `/opt/first-deploy/secrets.env`:

```dotenv
DB_PASSWORD=<отдельный-случайный-пароль>
DB_ROOT_PASSWORD=<другой-случайный-пароль>
```

Замените оба значения. Например, для каждого пароля отдельно можно использовать результат команды:

```bash
openssl rand -hex 32
```

Шестнадцатеричные строки удобны ещё и тем, что не требуют разбираться с экранированием специальных символов в env-файле.

Ограничьте доступ к файлу:

```bash
chmod 600 /opt/first-deploy/secrets.env
```

В репозиторий добавьте `.gitignore`:

```gitignore
secrets.env
.env
```

Если секрет уже попал в Git, добавления в `.gitignore` недостаточно: его нужно заменить. Удаление файла из последнего коммита не удаляет значение из истории.

### ⚙️ Записываем процедуру деплоя

В корне репозитория создадим `deploy.sh`. Его будем запускать и вручную, и из CI/CD, чтобы не поддерживать две разные последовательности команд:

```bash
#!/usr/bin/env bash
set -euo pipefail

cd -- "$(dirname -- "$0")"

dc() {
  docker compose \
    --project-name first-deploy \
    --env-file release.env \
    --env-file secrets.env \
    --file compose.yaml \
    "$@"
}

dc config --quiet
dc pull
dc up -d
dc ps

for attempt in $(seq 1 30); do
  if curl --fail --silent --show-error \
    --max-time 5 \
    --output /dev/null \
    http://127.0.0.1:8080/wp-login.php; then
    echo 'HTTP check passed'
    exit 0
  fi

  sleep 2
done

echo 'HTTP check failed' >&2
exit 1
```

Compose получает переменные из двух файлов: версионируемого `release.env` и серверного `secrets.env`. Не определяйте одни и те же переменные одновременно в обоих файлах и в окружении пользователя: это усложняет понимание того, какие значения будут использованы.

Постоянное имя проекта `first-deploy` нужно не для красоты. Compose использует имя проекта при формировании имён ресурсов, в том числе томов. Если случайно сменить его, сервисы могут подключиться к новым пустым томам — будет выглядеть так, будто данные исчезли, хотя старые тома остались на сервере.

Проверка HTTP здесь намеренно простая. `curl --fail` считает ошибкой HTTP-ответы с кодами `400` и выше, но допускает перенаправления. Успех означает, что endpoint отвечает без такой ошибки, а не то, что установка WordPress завершена и все функции сайта исправны. Для этого нужны отдельные проверки приложения.

### 🚀 Запускаем

На локальной машине из корня репозитория скопируйте файлы и запустите скрипт. Замените `VPS_HOST` адресом сервера:

```bash
scp compose.yaml release.env deploy.sh \
  deploy@VPS_HOST:/opt/first-deploy/

ssh deploy@VPS_HOST 'bash /opt/first-deploy/deploy.sh'
```

Перед первым подключением проверьте SSH-ключ сервера по доверенному каналу, например через консоль провайдера. Не подтверждайте неизвестный ключ автоматически только ради того, чтобы команда прошла.

Для доступа к WordPress откройте отдельное SSH-соединение:

```bash
ssh -N -L 8080:127.0.0.1:8080 deploy@VPS_HOST
```

Теперь адрес `http://localhost:8080` в браузере ведёт к WordPress на VPS. Туннель работает, пока открыто SSH-соединение. Если локальный порт занят, выберите другой свободный порт в левой части `-L`.

На тестовом стенде можно завершить установку и создать пробную запись. Но учитывайте: WordPress сохраняет адрес сайта. Если установить его как `http://localhost:8080`, при переходе на публичный домен понадобится корректно изменить настройки адресов и при необходимости ссылки в содержимом. Для реального сайта лучше сначала подготовить окончательный домен и HTTPS, а затем проходить установку по этому адресу.

## 🔄 Автоматизируем деплой через GitHub Actions

Теперь перенесём уже работающую последовательность в workflow.

В этом примере **CI** проверяет, что Compose-конфигурация корректно обрабатывается с заданными переменными. **CD** доставляет конфигурацию на сервер, загружает готовые образы и применяет изменения.

Мы не собираем WordPress, не тестируем его исходники и не создаём собственный Docker-образ. Проверка Compose также не доказывает совместимость выбранных версий: это только один уровень проверки.

### 🗝️ Настраиваем доступ к серверу

Создайте отдельную SSH-пару для автоматизации. Публичный ключ добавьте в `authorized_keys` пользователя `deploy`, приватный сохраните в GitHub Secrets.

Создайте GitHub Environment с именем `production` и добавьте в него секреты:

- `SSH_HOST` — адрес сервера;
- `SSH_PORT` — порт SSH, например `22`;
- `SSH_USER` — `deploy`;
- `SSH_PRIVATE_KEY` — приватный ключ для автоматизации;
- `SSH_KNOWN_HOSTS` — проверенная запись публичного SSH-ключа сервера в формате `known_hosts`.

При нестандартном порте запись `known_hosts` должна соответствовать подключению к этому порту. Ключ можно получить с помощью `ssh-keyscan`, но его отпечаток нужно независимо сверить с сервером. Сам по себе `ssh-keyscan` не подтверждает подлинность узла.

Пароли базы в GitHub не передаём: они уже находятся на VPS и не нужны для доставки конфигурации.

### 🧩 Добавляем workflow

Создадим `.github/workflows/deploy.yaml`:

```yaml
name: Deploy

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: first-deploy-production
  cancel-in-progress: false

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Check Docker Compose
        run: docker compose version

      - name: Validate Compose configuration
        env:
          DB_PASSWORD: validation-only
          DB_ROOT_PASSWORD: validation-only-root
        run: |
          docker compose \
            --project-name first-deploy \
            --env-file release.env \
            --file compose.yaml \
            config --quiet

  deploy:
    needs: validate
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4

      - name: Deploy to VPS
        shell: bash
        env:
          SSH_HOST: ${{ secrets.SSH_HOST }}
          SSH_PORT: ${{ secrets.SSH_PORT }}
          SSH_USER: ${{ secrets.SSH_USER }}
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          SSH_KNOWN_HOSTS: ${{ secrets.SSH_KNOWN_HOSTS }}
        run: |
          set -euo pipefail

          install -d -m 700 "$HOME/.ssh"
          printf '%s\n' "$SSH_PRIVATE_KEY" > "$HOME/.ssh/deploy_key"
          printf '%s\n' "$SSH_KNOWN_HOSTS" > "$HOME/.ssh/known_hosts"
          chmod 600 "$HOME/.ssh/deploy_key" "$HOME/.ssh/known_hosts"
          trap 'rm -f "$HOME/.ssh/deploy_key"' EXIT

          SSH_OPTIONS=(
            -i "$HOME/.ssh/deploy_key"
            -o IdentitiesOnly=yes
            -o StrictHostKeyChecking=yes
          )

          scp "${SSH_OPTIONS[@]}" -P "$SSH_PORT" \
            compose.yaml release.env deploy.sh \
            "$SSH_USER@$SSH_HOST:/opt/first-deploy/"

          ssh "${SSH_OPTIONS[@]}" -p "$SSH_PORT" \
            "$SSH_USER@$SSH_HOST" \
            'bash /opt/first-deploy/deploy.sh'
```

Проверка использует заведомо тестовые пароли. `config --quiet` не запускает контейнеры и не обращается к рабочей базе. Ему нужно лишь получить значения обязательных переменных и проверить конфигурацию. Содержимое конфигурации с подставленными паролями в лог не выводим.

Workflow предполагает наличие Docker Compose v2 на выбранном runner; отдельный шаг сразу выявит его отсутствие. Для GitHub Actions здесь используется известный релизный тег `actions/checkout`. Если политика проекта требует неизменяемых зависимостей, закрепите сторонние actions на проверенных полных commit SHA.

`concurrency` не позволяет двум workflow этой группы выполнять деплой одновременно. При этом это не строгая очередь всех релизов: ожидающие запуски могут заменяться более новыми. Ручные изменения на VPS эта настройка тоже не блокирует.

Защитите `main` и ограничьте доступ к environment `production`. Тот, кто может изменить `deploy.sh` и добиться запуска job с серверным SSH-ключом, фактически может выполнять команды на VPS.

### 🔍 Что происходит при обновлении

После изменения в `main`:

1. Actions получает содержимое коммита и проверяет Compose.
2. Job деплоя получает доступ к секретам окружения `production`.
3. SCP копирует три файла, не затрагивая `secrets.env`.
4. `pull` проверяет возможность получить указанные образы до изменения работающих контейнеров.
5. `up -d` применяет изменения конфигурации и при необходимости пересоздаёт контейнеры.
6. Скрипт выводит состояние сервисов и проверяет HTTP-ответ.

Если `pull` завершится ошибкой, до `up -d` выполнение не дойдёт. Если ошибка возникнет во время применения или проверки, job завершится неуспешно, но прежнее состояние автоматически не восстановится.

Копирование файлов тоже не атомарно: конфигурация на диске может уже обновиться, даже если следующий шаг не выполнился. Для небольшого стенда это допустимое упрощение. Для более строгой процедуры стоит доставлять каждый релиз в отдельный каталог, проверять его и только потом переключать активную конфигурацию.

## 🛡️ Что важно не сломать

### 💾 Постоянный том — не резервная копия

Тома защищают данные от обычного пересоздания контейнера, но не от удаления, ошибки приложения, повреждения базы или потери VPS.

Не используйте `docker compose down -v` как часть обновления: флаг `-v` удаляет управляемые Compose тома. Не запускайте без разбора очистку Docker-ресурсов с удалением томов.

Для этого стенда нужны резервные копии как минимум базы данных и файлов WordPress. Простое копирование каталога работающей MariaDB не гарантирует согласованную копию. Используйте подходящий для базы способ резервирования и отдельно проверяйте восстановление в другом окружении. Копия только на том же VPS не защищает от потери сервера.

### 🔁 Обновление контейнера — не всегда обновление WordPress

В примере весь `/var/www/html` находится в постоянном томе. Это удобно для обычной установки WordPress, но означает, что состояние сайта не определяется одним digest образа.

Новый образ не гарантирует замену уже существующих файлов ядра в томе. Обновления ядра, тем и плагинов через административную панель, в свою очередь, меняют состояние сайта вне Git.

Поэтому этот workflow автоматизирует **развёртывание окружения и применение его конфигурации**, а не создаёт полностью воспроизводимый релиз содержимого WordPress. Для управляемой доставки собственного кода тем и плагинов понадобится отдельная стратегия сборки и обновления. Не стоит выдавать `docker compose pull` за универсальный механизм обновления CMS.

### 🔐 Смена env-пароля не равна смене пароля в базе

Переменные `MARIADB_PASSWORD` и `MARIADB_ROOT_PASSWORD` используются при первичной инициализации пустого каталога данных. Если база уже существует, изменение `secrets.env` само по себе не меняет пароли внутри неё.

Типичная ошибка — заменить `DB_PASSWORD`, пересоздать контейнеры и получить отказ WordPress в подключении: приложение уже использует новое значение, а база всё ещё ожидает старое.

Ротацию нужно выполнять согласованно: изменить учётные данные в самой базе, обновить конфигурацию клиента и проверить подключение. Порядок зависит от выбранной процедуры и допустимого простоя.

### 🌐 Публичному сайту нужны домен и HTTPS

Привязка `127.0.0.1:8080:80` не предназначена для прямого доступа из интернета. Перед публикацией поставьте перед WordPress reverse proxy с TLS и настройте firewall: наружу должны быть доступны только необходимые порты.

При завершении HTTPS на прокси WordPress должен корректно определять исходную схему запроса. Иначе возможны циклические редиректы и неправильные ссылки. Настройка зависит от прокси и конфигурации WordPress; передаваемые сведения о схеме следует принимать только от доверенного прокси.

После этого проверяйте не только локальный endpoint, но и публичный HTTPS-адрес: работающий контейнер ничего не говорит о DNS, сертификате и маршрутизации внешнего запроса.

### ↩️ Неуспешный деплой не означает автоматический откат

`docker compose up -d` не является транзакцией над всем приложением. Обновление может прервать обслуживание, а ошибка — оставить сервисы в частично обновлённом состоянии.

Возврат старого `release.env` способен вернуть прежний образ контейнера, но не отменяет изменения файлов в томе и миграции базы. Особенно осторожно нужно обновлять MariaDB: прежний образ не обязательно сможет работать с каталогом данных после обновления.

Перед такими изменениями нужны резервная копия, проверка совместимости и понятный план восстановления. Требования к обновлениям без простоя и автоматическому откату выходят за рамки этого минимального процесса.

## 🧪 Проверяем полный цикл

Первый зелёный workflow показывает, что один запуск прошёл успешно. Чтобы проверить сам процесс, полезно пройти ещё несколько сценариев.

**1. Применение изменения из Git.** Добавьте к сервису WordPress диагностическую метку:

```yaml
labels:
  deployment.note: "first-pipeline-check"
```

Отправьте коммит в `main`, дождитесь workflow и проверьте наличие метки у контейнера. На сервере из `/opt/first-deploy`:

```bash
container_id=$(docker compose \
  --project-name first-deploy \
  --env-file release.env \
  --env-file secrets.env \
  --file compose.yaml \
  ps -q wordpress)

docker inspect \
  --format '{{ index .Config.Labels "deployment.note" }}' \
  "$container_id"
```

Ожидаемое значение — `first-pipeline-check`. Такая проверка подтверждает не только факт запуска workflow, но и применение конкретной конфигурации.

**2. Повторный запуск.** Повторно запустите workflow для актуального коммита. Он не должен требовать удаления контейнеров, ручного создания базы или повторной установки WordPress.

Не перезапускайте старый workflow без понимания последствий: он может доставить конфигурацию старого коммита поверх более новой. Это особенно опасно после изменений базы.

**3. Сохранность данных.** До изменения создайте тестовую запись и загрузите файл через WordPress. После пересоздания контейнера проверьте, что запись и файл доступны. Это проверяет подключение постоянных томов, но не заменяет тест восстановления из backup.

**4. Обнаружение ошибки.** В отдельной ветке удалите обязательную переменную и локально выполните ту же команду `config --quiet`, передав тестовые пароли через окружение. Проверка должна завершиться ошибкой до запуска сервисов. Текущий workflow запускается только для `main`, поэтому для автоматической проверки pull request нужно отдельно добавить соответствующий триггер без доступа к production-секретам.

**5. Поведение при сбое приложения.** На тестовом окружении убедитесь, что недоступность endpoint приводит к неуспешному завершению проверки. Отдельно зафиксируйте, что этот статус не запускает восстановление: исправление или откат остаются вашей задачей.

## 🏁 Выводы

Начать проект с деплоя — значит заранее проверить путь от репозитория до работающего сервиса. Для небольшого проекта этот путь может состоять из GitHub Actions, Docker Compose и одного VPS: без сложной платформы, но с понятными командами и проверкой результата.

В нашем примере конфигурация и ссылки на образы находятся в Git, пароли остаются на сервере, данные живут в постоянных томах, а обновление выполняется одной процедурой вручную и автоматически. Это уже полезная основа, на которую можно опираться при разработке.

Её границы тоже важны: простая HTTP-проверка не заменяет функциональные тесты, тома не заменяют backup, а пересоздание контейнеров не гарантирует обновление WordPress или безопасный откат базы. Улучшать процесс стоит по мере появления этих требований — но сам процесс доставки лучше получить до того, как первая большая функция будет готова к релизу.
