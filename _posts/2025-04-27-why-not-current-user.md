В контроллере Rails `current_user` помогает узнать пользователя, от имени которого пришёл запрос. Но сервисный объект или фоновая задача могут выполняться без HTTP-запроса. Если им нужен пользователь, эту зависимость стоит передать явно.

---

Когда приложение маленькое, `current_user` легко получить из контроллера. Но со временем появляются фоновые задачи, обработчики событий и команды. Им тоже может понадобиться знать, кто запустил действие.

## 🧵 Контекст теряется

Вот пример:

```ruby
class CreateReportJob < ApplicationJob
  def perform(report_id)
    report = Report.find(report_id)
    ReportBuilder.new(report).call # Кто запросил отчёт?
  end
end
```

Если отчёт нужно подписать именем пользователя или записать, кто его запросил, из аргумента `report_id` этого не узнать. Фоновая задача не выполняется внутри контроллера, поэтому взять в ней `current_user` напрямую не получится.

---

## 🧳 Передавай явно

Сервисному объекту передай пользователя как аргумент:

```ruby
GenerateReport.new(user: current_user, report: report).call
```

Тогда зависимость видна в его интерфейсе:

```ruby
class GenerateReport
  def initialize(user:, report:)
    @user = user
    @report = report
  end

  def call
    Rails.logger.info("Report #{@report.id} requested by user #{@user.id}")
    ReportBuilder.new(@report).call
  end
end
```

Если работу выполняет фоновая задача, передай ей идентификаторы при постановке в очередь:

```ruby
CreateReportJob.perform_later(report.id, current_user.id)

class CreateReportJob < ApplicationJob
  def perform(report_id, user_id)
    report = Report.find(report_id)
    user = User.find(user_id)
    GenerateReport.new(user: user, report: report).call
  end
end
```

К моменту выполнения задачи запись может быть удалена: `find` тогда вызовет исключение. Решение — повторить задачу, пропустить её или обработать ошибку — зависит от требований к отчёту.

---

## 🔥 Что пойдёт не так

* В тесте сервиса без контроллера `current_user` сам собой не появится — пользователя нужно передать в тестируемый объект.
* В обработчике Kafka и в фоновой задаче нет контроллера с его `current_user`. Нужного пользователя или его идентификатор следует предусмотреть во входных данных.
* Объект пользователя не всегда подходит для передачи между процессами. Active Job умеет сериализовать сохранённые записи Active Record через GlobalID, но при выполнении задачи запись может уже отсутствовать. Для сообщений Kafka формат данных нужно определить отдельно.

---

## 🛡️ Альтернатива: context

Если нескольким компонентам нужны одни и те же данные, их можно объединить в объект контекста:

```ruby
context = { current_user: user }
SomeService.call(context: context)
```

Но и такой контекст нужно явно создать и передать. Он не решает сам по себе вопрос сериализации при отправке задачи или события. Если сервису нужен только пользователь, отдельный аргумент обычно понятнее.

---

## ✅ Вывод

Передавай пользователя явно туда, где он нужен, особенно если работа выходит за рамки запроса. Для фоновой задачи заранее определяй, какие данные передать и что делать, если к моменту выполнения пользователь уже недоступен.
