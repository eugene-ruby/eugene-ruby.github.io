В Ruby методы можно создавать и менять во время выполнения программы. При необходимости метод также можно получить как объект `Method` или `UnboundMethod`. В статье разберём четыре инструмента для работы с определениями методов: от генерации до удаления и создания псевдонимов. Главное — понимать, как они взаимодействуют с наследованием.

---

## 🧠 Теория: зачем это нужно?

Ruby позволяет **изменять классы и объекты во время выполнения программы**. Это полезно для:

- Генерации однотипных методов без копипасты.
- Настройки API классов и DSL.
- Создания псевдонимов для обратной совместимости.
- Удаления локального определения метода, чтобы снова использовать унаследованное.

Ошибки в метапрограммировании могут проявиться только при вызове затронутого метода, поэтому особенно важно проверять поведение с учётом наследования.

---

## 1️⃣ `define_method` — фабрика методов

**Что делает:** создаёт метод во время выполнения программы.

```ruby
class User
  attr_reader :role

  def initialize(role:)
    @role = role
  end

  [:admin, :moderator, :guest].each do |role|
    define_method("#{role}?") do
      self.role == role.to_s
    end
  end
end

user = User.new(role: 'admin')
user.admin? # => true
```

Блок, переданный `define_method`, захватывает значение `role` для каждой итерации.

**Где полезно:**
- Генерация методов проверки ролей, как в примере выше.
- Создание однотипных геттеров и сеттеров для динамических атрибутов.
- Реализация набора методов по известному шаблону.

**Антипаттерн:**
```ruby
# Имя зависит от случайного числа, а назначение метода неясно
 define_method("unused_#{rand(100)}") { nil }
```

Такие методы трудно найти и использовать предсказуемо; случайное имя может совпасть с уже существующим.

## 2️⃣ `remove_method` — хирургическое удаление

**Что делает:** удаляет определение метода из текущего класса или модуля. Если метод есть у предка, после удаления станет доступна его реализация.

```ruby
class Parent
  def deprecated_method
    "Родительская реализация"
  end
end

class Child < Parent
  def deprecated_method
    "Переопределение в Child"
  end

  remove_method :deprecated_method
end

Child.new.deprecated_method # => "Родительская реализация"
```

Если метод определён **только у предка**, `remove_method` вызовет `NameError`: в текущем классе нечего удалять. Если нужно заблокировать поиск метода у предков, используйте `undef_method`.

**Где полезно:**
- Удаление локального переопределения с возвратом к реализации предка.
- Отмена метода, добавленного в конкретный класс, если вы контролируете этот код и понимаете последствия для вызовов.

**Опасность:**
```ruby
class String
  remove_method :upcase
end
# Вызовы upcase у строк перестанут работать, если метод не найден у предков
```

Изменение базового класса затронет весь код, который рассчитывает на этот метод.

---

## 3️⃣ `undef_method` — блокировка поиска у предков

**Что делает:** помечает метод как неопределённый в текущем классе или модуле. Обычный поиск метода на этом месте остановится, даже если реализация есть у предка.

```ruby
class Security
  undef_method :instance_eval
end

Security.new.instance_eval {} # => NoMethodError
```

Это ограничивает обычный вызов `instance_eval` у экземпляра `Security`, но **не создаёт безопасную песочницу**: Ruby-код, которому доступны другие способы вызова или переопределения методов, нельзя изолировать одним `undef_method`.

**Где полезно:**
- Исключение унаследованного метода из API класса.
- Запрет обычного вызова конкретного метода у экземпляров подкласса.

**Разница с `remove_method`:**
```ruby
class A
  def m
    "A#m"
  end
end

class B < A
  def m
    "B#m"
  end

  remove_method :m
end
B.new.m # => "A#m"

class C < A
  undef_method :m
end
C.new.m # => NoMethodError
```

## 4️⃣ `alias_method` — псевдоним метода

**Что делает:** создаёт новое имя для существующего определения метода.

```ruby
class User
  def display_name
    "Гость"
  end

  alias_method :name, :display_name
end

User.new.name # => "Гость"
```

**Где полезно:**
- Поддержка старого имени метода после изменения API.
- Предоставление второго имени для того же поведения.
- Сохранение прежней реализации перед её переопределением, если порядок определений находится под вашим контролем.

Не стоит делать `save!` простым псевдонимом `save`, если по соглашению вашего API метод с `!` должен вести себя иначе: псевдоним не добавляет никакой новой логики.

**Ловушка:**
```ruby
class Example
  def old_name
    "Старая реализация"
  end

  alias_method :new_name, :old_name

  def old_name
    "Новая реализация"
  end
end

Example.new.new_name # => "Старая реализация"
Example.new.old_name # => "Новая реализация"
```

`alias_method` связывает новое имя с определением, доступным **в момент создания псевдонима**. Последующее переопределение исходного имени не обновляет псевдоним.

## 🔥 Реальный кейс: динамический API-клиент

Ниже — схема клиента с общим обработчиком запросов. `send_request` возвращает данные вызова для наглядности; сетевых запросов пример не делает.

```ruby
class ApiClient
  HTTP_METHODS = [:get, :post, :put, :delete]

  HTTP_METHODS.each do |method|
    define_method(method) do |path, **params|
      send_request(method.upcase, path, params)
    end

    alias_method "#{method}_request", method
  end

  private

  def send_request(verb, path, params)
    [verb, path, params]
  end
end

client = ApiClient.new
client.get("/users") # => ["GET", "/users", {}]
client.post_request("/login", email: "test@test.com")
# => ["POST", "/login", { email: "test@test.com" }]
```

## 🧪 Тестирование динамических методов

Тест проверяет, что оба имени доступны и для одинаковых аргументов дают одинаковый результат:

```ruby
RSpec.describe ApiClient do
  described_class::HTTP_METHODS.each do |method|
    it "responds to #{method}" do
      expect(subject).to respond_to(method)
    end

    it "handles #{method} and #{method}_request the same way" do
      expect(subject.public_send("#{method}_request", "/users"))
        .to eq(subject.public_send(method, "/users"))
    end
  end
end
```

Такой тест проверяет поведение, но сам по себе не доказывает, что второе имя создано именно через `alias_method`.

## 💀 Опасные практики

1. **Бесконтрольная генерация методов** — число созданных методов растёт вместе с входными данными:
   ```ruby
   names.each { |name| define_method(name) { nil } }
   ```
   Если набор имён велик или меняется непредсказуемо, это усложняет отладку и расходует память.

2. **Удаление не в том классе:**
   ```ruby
   class Product < Item
     remove_method :name # NameError, если name определён только в Item
   end
   ```

3. **Устаревший псевдоним** — исходное имя переопределили после вызова `alias_method`, а псевдоним продолжает вызывать прежнюю реализацию.

---

## 🎯 Когда это действительно нужно

| Метод | Подходящие случаи применения |
|---|---|
| `define_method` | Генерация однотипных методов |
| `remove_method` | Удаление локального определения, в том числе для возврата к реализации предка |
| `undef_method` | Блокировка обычного поиска унаследованного метода |
| `alias_method` | Второе имя для существующего определения, обратная совместимость |

---

## 🧾 Вывод

1. **`define_method`** помогает создавать однотипные методы без копипасты.
2. **`remove_method`** удаляет локальное определение и может открыть доступ к методу предка; **`undef_method`** останавливает поиск у предков.
3. **`alias_method`** сохраняет под новым именем определение метода, доступное на момент вызова.

Если задачу можно ясно решить обычными методами, начните с них. Динамическое изменение методов полезно, когда оно действительно упрощает API, а его последствия для наследования и вызовов понятны.
