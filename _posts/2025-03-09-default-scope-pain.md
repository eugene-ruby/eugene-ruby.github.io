`default_scope` кажется удобным способом избавиться от повторяющегося фильтра. Но условие применяется не только там, где ты его ожидаешь: оно влияет на обычные запросы, связи и тесты.

---

## 😇 Наивное использование

```ruby
class User < ApplicationRecord
  default_scope { where(active: true) }
end
```

Кажется, ты избавился от дублирования. Теперь `User.all` возвращает только активных пользователей.

---

## 💥 А потом приходит боль

### 📌 Тесты не видят «неактивных»

```ruby
User.create!(active: false)
expect(User.count).to eq(1) # В чистой базе будет 0
```

Запись создана, но `User.count` учитывает только пользователей с `active: true`. Если тесту нужны все записи, можно явно снять область видимости: `User.unscoped.count`.

### 📌 Админка не показывает «всех»

Ты написал `User.all`, ожидая получить всех пользователей. Неактивные записи в выборку не попадут; для такого запроса нужен `User.unscoped`.

### 📌 Сложность с JOIN и merge

```ruby
Company.joins(:users).merge(User.all)
# Условие active: true попадает в запрос неявно
```

`User.all` уже содержит условие из `default_scope`. Кроме того, область видимости модели может применяться при запросах через связь `:users`. Поэтому, разбираясь в результате JOIN, нужно учитывать не только явно написанные условия, но и область видимости связанной модели.

---

## 🧯 Обходы и костыли

Ты начинаешь:

* использовать `unscoped`, когда нужны скрытые записи;
* искать источник неожиданного условия в SQL;
* разбираться, почему `merge` добавил фильтр.

`unscoped` помогает, но снимает все условия `default_scope` у модели, а не только `active: true`. Если их несколько, это важно учитывать.

---

## 🔍 Что делать вместо?

Если фильтр нужен не для каждого запроса, используй явный **scope**:

```ruby
class User < ApplicationRecord
  scope :active, -> { where(active: true) }
end

User.active
```

Так по вызову видно, где нужны только активные пользователи. Для типового списка можно сделать отдельный метод запроса; переопределять `.all` ради фильтра не стоит — это снова скроет условие от вызывающего кода.

---

## 🚨 TL;DR

| Проблема | Причина |
| --- | --- |
| Невидимые записи | `default_scope` добавляет `where` к запросам |
| Неожиданный результат теста | `User.count` считает только записи в области видимости |
| Неожиданный фильтр в JOIN или `merge` | Условие модели применяется неявно |

**Итог:** `default_scope` подходит лишь тогда, когда неявный фильтр действительно нужен почти во всех запросах к модели и его влияние на связи понятно. Если регулярно требуются и активные, и все пользователи, явный `scope` проще контролировать.
