В PostgreSQL асинхронная и синхронная физическая репликация различаются тем, ждёт ли основной сервер подтверждения от реплики при коммите [1]. Логическая репликация отличается способом передачи данных: она передаёт изменения выбранных таблиц, а не физическую копию экземпляра. При этом ожидание реплики можно настроить и для логической репликации [1], [2]. Разберём особенности этих подходов и сценарии их применения.

---

## 🔁 Асинхронная репликация

Для потоковой физической репликации это режим по умолчанию [1].

* **Коммит не ждёт реплику**, поэтому её задержка не увеличивает время подтверждения транзакции из-за ожидания репликации [1].
* При переключении на отстающую реплику **можно потерять последние подтверждённые транзакции**. Объём потери зависит от её отставания на момент переключения [1].
* Подходит для реплик, обслуживающих запросы на чтение, и для снятия резервных копий с реплики [1].

Пример фрагмента настройки на реплике: `primary_conninfo` задаёт подключение к основному серверу. Для рабочего подключения могут потребоваться и другие параметры, в частности пользователь и данные для аутентификации [3].

```conf
primary_conninfo = 'host=... application_name=replica'
```

📌 Используй, если допустима потеря последних изменений при переключении на реплику.

---

## 🧷 Синхронная репликация

* **Основной сервер ждёт подтверждения от синхронной реплики** перед подтверждением коммита. Что именно должна подтвердить реплика, зависит от настройки `synchronous_commit` [4].
* При стандартном значении `synchronous_commit = on` коммит подтверждается после записи WAL на долговременное хранилище синхронной реплики. Это не означает, что изменение уже видно в запросах на реплике: для ожидания применения WAL нужен режим `remote_apply` [4].
* **Увеличивает задержку записи**, поскольку коммит ждёт ответа реплики. Если необходимая реплика недоступна, коммиты могут ожидать её восстановления или изменения конфигурации [1].

На основном сервере имя в `synchronous_standby_names` должно совпадать с `application_name` реплики из примера выше [3]. После `ALTER SYSTEM` нужно перечитать конфигурацию, например вызвав `SELECT pg_reload_conf();` [5].

```sql
ALTER SYSTEM SET synchronous_standby_names = 'replica';
```

📌 Используй, когда важно снизить риск потери подтверждённых транзакций при переключении на реплику и допустима дополнительная задержка. Настройка защищает именно те коммиты, для которых включено ожидание синхронной реплики [3].

## 🧬 Логическая репликация

* Передаёт **изменения данных выбранных таблиц**, а не физическую копию экземпляра [2].
* Позволяет **выбирать таблицы** для публикации и может использоваться между **разными основными версиями PostgreSQL** с учётом ограничений совместимости [2], [6].
* Подходит для **миграций и передачи изменений** в другие системы. Задержка применения изменений зависит от нагрузки и состояния подписчика. Схема таблиц и команды DDL автоматически не реплицируются — при миграции их нужно учитывать отдельно [2], [7].

Команда создаёт публикацию для таблицы `users`, но сама по себе не запускает репликацию: для получения изменений нужна подписка [6].

```sql
CREATE PUBLICATION my_pub FOR TABLE users;
```

📌 Используй, когда нужно реплицировать выбранные таблицы или физическая репликация не подходит.

## ⚖️ Таблица сравнения

| Параметр | Асинхронная физическая | Синхронная физическая | Логическая |
| --- | --- | --- | --- |
| Риск потери последних изменений при переключении | Есть при отставании реплики | Снижен для коммитов, подтверждённых синхронной репликой | Зависит от отставания подписчика и сценария переключения |
| Влияние реплики на задержку коммита | Не ждёт реплику | Ждёт подтверждения реплики при соответствующей настройке | Обычно не ждёт применения изменений подписчиком; при синхронной настройке с `remote_apply` ждёт [1], [4] |
| Разные основные версии PostgreSQL | Обычно не поддерживаются [1] | Обычно не поддерживаются [1] | Возможны с учётом совместимости [2] |
| Запросы на чтение на принимающей стороне | Да | Да | Да, для реплицируемых таблиц |
| Передача выбранных таблиц | Нет | Нет | Да [6] |

## 🔚 Вывод

Выбор зависит от задачи:

* Важна скорость коммита и допустимо отставание реплики → **асинхронная репликация**.
* Нужно подтверждение записи WAL на реплике до завершения коммита → **синхронная репликация** с подходящей настройкой `synchronous_commit`.
* Нужно передавать выбранные таблицы или выполнить миграцию между совместимыми версиями → **логическая репликация**.
