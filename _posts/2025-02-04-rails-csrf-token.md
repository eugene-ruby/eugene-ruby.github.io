Каждый Rails-разработчик встречал `authenticity_token` в формах. Обычно Rails добавляет его сам, но при ручной отправке запросов или настройке API легко столкнуться с ошибкой проверки. Разберёмся, от какой атаки защищает токен и когда с ним нужно работать вручную.

---

## 🔐 Что такое CSRF?

**CSRF (Cross-Site Request Forgery)** — это атака, при которой злоумышленник заставляет браузер пользователя отправить нежелательный запрос в приложение, где пользователь уже авторизован.

Пример сценария:
1. Вы вошли в интернет-банк.
2. Переходите на вредоносный сайт. Он пытается отправить форму с POST-запросом на перевод денег.
3. Если браузер приложит к запросу сессионные куки, а банк не проверит происхождение запроса, операция может выполниться от вашего имени.

Отправятся ли куки, зависит в том числе от их настроек и политики браузера. Но приложение не должно полагаться только на эти ограничения.

---

## 🛡️ Как Rails защищается от CSRF?

Rails проверяет **authenticity_token** в запросах, которые могут менять данные. Токен связан с сессией пользователя; значение, переданное в конкретной форме, не обязательно совпадает с исходным значением в сессии. Браузер злоумышленника может попытаться отправить запрос с куками пользователя, но не может прочитать токен со страницы приложения и подставить его в свою форму.

Для форм, созданных Rails-хелперами, скрытое поле обычно добавляется автоматически:

```html
<form action="/posts" method="post">
  <input type="hidden" name="authenticity_token" value="k3j5h...">
  <!-- остальные поля -->
</form>
```

Если обязательный токен отсутствует или не проходит проверку, при стратегии защиты `:exception` Rails отклоняет запрос с `ActionController::InvalidAuthenticityToken`. GET- и HEAD-запросы такую проверку не проходят, поэтому они не должны изменять данные.

---

## 🔧 Как это работает под капотом?

1. **Генерация токена.** Rails предоставляет `form_authenticity_token`, но при использовании обычных хелперов форм вызывать его в контроллере не нужно. Токен для формы может быть замаскирован или привязан к конкретной форме, поэтому не стоит рассчитывать на побайтовое совпадение токенов из разных форм.
2. **Передача токена.** Форма отправляет его в параметре `authenticity_token`. JavaScript-запрос может передать токен в заголовке `X-CSRF-Token`.
3. **Проверка.** `ActionController::RequestForgeryProtection` проверяет токен для запросов, меняющих состояние. Это не отдельное правило для JSON API: необходимость защиты зависит прежде всего от того, отправляет ли браузер учётные данные автоматически, например сессионные куки.

## 💥 Типичные проблемы и решения

### 1. "У меня API — зачем мне CSRF?"
Если API **не использует автоматически отправляемые браузером учётные данные** и принимает, например, только токен авторизации, который клиент явно передаёт в заголовке, CSRF-защита для таких запросов обычно не нужна. Отключайте её только в контроллерах, для которых это условие выполняется:

```ruby
class ApiController < ActionController::Base
  skip_forgery_protection
end
```

Если тот же API принимает сессионные куки, это исключение уже небезопасно: запрос от чужого сайта тоже может прийти с учётными данными пользователя.

### 2. "Токен сломал мои тесты"
Сначала проверьте, включена ли CSRF-защита в тестовом окружении: в типичной конфигурации Rails она там отключена. Если проверка включена намеренно, создавайте тестовый запрос с токеном, полученным для той же сессии, и передавайте его в параметре `authenticity_token` или заголовке `X-CSRF-Token`. Само по себе `as: :json` проверку не обходит.

### 3. "Форма рендерится через Turbo Stream"
Turbo Stream не требует отдельного поля для CSRF. Если форма создана через `form_with`, Rails добавляет нужное скрытое поле для запроса, меняющего данные, даже когда форму рендерят через `render partial: 'form'`:

```erb
<%= form_with(model: @post) do |form| %>
  <!-- поля формы -->
<% end %>
```

Добавлять `form.hidden_field :authenticity_token` не нужно: это создаст поле модели, а не замену штатному параметру `authenticity_token`. Если форма собрана вручную, убедитесь, что токен передаётся в ожидаемом Rails параметре.

## ⚠️ Опасные антипаттерны

### ❌ Глобальное отключение защиты
```ruby
# config/application.rb
config.action_controller.default_protect_from_forgery = false
```

Не отключайте проверку для всего приложения, если его контроллеры работают с браузерными сессиями. Исключение для API без такой аутентификации лучше ограничить соответствующими контроллерами.

### ❌ Передача токена в URL
```ruby
link_to "Удалить", post_path(@post, authenticity_token: form_authenticity_token), method: :delete
```
Токен в URL может попасть в историю браузера или логи. Передавайте его в теле запроса или заголовке.

### ❌ Использование одного токена для всех пользователей
```ruby
# Не делайте так!
def form_authenticity_token
  "static_token"
end
```

Общий статический токен не подтверждает, что запрос создан в контексте сессии пользователя.

## 🛠️ Правильная работа с токенами

### Для AJAX-запросов:
Если страница и запрос относятся к одному Rails-приложению, добавьте в layout `<%= csrf_meta_tags %>` и прочитайте токен из метатега:

```javascript
const token = document.querySelector('meta[name="csrf-token"]').content;

fetch('/posts', {
  method: 'POST',
  headers: {
    'X-CSRF-Token': token
  }
});
```

Для запроса к тому же источнику `fetch` по умолчанию отправляет учётные данные. Если JavaScript-клиент расположен на другом источнике, этот пример нельзя перенести без изменений: ему нужен безопасный способ получить токен и отдельная настройка отправки учётных данных.

### Для API с сессиями:
Сохраняйте CSRF-проверку для запросов, которые браузер отправляет с сессионными куки. Если клиент работает на страницах того же Rails-приложения, используйте `csrf_meta_tags` и заголовок `X-CSRF-Token`, как в примере выше. Для отдельного фронтенда продумайте выдачу токена клиенту вместе с настройками CORS, куки и отправки учётных данных. Просто положить токен в доступную JavaScript куку — не универсальная замена этой настройке.

## 🎯 Вывод

`authenticity_token` помогает Rails отличать запросы, созданные приложением, от попыток отправить действие от имени пользователя с другого сайта. В формах Rails обычно передаёт токен сам. В ручных JavaScript-запросах его нужно передать явно, а перед отключением проверки для API — убедиться, что браузер не авторизует запрос автоматически.
