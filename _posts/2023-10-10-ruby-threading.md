Ruby позволяет работать с потоками, но в MRI есть важное ограничение: Global VM Lock (GVL) не даёт нескольким потокам одновременно исполнять Ruby-код. Поэтому потоки полезны, когда программа ждёт сеть, файл или базу данных, но обычно не ускоряют вычисления на нескольких ядрах. Разберём примеры, синхронизацию и варианты для CPU-задач.

---

## 🚧 Что такое GIL?

**GIL** — Global Interpreter Lock; в MRI Ruby этот механизм называется **GVL** (Global VM Lock). Он **не даёт двум потокам одновременно исполнять Ruby-код**. При этом некоторые операции ожидания и нативные расширения могут освобождать GVL, пока работают.

---

## 🤔 Тогда зачем вообще потоки?

- Они **полезны при I/O**: чтении файлов, сетевых запросах, ожидании ответа БД. Пока один поток ждёт, другой может продолжать работу.
- Потоки выполняются **конкурентно**, но в MRI обычно не исполняют Ruby-код параллельно на нескольких ядрах.
- Они подходят и для других задач с ожиданием, например `sleep`. Сетевые операции через `open-uri` или `Net::HTTP` — более практичные примеры.

---

## 🧪 Пример: работает с I/O

Здесь `sleep` имитирует ожидание: сам по себе он не выполняет I/O.

```ruby
threads = []

3.times do |i|
  threads << Thread.new do
    puts "Start #{i}"
    sleep 1
    puts "End #{i}"
  end
end

threads.each(&:join)
```

Ожидания могут перекрываться, поэтому три вызова `sleep 1` не обязаны занимать три секунды подряд. Это не означает, что три потока одновременно исполняют Ruby-код.

---

## 🧨 Пример: не работает с CPU

```ruby
threads = []

3.times do
  threads << Thread.new do
    10_000_000.times { Math.sqrt(1234) }
  end
end

threads.each(&:join)
```

Для такой вычислительной работы потоки MRI обычно не дают ускорения за счёт нескольких ядер: Ruby-код выполняется под GVL, а создание и переключение потоков добавляет накладные расходы. Утверждать, что этот пример непременно будет медленнее однопоточного варианта, нельзя без сравнения в конкретных условиях. Отдельный случай — вычисления в нативном коде, который освобождает GVL.

---

## 🔐 Mutex и защита от гонок

```ruby
mutex = Mutex.new
counter = 0

threads = 10.times.map do
  Thread.new do
    1000.times do
      mutex.synchronize { counter += 1 }
    end
  end
end

threads.each(&:join)
puts counter  # => 10000
```

`counter += 1` читает значение и записывает новое. `Mutex` защищает эту операцию, когда к счётчику обращаются несколько потоков. Не стоит считать GVL заменой синхронизации: если убрать `Mutex`, результат может зависеть от реализации Ruby и переключений потоков, хотя именно этот короткий пример в MRI может по-прежнему вывести `10000`.

---

## 📦 Queue — потокобезопасная очередь

```ruby
q = Queue.new

producer = Thread.new do
  5.times { |i| q << i }
  q << :done
end

consumer = Thread.new do
  loop do
    val = q.pop
    break if val == :done
    puts "Got #{val}"
  end
end

[producer, consumer].each(&:join)
```

`Queue` — встроенная потокобезопасная структура для передачи данных между потоками. В этом примере `:done` сообщает потребителю, что элементы закончились.

---

## 🧠 Так как же делать параллельность?

* Для CPU-задач в MRI можно использовать **отдельные процессы**: например, через `fork` там, где он доступен, `Process.spawn` или библиотеку `Parallel`. У процессов своя память, поэтому нужно продумать передачу данных и учитывать накладные расходы.
* Другой вариант — реализации Ruby без такого ограничения на параллельное исполнение потоков Ruby-кода, например **JRuby** или **TruffleRuby**.
* Вычислительную часть можно вынести за пределы MRI, если это оправдано задачей и сложностью взаимодействия между компонентами.

---

## ⚠️ На собеседовании могут спросить:

> «Как реализовать конкурентную загрузку 100 URL в MRI Ruby?»

Возможный ответ:

* Использовать `Thread` с `Net::HTTP` или `open-uri` либо подходящий клиент, например `Typhoeus`, `HTTPX` или `async`.
* Ограничить число одновременных запросов, предусмотреть тайм-ауты и обработку ошибок.
* Не путать ускорение за счёт перекрытия ожиданий с ускорением CPU-задач.

---

🔚 **Вывод:** потоки в MRI есть и помогают выполнять задачи конкурентно, особенно при ожидании I/O. GVL ограничивает параллельное исполнение Ruby-кода, но не отменяет ни пользы потоков, ни необходимости синхронизации общих данных.
