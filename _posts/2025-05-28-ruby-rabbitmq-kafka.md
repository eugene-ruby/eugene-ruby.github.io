## Введение: зачем нужны брокеры сообщений?

Представьте: Ruby-сервис получает множество запросов, и каждый требует отправить письмо, обновить аналитику и записать событие в лог. Если выполнять все эти действия синхронно, пользователям придётся ждать их завершения.

**RabbitMQ** и **Kafka** позволяют передавать такую работу другим компонентам. Но решают они разные задачи: RabbitMQ часто используют для очередей задач и маршрутизации сообщений, а Kafka — для потоков событий, которые могут читать несколько потребителей.

---

## RabbitMQ: брокер для очередей и маршрутизации

### Плюсы 🎯
- **Гибкость**: Очереди, маршрутизация и разные схемы доставки сообщений, включая публикацию и подписку.
- **Контроль обработки**: Потребитель может подтвердить получение сообщения после выполнения задачи.
- **Обработка ошибок**: Можно настроить повторную доставку и очереди для сообщений, которые не удалось обработать (dead letter queues).

### Минусы ⚠️
- **Не подходит для хранения истории событий**: После подтверждения обработки сообщение обычно удаляется из очереди.
- **Требует настройки под нагрузку**: Производительность зависит от размера сообщений, конфигурации брокера и потребителей.

### Когда использовать с Ruby?
```ruby
# Типичный пример: фоновые задачи в Rails
class UserNotifier
  include Sneakers::Worker
  from_queue 'user_emails'

  def work(message)
    user = User.find(JSON.parse(message)['user_id'])
    UserMailer.welcome(user).deliver_now
    ack! # Подтверждаем обработку
  end
end
```
**Подходит для:**
- Очередей фоновых задач
- Фоновой отправки писем и SMS
- Обмена сообщениями между сервисами

## Kafka: платформа для потоков событий

### Плюсы 🚀
- **Пропускная способность**: Подходит для обработки больших потоков событий.
- **Хранение событий**: Сообщения сохраняются в течение настроенного срока, и потребители могут прочитать их повторно.
- **Масштабирование**: Нагрузку можно распределять между брокерами и потребителями.

### Минусы ⚠️
- **Сложность эксплуатации**: Развёртывание и сопровождение обычно требуют больше усилий, чем для простой очереди задач.
- **Избыточность для небольших задач**: Если нужна только фоновая обработка отдельных заданий, возможности Kafka могут не понадобиться.

### Пример Ruby + Kafka:
```ruby
# Отправка событий в Kafka
WaterDrop.setup do |config|
  config.deliver = true
  config.kafka = { 'bootstrap.servers': 'localhost:9092' }
end

event = {
  user_id: 42,
  event: 'purchase',
  amount: 99.99,
  timestamp: Time.now.utc.iso8601
}

WaterDrop::SyncProducer.call(event.to_json, topic: 'user_events')
```
**Подходит для:**
- Аналитики на основе потоков событий
- Сбора действий пользователей
- Передачи событий нескольким сервисам

## Сравнение: RabbitMQ и Kafka

| Параметр        | RabbitMQ                          | Kafka                              |
|-----------------|-----------------------------------|------------------------------------|
| **Основная задача** | Очереди и маршрутизация сообщений | Хранение и обработка потоков событий |
| **Повторное чтение** | Обычно недоступно после подтверждения обработки | Возможно в пределах срока хранения |
| **Масштабирование** | Зависит от конфигурации и сценария | Рассчитана на распределённую обработку потоков |
| **Данные**      | Хранятся до обработки согласно настройкам | Хранятся в течение настроенного срока |
| **Ruby-гемы**   | bunny, sneakers                   | rdkafka, racecar                   |
| **Когда использовать** | Задачи, уведомления, маршрутизация | Потоки событий, аналитика, повторное чтение |

## Практика: что выбрать?

**Выбирайте RabbitMQ, если:**
- Нужны очереди фоновых задач
- Требуется маршрутизировать сообщения или настроить очередь для ошибок обработки
- Сообщения не нужно перечитывать после подтверждения обработки

**Выбирайте Kafka, если:**
- Один поток событий должны независимо обрабатывать несколько групп потребителей
- Нужно хранить события и перечитывать их
- Требуется обрабатывать большой поток событий

---

## Антипаттерны: когда стоит пересмотреть выбор

### Для RabbitMQ:
- **Хранить историю событий**: Для длительного хранения и повторного чтения обработанных сообщений лучше выбрать другое решение.
- **Передавать большие сообщения без оценки затрат**: Их размер влияет на производительность и потребление ресурсов.
- **Усложнять маршрутизацию без необходимости**: Правила становится трудно сопровождать, если логика обмена чрезмерно разрастается.

### Для Kafka:
- **Использовать в небольшом проекте без потребности в потоках событий**: Затраты на эксплуатацию могут не оправдаться.
- **Использовать только как очередь отдельных задач**: Модель хранения и обработки Kafka отличается от модели брокера задач.
    > ⚠️ Сначала проверьте, нужна ли вам история событий и независимые потребители.

---

## Заключение: очередь или поток событий?

Если нужно передавать задачи обработчикам и маршрутизировать сообщения, рассмотрите RabbitMQ. Если события должны храниться и быть доступны нескольким независимым потребителям, рассмотрите Kafka.

Не стоит выбирать инструмент только по ожидаемому объёму сообщений: важны также требования к обработке, повторному чтению и сопровождению системы.

---

## Чек-лист выбора

Выберите RabbitMQ, если:
- ✅ Нужны очереди задач
- ✅ После подтверждения обработки сообщения не требуется перечитывать
- ✅ Важна гибкая маршрутизация

Выберите Kafka, если:
- ✅ Поток событий нужен нескольким независимым потребителям
- ✅ Нужна история событий и возможность повторного чтения
- ✅ Требуется обрабатывать большой поток данных

Лучший инструмент — тот, который отвечает требованиям вашей задачи, а не тот, что в тренде 😉
