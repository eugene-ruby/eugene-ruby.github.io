RabbitMQ и Kafka позволяют вынести часть работы из синхронного запроса Ruby-сервиса, но используют разные модели. Сравним очереди с подтверждением обработки и потоки событий с возможностью повторного чтения, чтобы понять, какой вариант подходит задаче.

## Введение: зачем нужны брокеры сообщений?

Представьте: Ruby-сервис получает множество запросов, и каждый требует отправить письмо, обновить аналитику и записать событие. Если выполнять всё синхронно, пользователям придётся ждать завершения этих действий.

**RabbitMQ** часто используют для очередей задач и маршрутизации сообщений [1], а **Kafka** — для потоков событий, которые могут независимо читать несколько групп потребителей [2]. ([rabbitmq.com](https://www.rabbitmq.com/docs/exchanges))

---

## RabbitMQ: брокер для очередей и маршрутизации

### Плюсы 🎯
- **Гибкость**: очереди и обменники позволяют настраивать разные схемы маршрутизации, в том числе публикацию для нескольких получателей [1].
- **Контроль обработки**: потребитель может подтвердить сообщение после выполнения задачи [3].
- **Обработка ошибок**: можно настроить повторную доставку и маршрутизацию сообщений в очередь для ошибок обработки (dead-letter queue) [3], [4]. ([rabbitmq.com](https://www.rabbitmq.com////////////////////docs/confirms?utm_source=openai))

### Минусы ⚠️
- **Не подходит для повторного чтения обработанных сообщений из той же обычной очереди**: после подтверждения сообщение удаляется из неё [3].
- **Требует настройки под нагрузку**: производительность зависит от размера сообщений, конфигурации брокера и потребителей [3], [7].

### Когда использовать с Ruby?
```ruby
# Типичный пример: фоновая задача в Rails
class UserNotifier
  include Sneakers::Worker
  from_queue 'user_emails'

  def work(message)
    user = User.find(JSON.parse(message)['user_id'])
    UserMailer.welcome(user).deliver_now
    ack! # Подтверждаем сообщение после отправки письма
  end
end
```

В примере используется воркер Sneakers с ручным подтверждением [5]. Подтверждение не делает отправку письма атомарной вместе с обработкой сообщения. Если воркер отправит письмо, но завершится до `ack!`, неподтверждённое сообщение при закрытии соединения может быть доставлено повторно [3]. Для задач, где повторное действие нежелательно, предусмотрите защиту от дублей. Поведение при ошибке до подтверждения, включая повторные попытки и отправку в dead-letter queue, зависит от настроек потребителя и RabbitMQ [3], [4]. ([github.com](https://github.com/jondot/sneakers?utm_source=openai))

**Подходит для:**
- Очередей фоновых задач
- Фоновой отправки писем и SMS
- Обмена сообщениями между сервисами

## Kafka: платформа для потоков событий

### Плюсы 🚀
- **Пропускная способность**: подходит для обработки больших потоков событий [2].
- **Хранение событий**: записи остаются доступными в пределах настроенных ограничений хранения; их можно прочитать повторно [2], [6].
- **Масштабирование**: нагрузку можно распределять между брокерами и потребителями [2].

### Минусы ⚠️
- **Сложность эксплуатации**: развёртывание и сопровождение обычно требуют больше усилий, чем для простой очереди задач.
- **Избыточность для небольших задач**: если нужна только фоновая обработка отдельных заданий, возможности Kafka могут не понадобиться.

### Пример Ruby + Kafka:
```ruby
# Отправка события в Kafka через WaterDrop
producer = WaterDrop::Producer.new do |config|
  config.deliver = true
  config.kafka = { 'bootstrap.servers': 'localhost:9092' }
end

event = {
  user_id: 42,
  event: 'purchase',
  amount: 99.99,
  timestamp: Time.now.utc.iso8601
}

producer.produce_sync(payload: event.to_json, topic: 'user_events')
producer.close
```

В примере использован API `WaterDrop::Producer`: в отличие от исходного вызова `WaterDrop::SyncProducer.call`, он соответствует документированному способу синхронной публикации [8]. Пример показывает публикацию события, а не его обработку. Повторное чтение зависит от того, сохранились ли записи в Kafka; фиксация позиции потребителя не удаляет их из топика [2], [6]. ([karafka.io](https://karafka.io/docs/code/waterdrop/WaterDrop/ConnectionPool.html))

**Подходит для:**
- Аналитики на основе потоков событий
- Сбора действий пользователей
- Передачи событий нескольким сервисам

## Сравнение: RabbitMQ и Kafka

| Параметр | RabbitMQ | Kafka |
|---|---|---|
| **Основная задача** | Очереди и маршрутизация сообщений [1] | Хранение и обработка потоков событий [2] |
| **Повторное чтение** | Обычно недоступно из той же обычной очереди после подтверждения [3]; для повторного чтения у RabbitMQ есть streams [9] | Возможно, пока записи доступны согласно настройкам хранения [2], [6] |
| **Масштабирование** | Зависит от конфигурации и сценария | Рассчитана на распределённую обработку потоков [2] |
| **Данные** | Сообщения остаются в обычной очереди до удаления согласно настройкам и подтверждениям [3] | Записи хранятся согласно настроенным ограничениям [6] |
| **Ruby-гемы** | bunny, sneakers [5] | rdkafka, racecar, waterdrop [8] |
| **Когда использовать** | Задачи, уведомления, маршрутизация | Потоки событий, аналитика, повторное чтение |

RabbitMQ streams — отдельная модель хранения с повторным чтением. Поэтому противопоставление «RabbitMQ не умеет перечитывать сообщения, а Kafka умеет» верно только для сравнения обычных очередей RabbitMQ с топиками Kafka [9]. ([rabbitmq.com](https://www.rabbitmq.com/docs/streams))

## Практика: что выбрать?

**Выбирайте RabbitMQ, если:**
- Нужны очереди фоновых задач.
- Требуется маршрутизировать сообщения или настроить обработку ошибок.
- Сообщения не нужно перечитывать из обычной очереди после подтверждения.

**Выбирайте Kafka, если:**
- Один поток событий должны независимо обрабатывать несколько групп потребителей [2].
- Нужно хранить события и перечитывать их в пределах настроенных ограничений хранения [6].
- Требуется обрабатывать большой поток событий.

---

## Антипаттерны: когда стоит пересмотреть выбор

### Для RabbitMQ:
- **Хранить историю событий в рабочей очереди**: для длительного хранения и повторного чтения обработанных сообщений рассмотрите другую модель, в том числе RabbitMQ streams [9].
- **Передавать большие сообщения без оценки затрат**: их размер влияет на производительность и потребление ресурсов [7].
- **Усложнять маршрутизацию без необходимости**: правила становится трудно сопровождать, если логика обмена чрезмерно разрастается.

### Для Kafka:
- **Использовать в небольшом проекте без потребности в потоках событий**: затраты на эксплуатацию могут не оправдаться.
- **Использовать только как очередь отдельных задач**: модель хранения и обработки Kafka отличается от модели брокера задач. Сначала проверьте, нужны ли вам история событий и независимые группы потребителей.

---

## Заключение: очередь или поток событий?

Если нужно передавать задачи обработчикам и маршрутизировать сообщения, рассмотрите RabbitMQ. Если события должны сохраняться для нескольких независимых групп потребителей и повторного чтения, рассмотрите Kafka. При этом RabbitMQ streams тоже поддерживают повторное чтение [9].

Не стоит выбирать инструмент только по ожидаемому объёму сообщений: важны также требования к обработке, хранению и сопровождению системы.

---

## Чек-лист выбора

Выберите RabbitMQ, если:
- ✅ Нужны очереди задач.
- ✅ После подтверждения сообщения не требуется перечитывать из обычной очереди.
- ✅ Важна гибкая маршрутизация.

Выберите Kafka, если:
- ✅ Поток событий нужен нескольким независимым группам потребителей.
- ✅ Нужны хранение событий и возможность повторного чтения.
- ✅ Требуется обрабатывать большой поток данных.
