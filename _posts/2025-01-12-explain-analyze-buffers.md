PostgreSQL помогает разбираться с медленными SQL-запросами с помощью `EXPLAIN`. Опция `ANALYZE` показывает, что произошло при выполнении запроса, а `BUFFERS` — сколько блоков было затронуто. Это полезно и в Rails-приложении, и при разборе нагрузки на базу данных в целом.

---

`EXPLAIN (ANALYZE, BUFFERS)` помогает понять, **где запрос тратит время** и как работает с буферами. Но план нужно читать вместе с фактическим числом строк и повторений узлов: один `Seq Scan` или большой счётчик `read` сами по себе ещё не диагноз.

## 🚀 Пример

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE id IN (
  SELECT user_id FROM posts WHERE published = true
);
```

`ANALYZE` действительно выполняет запрос. Для этого `SELECT` данные не изменятся, но с запросами, меняющими данные, будьте осторожны.

---

## 📊 Что показывает план?

Для запроса выше возможен, например, такой *сокращённый* фрагмент плана. Конкретный план зависит от данных, статистики и доступных индексов:

```text
Nested Loop  (cost=... rows=... width=...)
  -> HashAggregate
       Group Key: posts.user_id
       -> Seq Scan on posts
            Filter: published
  -> Index Scan using users_pkey on users
       Index Cond: (id = posts.user_id)
```

* `Nested Loop` — соединение, при котором внутренний узел выполняется для строк внешнего узла.
* `Seq Scan` — последовательный просмотр таблицы; условие `Filter` отбрасывает неподходящие строки.
* `HashAggregate` — здесь устраняет повторяющиеся `user_id` перед поиском пользователей.
* `Index Scan` — поиск строк с помощью индекса.

В полном выводе с `ANALYZE` сравнивайте ожидаемое число строк (`rows` рядом с `cost`) с фактическим (`actual ... rows`) и смотрите на `loops`: именно они помогают заметить, что внутренний узел выполнялся много раз.

---

## 📦 BUFFERS

В выводе может встретиться строка:

```text
Buffers: shared hit=124 read=8 dirtied=0 written=0
```

Значения — **количество блоков**, а не число строк или миллисекунды:

* **hit=124** — блоки найдены в буферном кеше PostgreSQL (`shared_buffers`).
* **read=8** — блоки загружены в этот кеш. Это не обязательно физическое чтение с диска: данные могли находиться в кеше операционной системы.
* **dirtied/written** — блоки, изменённые или записанные в ходе работы узла; даже `SELECT` может сопровождаться такой активностью.

По одному `read` нельзя заключить, что запрос тормозит из-за диска. Сопоставляйте счётчики со временем, числом строк и повторений узла. Не складывайте бездумно показатели родительского и дочерних узлов: в плане они могут включать одну и ту же работу.

---

## 💥 Почему Nested Loop — не всегда хорошо?

При `Nested Loop` внутренний узел выполняется для строк внешнего узла. Если таких строк много, повторные поиски через `Index Scan` могут стать дорогими — обратите внимание на `loops` и фактическое время.

Но для небольшого внешнего набора и подходящего индекса `Nested Loop` может быть удачным выбором. `Hash Join` не гарантирует ускорения: построение хеш-таблицы тоже требует ресурсов.

## 🛠 Что делать?

* Найти узел, на котором сосредоточена работа, и сравнить ожидаемое и фактическое число строк. Большое расхождение может указывать на проблему с оценками планировщика.
* Проверить, подходят ли индексы для условий отбора и соединения. Не создавать индекс только потому, что в плане есть `Seq Scan`: при большой доле подходящих строк он может быть выгоднее.
* Рассмотреть другую форму запроса, в том числе `JOIN`, если она сохраняет результат. Замена `IN` на `JOIN` может добавить дубликаты, когда одному пользователю соответствует несколько публикаций; сама по себе она не гарантирует другой или более быстрый план.
* Сравнить планы и фактическое время для вариантов запроса на характерных данных.

## 🤓 Полезные флаги

| Ключ        | Что даёт |
| ----------- | -------- |
| `ANALYZE`   | Выполняет запрос и показывает фактическое время, число строк и повторений узлов. |
| `BUFFERS`   | Показывает счётчики работы с буферами, в том числе попадания в кеш и чтения блоков. |
| `VERBOSE`   | Добавляет детали плана, например выходные столбцы узлов. |
| `COSTS OFF` | Скрывает оценки стоимости, числа строк и ширины строки; фактические показатели при `ANALYZE` остаются. |

---

## 🧪 Совет

Начните с `EXPLAIN (ANALYZE, BUFFERS)`, если запрос можно безопасно выполнить: так время, строки, повторения и работа с буферами будут видны в одном плане. Если нужно сначала посмотреть только оценки, используйте `EXPLAIN` без `ANALYZE`.
