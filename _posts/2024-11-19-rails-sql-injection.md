SQL-инъекция возникает, когда пользовательский ввод попадает в текст SQL-запроса и начинает работать как часть команды. В Rails удобный API Active Record снижает риск, но не делает безопасной произвольную SQL-строку. Разберём, где проходит граница и как не перепутать защиту запроса с проверкой данных.

---

## 🔍 Как работает SQL-инъекция в Rails?

Представьте: у вас есть поиск пользователей по имени:

```ruby
User.where("name = '#{params[:name]}'")
```

Если передать в `name` значение `' OR '1'='1`, условие превратится в:

```sql
SELECT * FROM users WHERE name = '' OR '1'='1'
```

Условие `'1'='1'` истинно для каждой строки, поэтому запрос может вернуть всех пользователей. Проблема в интерполяции: ввод стал частью SQL, а не значением для сравнения.

### Почему Rails не защищает автоматически?

Active Record безопасно обрабатывает значения, переданные через API условий — например, через хеш или плейсхолдер. Но он не может исправить SQL, который разработчик уже собрал интерполяцией. Риск появляется, когда:

1. Пользовательский ввод вставляют в SQL-строку.
2. Из параметров собирают имена столбцов или другие части запроса без проверки.
3. Полагаются на санитизацию значений там, где нужна проверка допустимых полей и направлений сортировки.

## 💀 Антипаттерны: как ломают ваши приложения

### 1. Конкатенация строк в запросах

```ruby
# Плохо: ввод становится частью SQL
User.where("email LIKE '%#{params[:search]}%'")

# Безопасно от SQL-инъекции
User.where("email LIKE ?", "%#{params[:search]}%")
```

Второй вариант защищает от SQL-инъекции, но `%` и `_` во вводе по-прежнему работают как шаблонные символы `LIKE`. Если нужен поиск именно введённой подстроки, экранируйте их:

```ruby
search = ActiveRecord::Base.sanitize_sql_like(params[:search].to_s)
User.where("email LIKE ?", "%#{search}%")
```

### 2. Динамический `order` из параметров

```ruby
# Не передавайте пользовательский ввод в описание сортировки без проверки
@users = User.order(params[:sort] + " " + params[:direction])
```

Имя столбца и направление сортировки нельзя подставить вместо значений через `?`. Они должны выбираться из заранее заданного списка. Кроме риска SQL-инъекции, произвольный ввод может вызвать ошибку запроса; поведение зависит от версии Rails и формы аргумента `order`.

### 3. Прямое использование `params` в `execute`

```ruby
# Уязвимо: параметр вставлен в текст SQL
ActiveRecord::Base.connection.execute("SELECT * FROM users WHERE id = #{params[:id]}")
```

## 🛡️ Защитные механизмы Rails

### 1. Плейсхолдеры

```ruby
# Безопасные варианты для значения name
User.where("name = ?", params[:name])
User.where(name: params[:name])
User.where("name = :name", name: params[:name])
```

### 2. Плейсхолдеры для значений

Передавайте значения аргументами `where`, а не вставляйте их в SQL-строку:

```ruby
User.where("role = ?", params[:role])
```

Active Record обработает значение так, чтобы оно не стало частью SQL-синтаксиса. Это не означает, что каждый такой вызов обязательно отправляет значение в базу отдельным параметром: способ формирования запроса зависит от API и адаптера. Проверять допустимость самой роли, если она важна для приложения, нужно отдельно.

### 3. Whitelisting для сортировки

```ruby
# В контроллере
def sort_column
  %w[name email created_at].include?(params[:sort]) ? params[:sort] : "name"
end

def sort_direction
  %w[asc desc].include?(params[:direction]) ? params[:direction] : "asc"
end

# В запросе
@users = User.order("#{sort_column} #{sort_direction}")
```

Здесь интерполяция допустима, потому что оба метода возвращают только заранее перечисленные строки. Добавляя варианты сортировки, проверяйте, что соответствующие столбцы существуют и доступны в этом запросе.

## 🧩 Пример с `min_amount`: не путайте инъекцию с проверкой числа

Вот запрос, в котором параметр действительно попадает в текст SQL:

```ruby
Transaction.where("amount > #{params[:min_amount]}")
```

При значении `0 OR 1=1` условие может вернуть строки, которые не должны проходить фильтр. Исправление — передать значение через плейсхолдер. Если фильтр должен принимать только число, сначала проверьте формат ввода:

```ruby
if params[:min_amount].present?
  begin
    min_amount = BigDecimal(params[:min_amount].to_s)
  rescue ArgumentError
    return head :bad_request
  end

  @transactions = Transaction.where("amount > ?", min_amount)
end
```

А вот исходно похожий запрос уже защищён от SQL-инъекции:

```ruby
Transaction.where("amount > ?", params[:min_amount])
```

Строка, похожая на SQL, здесь остаётся значением. Она всё ещё может быть неподходящим числом и привести к ошибке или некорректной работе фильтра — это повод проверять ввод, а не свидетельство SQL-инъекции. Заменять проверку на `to_f` опасно: неподходящая строка может незаметно превратиться в `0.0`.

## 🧪 Тестирование на уязвимости

### 1. Руби-гем `brakeman`

Добавьте в `Gemfile`:

```ruby
group :development do
  gem 'brakeman', require: false
end
```

Запуск:

```bash
brakeman -q -w2
```

Статический анализ помогает находить подозрительные места, но не заменяет проверку конкретных запросов и обработки ввода.

### 2. RSpec-тесты с вредоносными параметрами

```ruby
RSpec.describe "SQL query values" do
  it "treats SQL-looking input as a value" do
    user = User.create!(name: "Alice")
    attack = "' OR '1'='1"

    expect(User.where("name = ?", attack).pluck(:id)).not_to include(user.id)
  end
end
```

Такой тест проверяет пример запроса. Для защиты приложения проверяйте также тот путь, по которому параметр действительно попадает из запроса в контроллер и далее в SQL.

## 🚀 Продвинутая защита: Arel и хранимые процедуры

Для сложных условий можно использовать **Arel** — инструмент построения SQL-выражений в Rails:

```ruby
users = User.arel_table
query = users[:name].eq(params[:name]).and(users[:active].eq(true))
User.where(query)
```

Если процедура принимает одно текстовое значение, его можно обработать через `quote` адаптера Active Record:

```ruby
connection = ActiveRecord::Base.connection
query = "SELECT secure_user_search(#{connection.quote(params[:query])})"
connection.select_value(query)
```

`quote` предназначен для значения, а не для имени таблицы или столбца. Он также не исправит небезопасную сборку динамического SQL *внутри* процедуры. Для обычных запросов Rails удобнее использовать условия Active Record с плейсхолдерами.

## 📝 Вывод: правила параноика

1. **Никогда** не интерполируйте `params` напрямую в SQL.
2. Передавайте значения через условия Active Record: хеш, `?` или именованные плейсхолдеры.
3. Имена таблиц, столбцов и направления сортировки выбирайте из разрешённого списка: плейсхолдеры предназначены для значений.
4. Проверяйте ввод по правилам приложения: защита от инъекции не делает любое значение допустимым.
5. Проверяйте запросы тестами с вводом, похожим на SQL, и используйте **Brakeman** для поиска подозрительного кода.
6. Strong parameters ограничивают mass assignment, но сами по себе не защищают SQL-запросы.

> «Доверяй, но проверяй» — плохой принцип для работы с `params` в Rails. Сначала определите, где значение, а где структура запроса, и не позволяйте вводу подменять последнюю.
