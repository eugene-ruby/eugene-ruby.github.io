Ты добавил колонку `metadata` с типом `jsonb`, сложил туда всё подряд, а потом начал писать вот так:

```ruby
where("metadata @> ?", { status: "error" }.to_json)
```

И это **работает**. А на подходящих запросах может помочь GIN-индекс.

---

## 🧠 Что такое `@>`?

Это оператор **«содержит»**: слева значение JSONB, справа — структура, которую мы ищем внутри него.

```sql
-- Найдёт записи, у которых metadata содержит поле status со значением "error"
SELECT * FROM logs WHERE metadata @> '{"status": "error"}';
```

Он работает и с вложенными структурами:

```sql
metadata @> '{"meta": {"country": "RU"}}'
```

Здесь совпадёт объект с `meta.country = "RU"`, даже если в `metadata` есть другие поля. Если же нужно сравнить значение по пути, пригодятся `#>` и `#>>`.

---

## 🚀 Почему это круто?

1. **Гибкость** — поля с меняющейся структурой не обязательно выносить в отдельные колонки.
2. **Возможность индексации** — GIN-индекс может ускорить подходящие фильтры, но его нужно подбирать под запросы.
3. **Поддержка в ActiveRecord** — условие можно передать в `where(...)`.

---

## 🧱 Но нужен индекс!

Если таблица большая и фильтр по `metadata` используется часто, стоит рассмотреть GIN-индекс:

```ruby
add_index :logs, :metadata, using: :gin
```

По умолчанию такой индекс использует `jsonb_ops` и поддерживает, в частности, `@>` и проверку ключей через `?`, `?|`, `?&`.

Если запросы используют главным образом `@>`, можно вместо него выбрать `jsonb_path_ops`:

```sql
CREATE INDEX idx_logs_metadata_gin ON logs USING GIN (metadata jsonb_path_ops);
```

`jsonb_path_ops` подходит для `@>`, но не заменит индекс с `jsonb_ops` для проверок ключей через `?`, `?|` и `?&`. Не создавай оба индекса автоматически: каждый занимает место и добавляет работу при записи. Даже при наличии индекса PostgreSQL может выбрать `Seq Scan`, например для небольшой таблицы или условия, которое возвращает много строк. Проверяй план конкретного запроса через `EXPLAIN`.

---

## 📦 Типовые примеры

```ruby
# Лог с определённым статусом
Log.where("metadata @> ?", { status: "ok" }.to_json)

# Вложенная структура
Log.where("metadata @> ?", { meta: { os: "linux" } }.to_json)
```

---

## 😱 Когда это ломается

* Без подходящего индекса фильтрация по большой таблице может оказаться дорогой. При этом GIN-индекс на `metadata` не ускоряет автоматически условия вида `metadata ->> 'status' = ...`: для часто используемого выражения может понадобиться отдельный индекс.
* `.where(metadata: { ... })` задаёт сравнение значения колонки, а не проверку вхождения через `@>`. Если в JSONB есть дополнительные поля, результат может отличаться от ожидаемого.
* При работе с вложенными ключами легко перепутать проверку вхождения с извлечением значения по пути.

---

## 💡 Лайфхаки

* Для проверки структуры и значений используй `@>`, а не поиск по текстовому представлению JSONB через `LIKE` или `ILIKE`. Если нужен именно поиск по подстроке, сначала извлеки текстовое значение через `->>` или `#>>`.
* Проверяй `EXPLAIN`: он покажет, какой план выбран. Наличие индекса само по себе не гарантирует, что он будет использован.
* Следи за временем выполнения запросов: на большом объёме данных неудачный фильтр может стать дорогим.

## 📘 Справочник операторов JSONB

| Оператор или функция | Назначение | Пример |
|---|---|---|
| `@>` | Содержит структуру | `'{"a":1, "b":2}'::jsonb @> '{"a":1}'::jsonb` → `true` |
| `<@` | Содержится в структуре | `'{"a":1}'::jsonb <@ '{"a":1, "b":2}'::jsonb` → `true` |
| `?` | Есть ли ключ верхнего уровня | `'{"a":1}'::jsonb ? 'a'` → `true` |
| `?\|` | Есть ли хотя бы один из ключей верхнего уровня | `'{"a":1, "b":2}'::jsonb ?\| array['x','a']` → `true` |
| `?&` | Есть ли все указанные ключи верхнего уровня | `'{"a":1, "b":2}'::jsonb ?& array['a','b']` → `true` |
| `#>` | Извлекает JSONB по пути | `'{"a":{"b":"c"}}'::jsonb #> '{a,b}'` → `"c"` как JSONB |
| `#>>` | Извлекает текст по пути | `'{"a":{"b":"c"}}'::jsonb #>> '{a,b}'` → `'c'` как текст |
| `->` | Извлекает JSONB по ключу | `'{"a":1}'::jsonb -> 'a'` → `1` как JSONB |
| `->>` | Извлекает текст по ключу | `'{"a":1}'::jsonb ->> 'a'` → `'1'` как текст |
| `jsonb_array_elements()` | Разворачивает массив JSONB в строки | `SELECT jsonb_array_elements('[1,2,3]'::jsonb)` → три строки |

`?`, `?|` и `?&` проверяют ключи верхнего уровня объекта; для вложенного объекта сначала извлеки его через `->` или `#>`. `#>` и `->` возвращают JSONB, а `#>>` и `->>` — текст, который можно сравнивать в `WHERE`.

## 💎 Использование JSONB в Rails

Rails не предоставляет обёртку над всеми JSONB-операторами, но условия с ними можно передавать в `where(...)`.

### 🔍 Примеры с `@>`

```ruby
# Проверка, что metadata содержит поле status = "ok"
Log.where("metadata @> ?", { status: "ok" }.to_json)
```

```ruby
# Проверка вложенного ключа
Log.where("metadata @> ?", { meta: { browser: "Safari" } }.to_json)
```

### ❓ Проверка ключа с `?`

```ruby
# Проверка, что ключ "error" существует на верхнем уровне
Log.where("metadata ? 'error'")
```

Если имя ключа приходит извне, передавай его через именованный параметр:

```ruby
Log.where("metadata ? :key", key: "error")
```

### 🔗 Получение вложенных значений

```ruby
# Выбрать записи, у которых metadata->>'status' = 'ok'
Log.where("metadata ->> 'status' = ?", 'ok')
```

```ruby
# Глубокое сравнение: metadata#>>'{meta,browser}' = 'Firefox'
Log.where("metadata #>> '{meta,browser}' = ?", 'Firefox')
```

---

### 💡 Советы

* Для этих условий достаточно строки SQL с параметрами в `where(...)`. Если в другом месте нужен `Arel.sql(...)`, передавай в него только заранее заданное выражение, а не непроверенный пользовательский ввод.
* Значения извне передавай через параметры, а не вставляй в SQL-строку. `.to_json` нужен здесь для сериализации структуры, передаваемой в `@>`.
* Проверь, чтобы в `schema.rb` колонка `metadata` была указана как `jsonb`:

```ruby
t.jsonb :metadata, default: {}, null: false
```

---

📢 **Важно:** при работе с JSONB в Rails различай сравнение целого значения и запросы к его частям:

* `.where(metadata: { ... })` не заменяет `@>`: это не поиск по части объекта.
* `.pluck(:metadata)` вернёт **всё значение колонки**, а не конкретное поле внутри.
* `.order("metadata ->> 'score' DESC")` сортирует по тексту: например, `'10'` окажется раньше `'2'` при сортировке по возрастанию. Если `score` хранит числа и нужна числовая сортировка, потребуется приведение типа с учётом возможных некорректных значений.

---

📌 *Вывод*: JSONB удобен для данных с гибкой структурой, но запросы к нему нужно выбирать осознанно: `@>` проверяет вхождение, операторы извлечения возвращают JSONB или текст, а польза индекса зависит от конкретного условия и данных.
